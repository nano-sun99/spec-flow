# 工作指南：按交付物分析体量、依赖与拆分

> 本文件提供可替换的分析方法，不另定义拆分审批或开单时机。流程顺序见 [one-path](one-path.md)，结构选择与必要依赖判据见 [gate-details](gate-details.md)，交付/批次信息归 [phase-handoff](phase-handoff.md)。历史案例留 [rationale](rationale.md) R15、R16、R28；不据此恢复旧“只拆 issue”的自动回退（依据：rationale R37）。

## 一、先找可验收成果

从目标、实际改动面和依赖找可独立说明的交付结果，不只按行数、章节、前后端或会话长度机械切。编码、测试、提 PR 通常是完成同一成果的工作；需要分别推进/验收/安排节奏的里程碑才是需说明的多阶段。

准备拆与不拆的真实比较：每个候选子件交什么、范围多大、还保留哪些阶段、依赖谁、能否并行，以及总纲/执行 spec/父子 issue 的维护代价。通常多阶段值得拆，不可分则说明为什么。不确定工期写估计，不说成实测。

用户选择后的结构及变化处理由 gate-details 负责，不在指南中再设卡。总纲保持共享设计与索引，子件各承接一个完整成果和本份验收；不用总纲再重复派一份全范围任务。

## 二、交付物地图与依赖表达

地图是设计视图，不是新台账平台。下面按信息而非列数组织，项目已有表达能覆盖就复用：

| 需要看清 | 推荐写法 |
|---|---|
| 子件身份与成果 | 稳定组标识/编号、规格链接、产出、消费与边界 |
| 文件归属 | 谁负责共享件、各自独占/不碰哪些范围 |
| 就绪与安排 | 开始、合入、发布分别依赖什么事实，可并行组与硬前置波次 |

依赖宜用“提供方 → 消费方”的有向边，交代具体契约/数据/配置运行时/发布验收产物、就绪条件、证据、责任方和挡住哪一步。文件重叠不自动等于语义依赖；既有共享文件又有接口依赖时分别看清，不能只画地盘。

例如 A 提供导出合同，B 实现调用：合同冻结和测试夹具可让 B 先开工；A 实现未合入可能挡 B 合入；生产配置未就绪可能只挡发布。不要把三种就绪混成“等 A 全部完成”。运行时互相调用不自动等于实施循环等待。

## 三、怎样发现拆法的缺口

沿依赖逐条检查，看看是否存在 A 等 B、B 又等 A 的实施环，同一产物多 owner/无 owner，仅写“等另一份完成”却没有具体结果，或者声称独立发布但实际只能同批。

可通过冻结共享契约、测试夹具、兼容安排、明确的同批合入或发布收尾责任使路径清楚。硬前置不伪装并行，软协调不伪装阻塞；共同发布不必倒退成巨型规格。无法说明可行路径时回结构决定，不自动把一份大 spec 换成多张阶段执行单。

共享判定只保留一个正文 owner，其余引用；文件冲突优先明确单一修改方。真实并行的 Git 锁及保护约束仍读 [worktree-lock](worktree-lock.md)，不由本指南给出规避方法。

## 四、身份、父子和后加子件

稳定身份利于跨 spec/文件/issue 追踪；可沿项目体例用日期+主题、S01/S02。编号是身份，不是波次；不因排期变化重编号，不批量改旧文件。总纲标识、子件身份、上下游与条件能对得上即可，不硬套头部模板。

父子关系表示归属；真正挡进度的才是阻塞关系。总览只跟踪，跨份验收明确由哪份承接，不等待父单关闭才允许所有子件开工。平台不支持原生关系时用双向链接并如实报告，不为建关系擅自升级/安装工具。

后加子件可能接手旧 owner、共享产物或依赖。先对照当前设计来源，把变化写清并同步真实现行地图/依赖；已合并正文需实质修改时，回 gate-details 的改旧规格决定，不用新子件悄悄覆盖旧决定。机械补链接按相应豁免；不能用历史方案重写现行事实。

开单与批次视图的必要信息只由 phase-handoff 定义；本指南可辅助核对，不新增额外审核轮次、agent 数或审批路线。
