# 交付与交接：信息、来源和更新责任

> 本文件只定义 spec / issue / PR / 候选交付所需信息及留痕。流程状态的含义与衔接只在 [one-path](one-path.md)，授权识别与放行只在 [gate-details](gate-details.md)，完成只在 [done-criteria](done-criteria.md)。记录沿用原字段，不新建台账或固定报告文件（依据：rationale R37）。

## 一、交付信息与更新责任

信息留原 issue 的交接/交付区；没有 issue 的直接干任务由原任务 PR 承接适用信息。已有字段足够就引用，不另抄正文。不要求手工复写 PR 每个代码文件，但不能从实际 diff 反推“没改就是不需要交付”。

| 信息组 | 必要内容 | 维护责任与时点 |
|---|---|---|
| 获批依据 | spec 仓内路径、获批版本完整提交、方案 PR；批准修订的适用版本 | 方案作者开执行单时填；实施者开工核当前应实施版本 |
| 澄清记录 | `grilling-cards` 的轮次、每轮问题与用户决定；未用原因 | 方案作者写 spec 时填；直接干由原任务 PR 承接 |
| 预期交付 | 实现成果/模块、必要测试入口、配套文档明确落点、所需共享约定 | 从获批 spec 提取；实施确定真实位置时同步；不是分拣者靠猜 |
| 全部实际来源 | 所有相关实现/补充 PR 与各自完整合入提交；文档真实位置，含改名/归档 | 实施者每次相关 PR 合入回填，保留此前来源，不只留最后一份 |
| 必要依赖 | 候选/发布所需 issue、共享 spec/契约、版本、就绪条件与满足证据 | 开单沿用 spec，实施者补实际满足结果；无则记无及原因 |
| 就绪证据 | 通过的测试/验收结果及链接，本任务是否仍有部署义务 | 实施者验证后填；仅命令、失败记录或标签不冒充通过 |
| 候选结果 | 挑选 PR、合入候选分支完整结果提交；spec、实现/测试、配套文档、依赖逐类核对结果 | 分拣者核当前实际候选、合入后回填；各类记本次纳入/已在核验/不适用及原因 |
| 合入预演 | 预演分支/提交、staging 基线、合并后构建与本 issue 验收证据 | 实施者在整条合入闸前填；失败重做 |
| 四类核对 | spec、实现/测试、文档、依赖逐类结果与证据 | 实施者在整条合入闸前填；发布记录引用 |
| 标签证据 | 当前标签、事实与证据、用户确认记录 | agent 每次动作后提议；用户确认后换 |

“不适用及原因”描述真实未发生/不需要的对象，不是免掉已发生动作的证据。任务已经挑选进入候选，缺 PR/结果提交就补原记录，不能把该字段临时标不适用来关单；有实际来源存于另一原记录时引用其可核位置，不猜值、不另造账。

直接干无 spec / 执行 issue：原任务 PR 承接目标、验收、实际来源与证据；无 issue 标签，发布记录手工列该任务（分支、PR、commit、验收证据），不能靠标签查询（依据：rationale R39）。

采用 staging 线时，整条 issue 合入 staging 前必须有合入预演和四类核对；缺一项不放进合入闸。发布记录按 issue 引用这组信息，不重抄。标签只是辅助视图，交接区正文状态仍是权威；冲突时停下报告（依据：rationale R40）。

spec 保留目标、范围、验收、结构与必要依赖的设计权威；issue 是当前执行和实际来源。PR 正文用「关联 issue：#N」，不用 Closes / Fixes / Resolves 自动关单；没有 issue 就写任务范围，不造假编号（依据：rationale R22）。开单时验收未勾；合并后只勾已真正满足项，评论「代码已合」与来源，不把未做部署或验证写成全部完成。

### 原字段与阶段记录

`spec-flow 交接` 区沿用：流程状态、实施授权、Spec、Spec 合并 commit、方案 PR、上游/ADR、实施范围、阶段/停止点、接手条件/当前状态、授权记录。

- **方案作者**：规格合并并开单时写当前状态、待明确委托、永久规格/完整版本、原方案 PR、做什么/不做什么/验收入口/已知限制、阶段与已声明停止点；当前事实写尚未认领实施工作区。上游/ADR 按项目约定一跳可达，未采用不引入制度。
- **实施者**：委托接收、认领、PR形成、必要验收与回填时更新当前状态/实际工作区/分支/当前提交/未做项；失败、撤销、暂停与恢复记录原阶段、原因和受影响范围。状态定义不在本文件重写。
- **分拣者**：使用本节预期与全部来源核当前候选，记录真实结果，不建立第二份交付账；缺字段补原记录，缺产物则由实施方补交付和验证。
- **收尾者**：按 done-criteria 勾已满足验收、更新来源/结果与状态，关单/放锁依各自正文；不回写冻结规格的目标/范围来迁就当前实现。

项目已采用 issue 状态标签时，映射只读 [issue-status-labels](issue-status-labels.md)；标签不替代交接区正文状态。

## 二、授权与接手留痕

判断某句话是否授权、接管或恢复只见 gate-details；这里列授权记录所需信息。交接 issue 追加在正文授权记录小节；无交接区旧单可写原 issue 评论。只追加，不篡改历史，不同时保留两份生效授权。

- 对象：执行 issue 编号，或无 issue 的直接任务及其范围。
- 方式：`issue-direct` / `same-window-handoff` / `takeover`，无 issue 任务记录当场明确入口。
- 用户原话与可核记录时间。
- 本次范围；相对获批依据的缩小明确记出，不借记录扩大范围。
- 同窗口入口摘录交接报告中的 Spec / 执行 issue / 下一步；定向入口记不适用。
- Spec 合并 commit 核对：固定完整提交与当前应实施版本是否相符；无规格旧任务记不适用，不补造已批准版本。
- 基线与锁核对：实际 `git fetch`、`git status`、`git worktree list` / `git branch --list 'issue/<N>'` 摘要，工作区/目标与规格/项目映射一致。

接管追加新授权原话、方式、时间、范围及旧记录链接；认领失败或撤销回退时保留旧记录并标未生效/已撤销及原因。当前状态事实回填原交接区，不以辅助评论、标签或旧摘要悄悄覆盖正文冲突。

## 三、结构、批次与关系

结构以获批 spec 为设计来源。拆分组从总纲交付物地图和依赖派生批次视图；不拆从该 spec 的交付物/路径派生，不另建表。开单报告、父单或交接报告承接批次、执行 issue、产物、前置、可并行组及合入/发布安排；可用适合客户端的表达，不固定列数。

单 issue 说明本批不拆、无并行项及原因；多 issue 说明可并行与硬前置波次，契约未冻结或依赖缺口如实指出。稳定组标识/子件身份贯通 spec 与 issue，父单只跟踪；原生父子/阻塞关系建立与否记实际结果，不把归属和阻塞混为一谈。具体设计方法见拆分指南，开单与结构放行见闸口正文。

## 四、交接报告与验证记录

交接报告交代：方案已交付、实施是否获委托；规格永久链接/完整版本、执行 issue、范围、批次安排、当前未做和限制、下一步由谁做。未委托时明确等待实施指令，结合 gate-details 的入口给可用命令；不用固定口吻/逐字起终点复述代替这些信息。

测试/假仓记录包含输入、预期、实际动作/产物、证据位置、结论和验证范围。只跑静态检查不写成客户端已执行；使用夹具、模拟平台或有限工具时明确说明；未实测部分如实披露，不把测试中的选择用于真实派审、合并或生产放行。

发布记录的载体与生产操作由已采用 release 及项目现有约定承接，本文件不复制发布模板；当前任务的预期/来源/证据仍留原任务，发布记录引用而非第二份复制账。
