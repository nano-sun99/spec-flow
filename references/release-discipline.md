# 选修：Git 分支流程与发布

> `release` 是同一个既有采用入口，包含 Git 分支流程与必要发布，不新增第二套开关。默认关闭；不因项目复杂自动启用。采用动作只见 [apply-to-project §九之三](apply-to-project.md)。本页不维护采用项目名单（依据：rationale R32、R33、R37）。

## 采用口径

- 默认：选修，不因项目复杂自动启用
- 本次按需读取：用户明确要求本次按本备忘录执行时读取，先核本次适用形态
- 项目级采用：通过 `apply-to-project` 的 `release`，或项目指令明确声明已采用时生效；注明单主线/三层及实际分支映射
- 项目入口：项目指令只留中央链接、已选形态和项目实际落点，不复制流程正文
- 项目资产：不新增可执行资产；发布记录仍用一张 `release:` issue，有 `issue-type` 挂 `chore`，没有不挂类型；不自动建分支/tag/开关
- 执行时点：任务开分支/PR 定目标前、进入候选前、发布前对齐、发布后回填；hotfix 继续原发布记录
- 验收：假仓核分支映射与完整候选，实际项目靠发布记录及真实验证；文档检查不证明已构建/部署；重复采用幂等

依赖仍由 `issue-status` 提供状态标签，采用前核既有接入；不借本轮重做标签或自动迁移。类型缺失不妨碍发布记录使用纯文本标题。未采用不新增 tag、长期分支或发布记录要求。

## 一、Git 分支形态

采用时说明当前项目的真实形态与映射，不从本页的示例分支名推定已获准建分支。既有项目缺映射先查真实指令、分支与发布约定；仍不明交用户决定，不在普通任务中擅改接入。

| 已选形态 | 任务起点与 PR 目标 | 候选/成功版本 |
|---|---|---|
| 单主线 | 从远端 main/master 的实际映射开短期任务分支，PR 回该主线 | 主线始终可发布；从固定不可变 tag 构建 |
| 三层 | 从远端集成分支（如 dev）开任务分支，规格/实现/普通文档 PR 都回集成分支 | 按任务完整挑入候选（如 staging）；验证成功后生产分支（如 master）留同 tag 快照 |

通用 worktree 的 main/master 示例服从这里的已选映射；有 issue 仍用 `issue-N` 锁，不在共享主检出切分支。hotfix 仍从真实生产 tag 切，不从集成/候选/生产分支 HEAD 切。

单主线的前提是主线始终可发布，未完成行为有明确默认关闭开关及清理期限；做不到时应让用户明确选择三层或维持原项目制度，不自动添 develop/uat。环境是部署目标，不必等于另一长期分支；长期 release/x.y 只用于确有多生产版本并行的项目，不借本轮重设计。

图的阶段与衔接只在 [one-path](one-path.md)；本页只映射 Git 对象和选修发布操作。权限、审核、修订和每份独立合并确认只在 [gate-details](gate-details.md)。

## 二、按任务形成完整候选

三层下普通文档与需求同走 dev → staging，不为文档另开热修/标签收尾路径。pick PR 以一个任务为范围，包含其必要方案/实现/补充来源与就绪依赖；不把“一个单”误解为“只挑最后一个实现 PR”。

分拣前先读原任务的**预期交付**与获批 spec，再查方案 PR 和**全部实际实现/补充 PR**、完整合入提交、文档实际位置及通过证据。交付字段与更新责任唯一见 [phase-handoff](phase-handoff.md#一交付信息与更新责任)，不在发布记录再建一份逐文件账。

对当前候选核四类结果：

- **spec**：本任务及必要共享合同的获批内容在；已归档核真实路径与正文，不只挑原路径删除。
- **实现/必要测试**：本任务实际来源及所需测试齐全；缺源、失败或仅命令不算通过。
- **配套文档**：预期文档确实交付且当前内容正确；PR diff 没出现不等于不需要。
- **必要依赖**：进入候选/发布所需版本、产物和证据就绪；父子归属不是一概阻塞。

已有内容不重复挑，但核版本/正文而非仅路径；没有某类的按事实记不适用及原因，不补造产物。缺记录先补原记录，缺产物先补交付并按原要求验证，再核候选。不能靠猜把四类标完整。

只带本任务相关补丁，不整段 merge dev，不把共享文件整体覆盖为 dev 的移动最新版，不夹其他未就绪任务；对冲突按获批共享约定协调。拆分/归档和必要依赖属于任务内容，不等于多造一套工作流。涉及 merge commit 的来源先核实际非 merge 提交，不能盲目 cherry-pick merge commit；可用 `git log --no-merges <merge>^..<merge>` 辅助找来源，仍核 diff 与任务范围。

挑选 PR 沿原审核/修订与独立合并确认；合入后回填原任务的挑选 PR、候选完整结果提交和四类纳入/已在核验/不适用结论。发布前再核当前内容，曾经合入不证明没被后来删除或覆盖。

无部署义务的普通文档不额外发布服务或建文档热修，内容留 staging 随下次正常版本进 tag/master。**是否已经完成只回 done-criteria 判定，包括原任务必要记录；本页不另给简化的完成条件。** 代码暂不发不等于无需部署；文档站、生成输入、运行配置按实际影响而非后缀/类型判断。

## 三、合并与候选边界

单主线合并前核行为完整、未完成部分有关闭开关、不让本期带半成品；跨迭代开关保留上线后一个迭代内清理期限。三层把发布就绪检查放在准备 pick 的候选 PR，集成分支可以保留还没进入本批的工作，但不因此提前关单。

分支合入不等于已发版。每份规格、实现、文档、挑选或回填 PR 的审核/合并均按 gate-details，不在本页设置豁免、额外审核档位或批量合并授权。

## 四、发布记录

仍是一张 GitHub `release:` issue，不新增记录平台。单主线标题沿用 `release: vYYYY.MM.DD`，三层按项目既有版本规则（本页原推荐见 §十二）。milestone 只是分组视图，不是第二账本；生产结果写原记录，成功后 hotfix 继续重开同一张记录。

可沿用下列原记录信息，版式可随项目：

- 本批目标 tag/完整提交、上一个实际生产 tag、窗口与执行者（不适用写明）；首次发布的基线或部署前快照。
- 本期 issue 范围、排除项、真实就绪证据与依赖；引用原任务交付区，不重抄逐文件来源。
- 增量核对的未知/搭车项、未就绪项及处置，非部署项和已经通过 hotfix 上线的内容。
- 本批明确批准记录、已核候选、已知风险、验证与回滚目标/可用性。
- 实际 tag/完整提交、构建产物及 sha256（不适用写明）、部署单元/时间、真实验证结果。
- 失败原因、回滚/hotfix 及回灌结果、线上版本台账、待验证/转出项和关单结论。

发布准备已开始的记录按原约定挂进行中；失败保持 open 直到按既有恢复流程收口，先不发保留结论供下轮复用或按用户决定关闭。不从任务合并自动创建发布记录或执行生产；批准对象与停止见 gate-details。

## 五、状态与就绪门槛

| 当前事实/标签 | 就绪判断 | 候选/发布处置 |
|---|---|---|
| 未开始/进行中，或待测试 | 实现或所需测试验收未完成 | 不进本批；已进发布基线则阻塞处置 |
| 待上线 | 有通过结果/用户验收、依赖和四类交付齐全才是候选 | 不是只贴标签即可发 |
| 等拍板/受阻，或待上线无证据 | 未就绪 | 不进本批；仅阻挡真正消费其缺失产物的任务 |
| 待验证 | 已上线，剩可主动验或已批准例外 | 不重发，不占下一期池；继续必要验证 |
| 无部署义务成果 | 按实际影响核，不由 docs 标签一律推断 | 列非部署项；原任务必要记录与完成只按 done-criteria，不用“记录待补”豁免 |

单主线或已挑入候选的未就绪/搭车代码不能只从发布卡划掉：既有处置是等验收、明确关闭开关、获准回滚该合并；临时 release 分支仅紧急例外，需用户同意。不借“分拣”自己运行危险 Git/配置动作。必要回滚目标产物可用或平台能回滚；不可用阻塞；首次发布按已记部署前快照/原项目恢复办法。

## 六、发布前对齐

先读本批原发布记录及范围，回到任务预期/全部来源核依赖与当前候选内容，再查发布基线增量。单主线基线为主线映射，三层为候选映射，不拿只有成功快照的生产分支去找全部功能提交。

增量起点为最近实际生产 tag（含 hotfix）；首次使用记录好的初始基线，不临时换起点。PR 归属优先正文「关联 issue：#N」，提交标题仅线索；squash/merge 历史结合 PR 来源核，不仅凭 git log。未知来源不静默放行。生产 tag 里已有内容及已上线 hotfix 标明排除，不作为搭车阻塞。

把当前可发、未就绪、非部署、未知/搭车分别对齐，不要求固定四张表。当前四类交付仍在、必要依赖已满足、没有其他未就绪内容搭车，才具备本批放行事实；冲突按 §五 原处置，不用菜单为已混入基线的代码假造剔除。

发布卡所需对象/范围、未答与失效条件只在 gate-details。实际批准内容和风险/排除/验证贴原发布记录；任何未获准生产动作不因下节命令存在而自动执行。

## 七、发布与 hotfix

保留既有操作边界，不重做项目生产手册：常规从固定不可变 tag 构建，不从 HEAD；单主线 hotfix 从最近实际生产 tag 切 `hotfix/<tag>-<slug>`，在修复提交打临时 tag（如 `v2026.11.03-hotfix.1`），从该 tag 构建；回主线后在下一轮对齐标已上线，不重发。三层回灌/快照沿 §十二。

hotfix 工作区基准为生产 tag，是普通任务分支起点的既有例外，issue 锁及独立 worktree 安全不变。回滚仍重新部署上一个生产 tag/可用产物；首次失败用原快照/恢复方案，不从失败目标 tag 推断真实生产基线。临时/废弃 tag 不移动、不删除，按原记录明确排除错误基线。生产/危险 Git 操作仍需相应明确授权。

## 八、发布后回路

按项目既有验证检查实际产物/部署端身份、健康、关键接口和错误日志，覆盖本批约定验证项。tag 只是版本名，不证明构建、部署或验证成功。

成功后才更新成功快照与实际版本台账，回填原记录。issue 标签分拣唯一见 issue-status-labels：能主动验或已批准长尾留下，不能验且未批准的按原规则转出；有必要留下项不冒充关单。失败按既有回滚/hotfix 流程记录原因及结果，不推进成功快照、不抹掉失败证据。

一个 tag 是整棵树的版本快照，不代表所有服务此刻在线同版；发布记录分清本批部署单元与实际版本。快照之后才产生的结果/台账正常进入开发分支，不能倒灌已固定 tag；生产分支台账可能滞后，线上事实以实际产物/部署记录核，不靠路径或分支名推断。

## 九、长期维护分支

确有多个生产版本同时维护时才考虑原来的 `release/x.y`；仅接 bugfix 并按原约定回主线。没有这类需求不新增长期 release 分支，本轮不设计新的版本制式或恢复流程。

## 十、不采用时

两段流程照走，不改项目分支模型，不自动建 dev/staging，不新增 tag、开关或发布记录义务；已有项目明确生产约束仍有效，不能把未采用选修当成免生产验证。

## 十一、验证边界

本页是 Markdown 行为规则，不新增 CI、脚本、Hook、执行引擎、配置语言或授权平台。静态检查只证明必要章节、链接和契约存在；假仓/实际客户端测试仅证明所测输入的动作，不能冒充真实生产、所有客户端或全模型认证。接入、安装、配置、测试、实际发布分别报告末态。

## 十二、三层的既有 Git 操作与版本约定

三层流向保持：功能/规格/文档 PR → 集成分支 → 按任务完整 pick → 候选 → 不可变 tag → 构建/部署/验证 → 生产成功快照。没有整段集成合候选、没有 `pick/*-to-生产分支`。本节保留已有安全不变式和操作，不把中央交付变成实际项目发布。

### 原有不变式与禁区

收尾时生产分支的树等于最近成功生产 tag 的树；候选超出上个实际生产 tag 的内容都有本批归属；生产 tag 不移动、不删除。快照提交保留 tag 父提交，tag 用附注 `git tag -a`，否则可达性与 `git describe` 可能不成立。

不从生产分支切普通功能、不从任何 HEAD 构建、不在生产分支 revert 未上线内容、不用 merge/reset/read-tree 覆盖生产快照、不在共享主仓切分支/做快照、不直改另一个 worktree 已检出的本地引用。不因文档给出命令就获得保护分支 push 权限。

### 原有固定候选与快照步骤

发布前先把生产分支独有文档按原任务交付回开发线，核本批单元及 DDL/配置/数据前置和破坏性变更；冻结候选后不再 pick。沿用 `git log --oneline --first-parent --no-merges <上一个生产 tag>..<候选分支>` 辅助核增量，但结合全部 PR/当前补丁，不只看该命令推断交付完整；逐项核 `git tag --contains <commit>` 的实际生产身份，废弃/未成功 tag 不作已上线证明。hotfix 掉队检查沿用对真实生产 tag 的 `git cherry <候选> <tag>`，未带入先停。

获相应批准后固定完整提交，附注 tag 并立即 push，`git ls-remote --tags origin` 核远端可复现；只从 tag 在独立工作区构建。生产步骤仍依原项目手册，保留既有断流 → 验静 → 本批 DDL（如有）→ 替换 → 验 → 复流，不由中央新增真实操作。

验证成功后沿用不碰工作区的快照方法；以下是原操作示例，不是授权或自动执行入口：

```bash
set -euo pipefail
VER=v26.11.0; PROD=master
git fetch origin --tags
BASE=$(git rev-parse "origin/$PROD")
NEW=$(git commit-tree "$(git rev-parse "$VER^{tree}")" \
      -p "$BASE" -p "$(git rev-parse "$VER^{commit}")" \
      -m "release: ${VER}（tree = tag）")
git push origin "$NEW:refs/heads/$PROD"
git fetch origin
git diff --quiet "$VER" "origin/$PROD" || { echo "⛔ 快照 tree 与 tag 不一致"; exit 1; }
```

不加 `git update-ref refs/heads/<生产分支>` 去移动已检出分支；它可能污染其他工作区。本地确要移动引用时沿既有 Git 保护与用户授权，不把示例扩成长期任意写权限。

三层 hotfix 从实际生产 tag 切，附注 hotfix tag、push 后只从它构建，验过补同口径成功快照，再 merge 回集成和候选，不用 cherry-pick 破坏 tag 祖先链。不能拿候选下一批内容冒充 hotfix。失败继续原恢复流程，不推进 master。

### 沿用版本约定

三层原推荐 `vYY.M.PATCH`：两位年、月不补零、当月已有最大 PATCH + 1，尚无则 .0；常规和 hotfix 共用计数，不另加后缀。已有日期式老 tag 留不动，采用项目保留其已明确命名规则，不因本轮重构强迁。

查创建时间仍带 `refs/tags/`：`git for-each-ref --format='%(creatordate:short)' "refs/tags/$VER"`。打错 tag 保留并在原发布记录标废弃，取生产基线/掉队检查时排除；tag 存在不等于成功生产版本。按单元独立发版的既有项目核实际单元/tag，中央快照不宣称所有单元在线同版。
