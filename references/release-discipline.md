# 备忘录：发布纪律（A 方案：单主线 + tag 发布）

> 这是可选备忘录，不改变 spec-flow 两段流程的步骤与顺序，默认不启用。只有用户明确要求采用，或项目规则已经声明采用，才按它执行；不因项目复杂自动启用。采用动作见 [〈应用到项目〉§九之三](apply-to-project.md)，本仓不维护采用项目名单。

## 采用口径

- 默认：选修，不因项目复杂自动启用
- 本次按需读取：用户明确要求本次按本备忘录执行时读取
- 项目级采用：通过 `apply-to-project` 的 `release`，或项目指令明确声明已采用时生效
- 项目入口：采用后由 `apply-to-project` 写入项目指令的指针节
- 项目资产：不新增可执行资产；只写项目指令指针，不复制正文
- 执行时点：合并 PR 前、发布前、hotfix 时
- 验收：机械检查不适用；dogfood 验证默认不启用、采用后按发布线执行、重复采用不重复建

## 一、什么时候值得用

不是每个项目都需要。满足任意两条适合采用；最终是否采用仍由用户明确要求：

- 同时有多个功能在开发，发布时只带其中一部分；
- 发布频率高（每周或更快），没有固定窗口；
- 出现过「未完成代码跟着发布上线」的事故；
- 需要从生产版本直接切 hotfix，且不想被主线上的未完成代码干扰。

只有一条主线的简单项目，不要为了「规范」启用它；两段流程照走即可。

## 二、发布线

- **一条长期主线**（`master` / `main`）：功能分支从它切，短生命周期，合并后删除。
- **不新增长期 `develop` / `uat` 分支**：环境差异用部署流程区分；要长期 uat 环境，也把它当部署目标，不当版本选择器。
- **主线始终可发布**：这是本备忘录的核心假设。做不到，就先给未完成的大功能加开关，或者不要采用本备忘录。

## 三、合并闸

- **未完成的功能不进主线**：PR 合并前核对「代码是否完整、未完成部分是否有开关、会不会让本期发布带上半成品」；不能就留在功能分支。合并闸不替代测试环境验收。
- **跨迭代大功能带开关**：代码可以早合，行为默认关闭；本期要上的功能在发布前按计划打开，不在本期的保持关闭；开关要有清理期限（上线后一个迭代内删掉）。
- **发布前逐条核对**：列出本期包含的 issue，逐条确认已验收（已验收 = 验收项已勾，或用户批准转出 / 长尾）；有一条没验收，就停下。单主线下，已合进主线的代码无法从 tag 里剔除——发现未完成，只能停发布、回滚该合并，或确认开关已关闭。
- **所有 PR 单独确认合并**：照主流程的合并卡，不因为是文档或回填就跳过。

## 四、发布与 hotfix

- **发布从不可变 tag 取码**：每次发布在要发布的 commit 上打不可变 tag（常规发布打主线 commit，如 `v2026.11.03`；紧急 hotfix 打 hotfix commit）；构建记录基线 commit；发布只从 tag 构建，不从主线 HEAD 构建。
- **hotfix 从生产 tag 切**：`hotfix/<tag>-<slug>`，修完合回主线；下个发布 tag 自然带上，不需要同步第二条长期分支。hotfix 的 worktree 基准是生产 tag，不是 `origin/main`（主流程工作区规则的例外）；有 issue 号按 `issue-<N>` 锁，无 issue 号按 `worktree-lock.md` 的「没有 issue 号的活」边界，命名 `hotfix/<tag>-<slug>`，无锁可领。
- **紧急发布**：在 hotfix 构建 commit 上打临时 tag（如 `v2026.11.03-hotfix.1`），从该 tag 构建上线；同时把 hotfix 合回主线，避免下个版本回归。已发布的 tag 不移动、不删除。
- **回滚**：重新部署上一个生产 tag；临时 hotfix tag 保留，不删除；tag 不可变，回滚目标明确。

## 五、发布前核对清单

- [ ] 本期包含的 issue 逐条列出，全部已验收（定义见 §三）
- [ ] 本期要上的功能开关已按计划打开，并记录清理期限
- [ ] 不在本期的未完成功能开关已关闭
- [ ] 发布 tag 已打，构建基线 commit 已记录
- [ ] 回滚目标是上一个生产 tag，产物可用
- [ ] 发布后版本台账 / 发布记录已更新

## 六、什么时候才升级到长期 release 分支

只有一种情况值得：**同时维护多个生产版本**（客户锁定旧版本、API 多版本并行）。这时才从主线切长期 `release/x.y`，只收 bugfix，修完回主线。

没有多版本维护需求，不要养长期 release 分支；临时 hotfix 分支已经够用。

## 七、不采用时

- 不读本备忘录；
- 不改项目分支模型；
- 不新增 tag / 开关 / 发布清单要求；
- 两段流程照走。

## 八、验证边界

本备忘录只写 Markdown 规则，不新增 CI、脚本、Hook、分支保护或 tag 自动化；`scripts/check-docs.sh` 绿只证明文档登记与预算，不证明任何客户端执行。项目采用后是否真的按 tag 发布、是否真的挡住未完成代码，要靠项目自己的发布记录和发布前核对来验证。
