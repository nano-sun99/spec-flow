# 备忘录：发布闭环（A 方案：单主线 + tag 发布）

> 这是可选备忘录，不改变 spec-flow 两段流程的步骤与顺序，默认不启用。只有用户明确要求采用，或项目规则已经声明采用，才按它执行；不因项目复杂自动启用。采用动作见 [〈应用到项目〉§九之三](apply-to-project.md)，本仓不维护采用项目名单。

## 采用口径

- 默认：选修，不因项目复杂自动启用
- 本次按需读取：用户明确要求本次按本备忘录执行时读取
- 项目级采用：通过 `apply-to-project` 的 `release`，或项目指令明确声明已采用时生效
- 项目入口：采用后由 `apply-to-project` 写入项目指令的指针节
- 项目资产：不新增可执行资产；只写项目指令指针，不复制正文；发布记录是一张 `chore` issue，按〈发布记录〉模板建
- 执行时点：发布前建发布记录、做发布前对齐与发布卡；发布后按〈发布后回路〉回填；hotfix 时
- 验收：机械检查不适用；dogfood 验证默认不启用、采用后按发布线执行、重复采用不重复建

## 一、什么时候值得用

不是每个项目都需要。满足任意两条适合采用；最终是否采用仍由用户明确要求：

- 同时有多个功能在开发，发布时只带其中一部分；
- 发布频率高（每周或更快），没有固定窗口；
- 出现过「未完成代码跟着发布上线」的事故；
- 需要从生产版本直接切 hotfix，且不想被主线上的未完成代码干扰。

只有一条主线的简单项目，不要为了「规范」启用它；两段流程照走即可。

## 二、发布线

- **一条长期主线**（`master` / `main`）：功能分支从它切，短生命周期，合并后删除。
- **不新增长期 `develop` / `uat` 分支**：环境差异用部署流程区分；要长期 uat 环境，也把它当部署目标，不当版本选择器。
- **主线始终可发布**：这是本备忘录的核心假设。做不到，就先给未完成的大功能加开关，或者不要采用本备忘录。
- **发布从不可变 tag 取码**：常规发布在要发布的 commit 上打 `vYYYY.MM.DD`；构建记录基线 commit；发布只从 tag 构建，不从主线 HEAD 构建。
- **hotfix 从生产 tag 切**：`hotfix/<tag>-<slug>`，修完合回主线；下个发布 tag 自然带上，不需要同步第二条长期分支。
- **回滚**：重新部署上一个生产 tag；临时 hotfix tag 保留，不移动、不删除。

## 三、合并闸

- **未完成的功能不进主线**：PR 合并前核对「代码是否完整、未完成部分是否有开关、会不会让本期发布带上半成品」；不能就留在功能分支。合并闸不替代测试环境验收。
- **跨迭代大功能带开关**：代码可以早合，行为默认关闭；本期要上的功能在发布前按计划打开，不在本期的保持关闭；开关要有清理期限（上线后一个迭代内删掉）。
- **所有 PR 单独确认合并**：照主流程的合并卡，不因为是文档或回填就跳过。
- **发布前不再逐项补验收**：合并后的就绪由〈状态与就绪门槛〉判定，主干里的意外搭车由〈发布前对齐〉处理；合并闸只负责挡住半成品进主线。

## 四、发布记录

### 形式

- 一张 GitHub issue，标题 `release: vYYYY.MM.DD`，类型 `chore`；项目没有 `issue-type` 时，标题保留 `release:` 前缀，不挂类型。
- 用 milestone 做分组可以，但 milestone 只是视图；**发布记录是唯一账本**，不维护第二份列表。
- 发布记录在发布前创建，开单挂 `进行中`；发布后回填；归档 = 关单 + 写结论；验证失败时保持 open，直到回滚 / hotfix 收口。

### 模板

```markdown
## 发布记录：v2026.11.03

- 目标 tag：v2026.11.03
- 基线 commit：
- 回滚 tag：上一个生产 tag（首次发布写「无 / 部署前快照」）
- 发布窗口：
- 发布人：

### 本期范围

- [ ] #N 标题（类型 / 状态 / 证据链接）
- [ ] #N 标题（类型 / 状态 / 证据链接）

### 依赖

- #N blocked by #M；#M 未就绪时，本项不发

### 非部署项

- #N docs / chore，合并即算上线，不占本期发布范围 / 不要求单独发布 / 不进发布卡纳入项

### 就绪证据

- #N：测试结果 / 验收评论链接

### 主干增量核对

- 上个生产 tag：v...
- 上个 tag 到 main 的 PR：#...
- 不在本期范围的主干 PR：#... → 处置：等 / 关开关 / 回滚
- 非部署项 PR：#... → 列入〈非部署项〉，不按搭车阻塞

### 冲突处置

- #N 待测试 / 进行中 → 等 / 关开关 / 回滚该合并 / 紧急 release 分支（仅用户同意）

### 发布结果

- 发布卡确认：确认人 / 时间 / 结论 / 评论链接
- tag / commit：
- 产物 sha256：
- 部署时间：
- 验证：健康检查 / 关键接口 / 错误日志
- 回滚产物核对：可用 / 不可用
- 回滚演练：是 / 否

### 回填

- 按 `issue-status` §三〈上线时分拣〉处理：留下 → `待验证` + 下次看；转出 → 当场评论后关单；全验完 → 关单
- 发布记录归档 = 关单 + 写结论
```

### 谁维护

- agent 在发布前准备发布记录、拉标签池与主干增量、填冲突项。
- 用户确认发布卡；agent 不打 tag、不部署，直到用户明确确认。
- 发布后 agent 回填结果；失败的记录不关，直到回滚 / hotfix 收口。

## 五、状态与就绪门槛

| 状态 | 含义 | 发布动作 |
|---|---|---|
| `未开始` / `进行中` | 未进主干或还在改 | 不进本期；出现在主干增量里 = 异常，先查 |
| `待测试` | 已合主干，等测试环境验收 | **不进本期**；出现在主干增量里 = 阻塞，等 / 关开关 / 回滚 |
| `待上线` | 测试环境验过，或本项目不需要测试环境；等发生产 | 候选；必须有验收证据，否则不算就绪 |
| `待验证` | 已上线，剩正式环境验证或批准的长尾项 | 已上线，不重发；不占本期池 |
| `等拍板` / `受阻` | 等决定或被外部条件卡住 | 不进本期；依赖它的项也阻塞 |

规则：

- **证据门槛**：`待上线` 的证据 = issue 评论里的测试命令 / 结果链接，或用户验收评论；没有证据 → 不就绪，不进发布卡。
- **非部署项**：`docs` / `chore` 或明确不需要生产部署的项，在发布记录〈非部署项〉列出，合并即算上线，不要求 tag。
- **依赖**：发布记录〈依赖〉列出 blocked by / 父子单；被依赖项未就绪时，依赖项不能进入本期。GitHub 原生依赖可用就用，不可用就手写一行。
- **标签转换**：发布成功后按 `issue-status` §三〈上线时分拣〉执行——能验或方案期批准的长尾 → `待验证` + 「下次看」；不能验且未批准 → 当场评论「以下不在本单跟踪：…」后关单；全验完 → 关单。`待测试` 不动；`待验证` 不动。
- **采用依赖**：`release` 依赖 `issue-status` 提供状态标签；没有 `issue-status` 就不启用 `release`。`chore` 类型由 `issue-type` 提供；没有 `issue-type` 时发布记录标题写 `release:`，不挂类型。
- **回滚目标可用**：上一个生产 tag 的产物可部署，或部署平台能回滚到该 tag；不可用 → 阻塞。首次发布写「无 / 部署前快照」。

## 六、发布前对齐

### 顺序

1. **读发布记录**：本期范围、依赖、非部署项、就绪证据。
2. **拉主干增量**：`git log <上个生产 tag>..main`；首次发布以初始基线 commit（或首个 tag 前最后一个 commit）为起点。把 PR 按「关联 issue：#N」归位；无关联的 PR 单独列为“未知”，不静默放行。
3. **对齐四张表**：可发（`待上线` + 证据 + 在增量）、未就绪（`待测试` / `进行中` / `等拍板` / `受阻`）、非部署项（按 `docs` / `chore` 类型判，不要求记录预先列出）、搭车（在增量但不在本期范围且非非部署项）。
4. **冲突处置**：搭车项默认阻塞，只有三类处置——等它验收、关开关、回滚该合并；临时 release 分支只当紧急例外，须用户同意。非部署项不适用这三类处置，直接列〈非部署项〉。
5. **发布卡**：列出发什么、不发什么、风险、回滚 tag；用户明确确认后才打 tag。

### 为什么不做逐项菜单

逐项菜单把“上游没挡住”的失败变成发布时的人工选择题，既慢又容易漏。常规路径只保留三类处置；如果同一版反复出现搭车项，说明合并闸或开关没守住，应回到上游修，而不是在发布时加更多选项。

### 发布卡

发布卡至少包含：

- 本期纳入的 issue（附证据）；
- 本期排除的 issue 与原因；
- 主干增量里的未知 / 搭车项与处置；
- 目标 tag、基线 commit、回滚 tag，以及回滚产物可用性（首次发布写「无 / 部署前快照」）；
- 已知风险与验证项。

未确认、被关闭、选“先不发”或用户暂停 → 停止，不打 tag、不部署。

## 七、发布与 hotfix

- **tag 不可变**：常规发布在要发布的 commit 上打 tag，构建记录基线 commit，发布只从 tag 构建，不从 HEAD 构建。
- **hotfix**：从生产 tag 切 `hotfix/<tag>-<slug>`；在 hotfix commit 上打临时 tag（如 `v2026.11.03-hotfix.1`），从该 tag 构建上线；修完合回主线，写回同一张发布记录。
- **worktree**：hotfix 的 worktree 基准是生产 tag，不是 `origin/main`（主流程工作区规则的例外）；有 issue 号按 `issue-<N>` 锁，无 issue 号按 `worktree-lock.md` 的「没有 issue 号的活」边界。
- **回滚**：重新部署上一个生产 tag；首次发布没有上一个 tag 时，用部署前快照 / 项目现有回滚方案。临时 hotfix tag 保留，不移动、不删除；回滚后开 bug / hotfix，回到发布记录。

## 八、发布后回路

1. **验证**：按项目现有发布验证跑健康检查、关键接口、错误日志；至少覆盖发布记录〈发布结果〉里的验证项。
2. **成功**：按 `issue-status` §三〈上线时分拣〉处理——留下 → `待验证` + 下次看；转出 → 当场评论后关单；全验完 → 关单。发布记录归档 = 关单 + 写结论；更新线上版本台账。
3. **失败**：回滚到上一个生产 tag；开 bug / hotfix；在发布记录写失败原因、回滚结果；下一轮按 hotfix 路径回到同一张记录。
4. **长尾**：`待验证` 的正式环境验证项按 `issue-status` 的“下次看”规则收口；不占下一期发布池。

## 九、什么时候才升级到长期 release 分支

只有一种情况值得：**同时维护多个生产版本**（客户锁定旧版本、API 多版本并行）。这时才从主线切长期 `release/x.y`，只收 bugfix，修完回主线。

没有多版本维护需求，不要养长期 release 分支；临时 hotfix 分支已经够用。

## 十、不采用时

- 不读本备忘录；
- 不改项目分支模型；
- 不新增 tag / 开关 / 发布记录要求；
- 两段流程照走。

## 十一、验证边界

本备忘录只写 Markdown 规则，不新增 CI、脚本、Hook、分支保护或 tag 自动化；发布记录是一张带模板的 issue，不是新的项目管理工具。`scripts/check-docs.sh` 绿只证明预算、路径、链接、双语与四个发布闭环章节存在，不证明任何客户端执行。项目采用后是否真的按 tag 发布、是否真的挡住未完成代码，要靠项目自己的发布记录和发布前核对来验证。
