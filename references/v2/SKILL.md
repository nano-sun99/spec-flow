# spec-flow v2

- **是什么**：一个决策环境，不是流程编译器。给出五层知识（铁律 → 阶段合同 → 决策目录 → playbook → 案例），由 agent 按当前事实自选路径。
- **何时用**：通过根入口默认使用，也可直接点名 v2。遇到项目固定版本与本次请求冲突，先按[根入口的版本规则](../../SKILL.md#选择版本)给选项并等答复。
- **硬闸**：D0-D7 八类用户决定（实施委托、范围与结构、设计确认、spec 合并、每份 PR 的两个时点〔审核档位 / 合并〕、整条 issue 合入 staging、生产发布、回滚）。走到需要该授权的动作才停，先按下方运行循环处理当前请求。八类之外遇到 L0-7 承重缺口，走异常协议停。
- **需求澄清由 v2 自己完成**：`grill-me`、`grilling`、`grilling-cards`、Superpowers 的 `brainstorming`、`writing-plans` 及同类技能都不是本流程的依赖。即使客户端列出了它们，也不去查找、读取、调用、推荐或提示安装。缺写文件等项目工具时只报告实际限制，不去读技能找替代路径，不改其他文件充当交付。
- **v1/v2 冲突**：v2 任务内同时读 v1 与 v2 时，**v2 铁律与入口优先**；v1 保留三类用途——项目采用只按 [v2 接入边界](50-adapters/README.md) 借用 v1 说明；v2 playbook 明确指向的 v1 操作细则（如 issue-type 迁移、release 历史操作）按该处引用；历史档案按需查。两处对同一动作给出不同要求，按 v2，并报告「v1 与 v2 不一致：<一句>」。不静默二选一。

## 运行循环

先核用户原话、项目事实、获批材料及适用的分支、issue、锁。指南里的举例不构成本项目的决定。

| 本轮的实际任务 | 下一步动作 |
|---|---|
| 核实已有的结果能否满足本次请求 | 满足就直接交付并结束。例如既有 CSV 的记录已按获批范围过滤、格式也吻合，答复列出范围依据和结果路径。此时没有待执行的改动、待选的范围或需要确认的计划。 |
| 完善现有需求稿，只缺一项会影响范围、目标、验收、权限或数据的决定 | 用**业务选项卡**直接问这一项。比如导出范围待定，按钮给「仅本人」「全组」，允许自填；答了写回同一份稿。范围已定则引用原决定。选择范围不授权取数。 |
| 对照用户给的设计与现有规格 | 在同一稿中核对实际交互、状态和接口，尚无依据的细节记为待核。一次对照涵盖多个页面状态，仍是同一份交付。 |
| 明确的单处修改或按已有委托交付 | 一句话说明后执行并验证。改判据 / 术语 / 范围 / owner / 边界 / 分类时，按 [change-protocol](30-playbooks/change-protocol.md) 交 manifest 并跑 `check-change.py`；纯措辞改名且不改变判定 / 范围 / 默认 / 权限的，不触发本协议。改名时，原文件用来定位旧名，目标文本取自用户原话；单字母也可以是完整名称。「把表头 A 改为 B，顺序不变」就把原列名 `A` 替换成字面值 `B`，再核对其他列和数据。 |
| 新任务且范围不平凡，例如按同一结算口径更新列表、报表、接口三处交付物 | 发下方的**计划卡**。实施委托或个别契约尚待核实，也能先让用户核对改动面和验收。 |

按总纲判断计划卡的三个触发条件：新任务且范围不平凡、即将不可逆、预计要问用户超过 3 次。分别按本轮实际交付、下一步动作和真实缺口判断。简单直接干、已有需求补一个答案，以及在同一稿内做对照，通常不触发；如果确有不可逆动作或超过 3 次的实际提问，仍发计划卡。

**计划卡模板**（只替换题干的花括号，两个按钮保持原样）：

~~~json
{"question":"计划覆盖{交付物}，用{场景}验收。待核事项：{事实缺口或无}。是否确认这份计划？","options":["确认计划","调整计划"]}
~~~

用客户端选项工具发卡，无工具才给等价文字。题干中的待核事项只列事实，另有需要再独立询问。两项按钮都只改变计划的状态；确认后若尚无实施委托，就报告计划已确认并结束本轮。

**其他需要答复的决定**各自调用客户端选项工具（如 `ask_user_question`）。没有该工具才在正文给等价选项。两种形式的授权边界相同。例如只完善导出规格时，可问：「导出范围选仅本人、全组，还是你补充的范围？答复只用于更新这份规格，实际取数和执行导出另需授权。」用户答复后，交付更新过的原稿，本轮结束。

用户只要求做对照或只读检查时，交付对照结果或检查报告即结束。写入、安装等后续授权在用户请求相应动作时再处理。

**执行前核对写入对象**。用户要求改现有文件，就改指定对象并验证；用户要导出时，源文件只作输入。需要新文件而工具不能创建，就报告未生成，保持输入字节原样。只有实际产生了产物才报告生成成功。
收尾只在任务改变了行为或教会了什么失败时写案例。发现铁律缺项可提议替换或合并，不自行增添。

## 异常协议

- 先查 L0-L2 落点，再查 L3 playbook、L4 案例，并核实际事实（`file:line`、diff、锁、证据）。
- 只有不需用户决定的可逆做法才可用安全默认。遇到不可逆、无安全默认、多 owner 或承重缺口，按 L0-7 停；只问影响本次任务的问题，不把假设的新功能列为选项。
- 依运行循环给 2–3 个可行选项，说明差别与推荐，允许自填。
- **卡片未答或取消**：结束本轮。最终答复只交代哪项待定、哪些动作已停，保留原卡供回答。卡片已答就引用用户原话完成本次请求，补充答案也按原话留证。收尾处不再追加“是否继续”、下一阶段的选择或同一组文字选项。
- 失败、崩溃、监控异常：停住上报，不自动回滚、不静默重试（L0-4）。

## 重读触发

任何不可逆动作前，重读 L0-1 与当次决策卡；长任务被压缩后，不假设自己还记得铁律。

- 显式使用 v1 时，旧文档仍可按[根入口的 v1 导航](../../SKILL.md#v1-导航明确指定时使用)读取。
- 本文件只做入口与导航，不写步骤、不新增规则；各层各有唯一 owner。
- 需求已有明确实施委托时从交付段接手，不重开访谈或另写规格。
