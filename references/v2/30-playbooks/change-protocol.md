# Playbook: 替换式变更（改判据 / 术语 / 范围 / owner / 边界 / 分类）

> **示例非必须**：本页的分类、台账列、扫描步骤和重建方法是可替换方法，不是必须顺序；按实际情况调整。
> **规范性**：只有标「（规范性）」的章节；它们引用 L0-L2，不新增、不放宽闸口。必须做的完成条件在 [10-stages](../10-stages.md) 设计段与交付段；载体边界在 [15-records](../15-records.md)；闸口证据在 [20-decisions](../20-decisions.md)。本页只给方法与证据格式。

- **适用**：改判据、术语、范围、owner、边界或分类；包括新增一条会改变既有行为的规则，以及退役一条旧规则。只改错字、只换措辞且不改变判定 / 范围 / 默认 / 权限的，不触发本协议。
- **失败模式**：只加新句、不列旧 owner；只 grep 新词，把「0 命中」当反向冲突已清；把已合并 / 冻结正文当草稿删改；把历史记录、迁移别名当活跃残留删掉；新增规则不说明取代或合并了哪条。
- **证据**：旧→新台账（行数 / 活跃残留 / 白名单 / 未处置）、双扫描记录、载体分流结果；D2 / D3 / D4 与审核报告按 [20-decisions](../20-decisions.md) 和 [review](review.md) 的字段出示。

## 一、变更分类（规范性）

每条改动先归一类：

| 类 | 判据 | 必须回答 |
|---|---|---|
| 新增 | 不改变任何既有判定、范围、默认、权限或 owner | 为什么没有旧规则被取代？若答不出，改判为替换 |
| 替换 | 同一触发下，旧规则的行为 / 判据 / owner 被新规则取代 | 旧规则是谁、在哪、现在什么状态、怎么处置 |
| 退役 | 旧规则不再生效，且没有同触发的新规则接替 | 谁接手；若无人接手，写「无接替」及事实理由 |

拿不准按替换处理。新增规则不得与现行规则同触发不同行为；出现这种情况，先归为替换并裁决，不许两条并存。

## 二、旧→新台账（规范性）

最少列这些列；项目已有 registry / 映射表 / 台账的，用项目的表，不另建第二份：

| 旧 owner（文件:行 / ID） | 旧口径（一句话） | 处置 | 新 owner（文件:节 / ID） | 证据 | 状态 |
|---|---|---|---|---|---|
| ... | ... | 删 / 换 / 合并 / 降为别名 / 保留历史 / 不适用 | ... | 扫描命中 / diff / 测试 / 引用链 | 已处置 / 白名单 / 未处置 |

- **一行一条旧规则**，不是一行一个文件；同一文件里两句相反的话要分两行。
- **处置只有六种**：删、换、合并、降为别名、保留历史、不适用（必须写事实理由）。没有「以后再说」。
- **状态只有三种**：已处置、白名单（写明为什么可以留）、未处置（阻断合并）。
- 台账是本次变更的证据，不是全仓规则登记表；不建全局 registry，避免第二份真相漂移。

## 三、双扫描（规范性）

### 1. 活跃残留扫描

扫旧词、旧 ID、旧档位、旧默认值、旧路径、旧 owner 名。**扫描范围 = 本次变更影响的现行载体（spec / 现行文档 / 索引）+ 引用这些载体的入口；历史记录与案例只用来对账，不作为活跃引用来源。** 命中后逐条判：

- 仍是现行引用 → 未处置，改掉。
- 只在白名单内 → 标白名单，写事实理由。

**白名单至少包含**：已合并 / 冻结 spec 的基线正文；历史记录与案例（带日期、标「历史快照」）；迁移别名（只出现在「原 X → 新 Y」行）；带「旧称 / 原 X / 历史快照」标记的对照句；刻意保留的旧版抓手（文件内已写明「别当残留删」）；外部契约 / 已发布 API 的旧名（加兼容层说明）。白名单不是「懒得改」的筐，每条要有事实理由。

### 2. 反向冲突扫描（不是关键词扫描）

对每个被改的触发条件，读所有可能说反话的地方，找这五类：

| 类 | 长什么样 |
|---|---|
| 同触发不同行为 | 同一动作，一处说「必须删」，另一处说「不许改」 |
| 旧 owner 仍被当现行 | 新规则已取代旧规则，但旧文件仍被引用为「唯一正文」 |
| 多 owner | 同一判定在两个 L1 / L2 文件各有一份规范性正文 |
| 验收 / 范围 / 默认不一致 | 新规则改了默认值或范围，旧验收仍按旧值判 |
| 权限 / 载体错配 | 新规则要求删改，但目标载体是已合并 / 冻结 / 只追加记录 |

扫描方法：先按语义读同层和相邻层（L0 → L1 → L2 → L3 → L4），再用关键词辅助；关键词只用于找线索，不能单独作为「无冲突」的证据。**反话通常用旧词汇写**（「只追加不篡改」「不改正文」「不重写获批正文」「默认不动冻结正文」「留作历史别名」），只 grep 新词一定漏。

## 四、载体分流（规范性）

载体规则引用 [15-records](../15-records.md)。

| 载体 | 处置 | 证据 |
|---|---|---|
| 未合并、未冻结的草案 / 现行文档 | 原位删或替换旧句；同一决定只留一个正文 | diff + 台账行 |
| 已合并 / 冻结 spec 正文 | 不改正文；事实写错走带日期勘误，新增 / 取消 / 改变范围或验收走 D3 新 spec | 勘误链接或 D3 记录 |
| 拍板 / 授权 / 审核 / 修订记录 | 只追加不篡改；旧记录正文不改不删；新记录写「取代 <旧记录>」 | 追加记录链接 |
| 历史记录 / 案例 / 旧规格 | 保留；头部标「历史快照（日期）：现状见 X」；新旧互链 | 标记 + 链接 |
| 迁移别名 / 旧 ID | 只保留在「原 <旧> → <新>」迁移行或别名字段；不得作为现行引用 | 迁移行链接 |
| 外部契约 / 已发布 API | 不静默删旧名；加兼容层或废弃公告，旧名标「已废弃」 | 契约 / 公告链接 |

载体判不清时按 L0-7 停，不自行选一个继续。**「旧句必须删」只适用于第一行；其余行按各自规则处置。** 这是本协议与 [15-records](../15-records.md) 的边界，不得把第一行外推到全仓。

## 五、重建通道（规范性）

满足任一条件，不走逐句替换，按新不变量重建受影响的结构：

- owner 变了（同一判定换正文位置）；
- 边界 / 分类变了（术语重新分组、规则层级变化）；
- 旧结构已经无法用「一行换一行」表达（同一决定出现三份以上正文、补丁互相引用）。

重建步骤：

1. 写清新不变量（一句话：什么必须为真）。
2. 列出受影响的文件 / 章节 / 决定 ID（按 owner，不按关键词）。
3. 按新不变量重推这些段落的正文；旧正文只作行为对照，不逐句修补。
4. 用旧行为清单对账：每条旧行为要么被新结构覆盖，要么明确退役；不得静默丢失。
5. 走完整的双扫描与台账，不因为「重写」跳过。

重建不是全仓重写；只重建受影响面，其他文件不动。

## 六、证据入闸（规范性）

- **D2**：台账行数 / 活跃残留 / 白名单 / 未处置；未处置 > 0 = 设计未完成。
- **D3**：spec 合并前出示台账；已合并 spec 的旧句不改，按勘误或新 spec 记录。
- **D4**：每份 PR 的合并卡含台账数字；文档类 PR 未交台账 = 未完成。
- **审核报告**：闭合核对按 [review](review.md) 的字段，不把「grep 0 命中」当双扫描完成。
- **直接干**：PR 正文含台账；无 spec 不等于免台账。

## 七、与现有规则的关系

- 本页不新增闸口；完成条件、证据和载体边界分别由 [10-stages](../10-stages.md)、[20-decisions](../20-decisions.md)、[15-records](../15-records.md) 定义。
- 与「只追加不篡改」「已合并不改正文」「默认不动冻结正文」不冲突：那些规则管记录和基线载体，本协议管未合并草案的替换；载体分流表是分界线。
- 与 L0-8 同向：L0-8 要求新增铁律必须替换或合并一条；本协议把同一纪律下沉到 L1-L3 的规则变更，但不改 L0。
- 与 [spec-revision-sync](../../spec-revision-sync.md) 的关系：v1 任务按该页的同步方法；v2 任务按本页。两页不互相改写。

## 八、例子（#190 / #1195）

#190 想把「改口径要删旧句 + 反向扫描 0 残留」抬成 L1 完成条件，但在 5 个文件各加一句，没有台账，也没扫反向冲突；结果与「拍板记录只追加不篡改」「已合并 spec 不改正文」「旧 ID 留作别名」同时生效。它的 `grep 作废|反向扫描` 只扫新词，反话用旧词写，必然 0 命中。

正确做法（用户 2026-11-25 给的样本）：旧口径逐条处置——两档 → 两个读锚点；业务数据档 ALL / 财务=ALL → CUSTOMER_VIEW=ALL；D04/D05/D06/D12/D13 → 别名 / 部分保留 / 取代；A11/A12 改为并集；§0.1 档位表改为同一 CUSTOMER_VIEW；最后 2 处 D17 台账 / D17.2 也改完。检查：表绿（2020 张 / 0 行不一致）；registry 74 行 / 11 列 / 无重复；旧口径扫描 0 命中。未改完的中低项单列，下一批清掉后再做一次正向 + 逆向扫描。

这个样本的关键不是「扫到 0」，是**每条旧口径都有处置和证据**；0 只是台账的结果，不是方法本身。
