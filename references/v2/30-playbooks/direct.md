# Playbook: 直接干（无 spec / 无 issue）

> **示例非必须**：本页的走法是一条走通过的路，不是必须顺序；按实际情况调整。
> **规范性**：只有标「（规范性）」的章节；它们引用 L0-L2，不新增、不放宽闸口。

- **适用**：改动边界清楚、无获批 spec / 执行 issue；用户选择直接干，或 agent 判定落点后报告且用户未否决。直接干只免方案期，不免交付与合并闸。
- **一条走通过的路**：说明计划与改动面 → 切 `task/<slug>` → 实现与测试 → PR 先不合 → 部署 PR 分支验收 → 合并闸 → 发布记录手工列。
- **失败模式**：先合再测；把「改动小」当免闸；用 issue 标签找直接干任务；跳过 worktree；PR 正文不写目标 / 验收 / 证据。
- **证据**：PR 正文（目标、范围、验收、来源）、构建与验收结果、合并确认、发布记录中的手工条目。
- **注意**：这是示例，不是必须顺序；闸口相关章节是规范性的，不能自行放宽；改动闸口证据须用户批准。

## 一条走通过的路（示例非必须）

1. **入口澄清与计划说明**：做最小澄清，写清改哪里、怎么改、验收是什么；尚无批准基线时，先说明计划与改动面再执行（L0-6）。不用 spec 不表示不用澄清。
2. **落点判定**：先核是否有 open issue 覆盖这次改动、分支是否已合入候选；判定方法见 [issue playbook](issue.md) 的落点表。agent 查事实、给推荐并报告，用户可按 L0-6 否决。
3. **开工作区**：从项目映射的开发基线切 `task/<slug>`，worktree 目录 `task-<slug>`；分支名唯一即锁。映射与锁见 [worktree playbook](worktree.md)。
4. **实现与验证**：改动和必要测试在 task 分支完成；有测试环境就把 PR 分支部署上去跑验收；没有则写不适用及事实理由。
5. **PR 先不合**：PR 提到目标分支（staging 线为 staging），正文写目标、验收、来源与证据；先不合，验收通过后才摆合并卡。
6. **合并闸（D4）**：先选当份审核档位与修订范围，审核 / 修订完成后单独摆合并卡；确认后合入。
7. **收尾**：发布记录手工列该任务的分支、PR、commit、验收证据；不靠 issue 标签查询。批次失败切 `fix/<slug>`，不回已合并的任务分支。

## 失败模式（示例非必须）

- 把 PR 先合进候选再问「用候选测吗」；测试对象已经不是待合入的版本（2026-11-11 演练）。
- 「只改一行」被当成免澄清、免 worktree、免合并闸的理由。
- 发布分拣只查 issue 标签，直接干任务整个漏列（发布说不清的主因之一）。
- task PR 被套上 issue 分支的标签语义；标签与正文冲突时没人停下。
- PR 正文只写「修了个问题」，验收证据和来源都靠会话记忆。
- 批次失败后回到已合并的 task 分支继续改；修复提交与批次基线混在一起。

## 证据（示例非必须）

| 时点 | 证据 |
|---|---|
| 开工前 | 计划说明：改哪里、怎么改、验收；落点判定的事实与推荐 |
| PR 提交 | PR 正文：目标、范围、验收、关联 issue 或无 issue 说明、验证结果 |
| 合并前 | 当份审核结论（或「不审」自查记录）、修订记录、文档检查结果、合并卡 |
| 合并后 | 合入提交；发布记录中的手工条目（分支、PR、commit、验收证据） |

## 闸口（规范性）

- **L0-6 计划说明**：尚无批准基线时，agent 必须先说明计划与改动面再执行；没有基线不代表没有否决点。
- **D4 每份 PR**：两个时点——① PR 提交后选审核档位与修订范围；② 审核 / 修订完成后确认合并。触发、证据、选项与默认以 [20-decisions](../20-decisions.md) D4 为准；直接干的 task PR 同样适用。
- **独立确认**：审核、修订、合并分别是独立授权（L0-5）；不审、零发现、检查绿都不等于合并同意。
- **交付完成条件**：无 issue 时按 [10-stages](../10-stages.md) 交付段的条件分支判定；有测试环境则部署验收，无则写不适用及事实理由。
- **不套 issue 标签**：直接干任务无 issue 标签；发布记录手工列，不用标签查询替代。
- **不新增闸**：本页不新增审核档位、卡片或完成条件；与 L0-L2 冲突时以 L0-L2 为准。
