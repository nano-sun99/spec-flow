# Playbook: hotfix

> **示例非必须**：本页的走法是一条走通过的路，不是必须顺序；按实际情况调整。
> **规范性**：只有标「（规范性）」的章节；它们引用 L0-L2，不新增、不放宽闸口。

- **适用**：生产环境确认缺陷，需要从生产版本切出最小修复；项目已采用 release，且已有至少一个真实生产 tag。
- **一条走通过的路**：从生产 tag 切 `hotfix/<tag>-<slug>` → 只修该问题 → 临时 tag → 从临时 tag 构建验证 → D4 合回主线 / 集成 / staging → 跟下一班车发版。
- **失败模式**：从 staging / 集成 HEAD 切；夹带其他改动；修完立即打生产 tag；cherry-pick 破坏祖先链；首次发布前就开 hotfix；移动或删除临时 / 失败 tag。
- **证据**：基于的生产 tag、修复提交、临时 tag、验证结果、D4 合并提交、原发布记录中的 hotfix 记录。
- **注意**：这是示例，不是必须顺序；闸口相关章节是规范性的，不能自行放宽；改动闸口证据须用户批准。

## 一条走通过的路（示例非必须）

1. **确认基线**：从最近的真实生产 tag 切 `hotfix/<tag>-<slug>`；不从集成分支、候选分支或生产分支 HEAD 切（v1 `release-discipline.md` §一 / §七；L1 发布安全不变式）。
2. **最小修复**：只修这一个问题，不夹带其他改动、不拿候选下一批内容冒充 hotfix。
3. **临时 tag 与验证**：在修复提交打临时 tag（如 `v2026.11.03-hotfix.1`），从该 tag 构建、部署可用环境验证；验证证据贴原发布记录。
4. **D4 合回**：按项目形态合回主线 / 集成分支 / staging；这是独立合并闸，卡上列 hotfix 分支、修复提交、临时 tag、验证证据。
5. **不立即发生产**：修完不立即打生产 tag；跟下一班车走 rc / 最终 tag。三层在 hotfix tag 验过后补同口径成功快照，再 merge 回集成和候选，不用 cherry-pick 破坏 tag 祖先链。
6. **回填**：原发布记录继续同一张记录；标已上线 / 排除；下一轮发布对齐不再重复纳入。

## 失败模式（示例非必须）

- 从 staging HEAD 切 hotfix；修复合入了候选，但生产基线并不是它。
- 顺手带上「反正也要改」的其他提交；hotfix 变成第二班车。
- 修完立即打生产 tag；跳过了 rc、批次和 D6。
- 三层用 cherry-pick 回灌，tag 祖先链断裂，`git describe` / 可达性失效。
- 首次发布还没有生产 tag 就开 hotfix 分支；基线不存在。
- 临时 tag 或失败 tag 被移动 / 删除；后续无法重现验证过的是哪一版。

## 证据（示例非必须）

| 时点 | 证据 |
|---|---|
| 开工 | 基于的生产 tag、hotfix 分支名、基线提交 |
| 修复 | 修复提交、临时 tag、从临时 tag 构建与验证结果 |
| 合回 | D4 卡与合并确认、合回目标分支的合并提交 |
| 发布 | 下一班车的 rc / 最终 tag、原发布记录中的 hotfix 条目 |

## 闸口（规范性）

- **D4 每份 PR（含 hotfix 合回）**：证据另含基于的生产 tag、修复提交、临时 tag、验证证据；触发、选项与默认以 [20-decisions](../20-decisions.md) D4 为准。
- **L0-1**：tag 移动 / 删除、生产写、覆盖生产分支快照都必须用户明确确认；打错 / 废弃 tag 保留并标记，不删除。
- **发布安全不变式**（[10-stages](../10-stages.md) §三）：只从不可变 tag 构建；三层 / staging 的生产分支的树等于最近成功生产 tag 的树，单主线不要求主线树等于旧 tag；不在生产分支 revert 未上线内容；保护分支直推不在普通授权范围。
- **不自动发版**：hotfix 合回不等于生产发布；D6 仍独立触发。
- **不新增闸**：本页不新增决定类型或完成条件；与 L0-L2 冲突时以 L0-L2 为准。
