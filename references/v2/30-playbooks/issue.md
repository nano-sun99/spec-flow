# Playbook: 续已有 issue（实施委托与整条交付）

> **示例非必须**：本页的走法是一条走通过的路，不是必须顺序；按实际情况调整。
> **规范性**：只有标「（规范性）」的章节；它们引用 L0-L2，不新增、不放宽闸口。

- **适用**：用户点名执行 issue（「请做 #N」「开始实施 #N」）、新请求落在某 open issue 的已批准范围内且分支未合入、或接管已认领工作。
- **一条走通过的路**：对表远端 → 落点判定 → D0 授权记录 → 认领 worktree → 实现 PR → 每份合并 → 分支验收 → 预演 + 四类 → 整条合入 → 发布段。
- **失败模式**：拿 issue `open` 当没人认领；未获 D0 就实施；父单 / PR 号当委托；实现 PR 直接合 staging；整条合入用 squash；预演在假树上跑；范围扩大不回 D1 / D2。
- **证据**：授权记录 8 字段、worktree / 锁记录、PR 列表与合入提交、分支验收、预演记录、四类逐项、D5 合并提交。
- **注意**：这是示例，不是必须顺序；闸口相关章节是规范性的，不能自行放宽；改动闸口证据须用户批准。

## 落点判定（示例非必须）

先查事实再给推荐；证据来源包括分支名、PR 正文「关联 issue：#N」、commit `(#N)`、issue 交接区、worktree 锁与发布记录。

| 事实 | 归属 |
|---|---|
| 在某个 open issue 的已批准范围内，且分支未合入候选 | 续该 issue 分支 |
| 命中多个 issue | 列候选给用户选 |
| 无命中，改动边界清楚 | 直接干，开 `task/<slug>` |
| 无命中，有独立验收或需要设计 | 开新 issue，必要时先开 spec |
| issue 已合入候选或已关单 | 不续；走 `fix/<N>` / `fix/<slug>` 或新 issue |

## 一条走通过的路（示例非必须）

1. **对表远端**：`git fetch`、`git status -sb`、`gh issue view N`；核 issue 仍 `open`、获批 spec 版本、当前范围、标签、是否已有锁。
2. **D0 授权识别**：定向入口（`issue-direct`）、同窗口交接（`same-window-handoff`）、接管（`takeover`）按 D0 判定；父单、PR 号、已有锁、审核通过都不算委托。
   - **同窗口入口三条件**：交接报告是最后一条 agent 消息、用户开始意图紧接、恰好一张未授权执行单。开始意图闭集为「开始实施 / 开始干 / 开工」，礼貌前缀不改变含义；「继续」「开始吧」「就按这个做」不替代闭集。中间有问答、工具结果、压缩、新窗口或多执行单时，同窗口入口不成立，只有点名 `#N` 才构成定向委托。
3. **写授权记录**：按 [15-records](../15-records.md) §二 的 8 字段写进原 issue；只追加不篡改，不同时保留两份生效授权。
4. **认领 worktree**：`issue/<N>` 分支、`issue-<N>` 目录；开得成 = 没人做，撞锁停。细则见 [worktree playbook](worktree.md)。
5. **实现**：实现 PR 只回 `issue/<N>`，不直接合候选；每份 PR 走 D4 的两个时点。
6. **分支验收**：按获批 spec 的验收路径在 issue 分支跑；证据贴 issue；四类（spec、实现 / 测试、文档、依赖）逐项核对。
7. **合入预演（staging 线）**：把当前候选合入 issue 分支或临时预演分支，在真实 merge 树上构建并跑本 issue 验收；结果树必须等于真实 merge 树。
8. **D5 整条合入**：卡列 issue、分支、完整提交、预演证据、四类逐项、未处理项、候选当前提交；确认后真 merge，不 squash；标签转「待上线」（需用户确认），分支冻结。
9. **发布段**：批次测试、rc、生产按 [release playbook](release.md)；批次失败按 [batch-fix playbook](batch-fix.md)。

## 影响分析（示例非必须）

实现前先核改动面与影响：按业务词 / 符号在源码检索，读真实 diff 与相关测试，核调用方、分母与实际文件集合。代码地图工具默认停用；只有用户另行明确要求试用 / 恢复时才读。工具自报 `complete` 不证明覆盖全仓，结构图、导入方、影响查询各有独立边界；未验证的结论回落到源码与真实 diff。历史见案例 [2026-10-17 代码地图](../40-cases/2026-10-17-code-map.md)。

## 失败模式（示例非必须）

- `open` 被当成「没人做」：2026-09-16 实测两个 agent 都据此判断，双双做完浪费一份。
- spec 合并、issue 建好就自动开工：2026-10-24 实测一个会话在未获实施指令时认领并改代码。
- 父单 / PR 号 / 已有锁 / 审核通过被当成实施委托。
- 实现 PR 合进 issue 分支后直接报 issue 完成；四类、预演、整条合入都没做。
- 预演用 rebase 或 CI 结果，却没有证明结果树与真实 merge 树一致。
- 整条合入图省事用 squash；merge commit 里看不到各 PR 提交，来源难追。
- 实施中新增接口 / 换范围，不回 D1 / D2；旧批准覆盖新范围。
- 标签当成状态机：合入即转、失败即回退；与交接区正文冲突时不停下。

## 证据（示例非必须）

| 时点 | 证据 |
|---|---|
| 认领前 | D0 授权记录（对象、方式、原话、时间、范围、同窗口摘录、spec 合并 commit、基线与锁核对、生效状态） |
| 认领 | `git worktree list`、分支名、基线提交 |
| 每份 PR | PR 链接、目标分支、完整提交、审核结论、修订记录、文档检查结果、合并确认 |
| 整条合入前 | 分支验收、预演分支 / 提交、候选基线、合并后构建与本 issue 验收、四类逐项 |
| 合入后 | merge commit（真 merge）、标签证据、发布记录引用 |

## 闸口（规范性）

- **D0 实施委托**：触发、证据、选项与默认以 [20-decisions](../20-decisions.md) D0 为准；issue 已关闭、范围扩大、spec 版本不再一致、出现第二份生效授权都使授权失效。
- **D4 每份 PR**：两个时点以 D4 为准；每份单独选档，不沿用规格期。
- **D5 整条合入（仅 staging 线）**：触发、证据、选项与默认以 D5 为准；预演未做 / 未绿、四类缺项、仍有未合入实现 PR 时不合入。
- **L0-5**：每份 PR、每次合入独立确认；同批另一份的同意不延伸到本份。
- **交付前置条件**：独立 worktree、锁键 = 精确分支名、撞锁停，按 [10-stages](../10-stages.md) §三 执行。
- **发布安全不变式**：从 tag 构建、不覆盖生产快照、tag 不移动 / 删除，按 L1 与 [release playbook](release.md)。
- **范围变化**：新增实质内容、换目标、返修、暂停、撤销或要求重审，回 D1 / D2 / D4（L0-6）。
- **不新增闸**：本页不新增决定类型或完成条件；与 L0-L2 冲突时以 L0-L2 为准。
