# Playbook: 回滚

> **示例非必须**：本页的走法是一条走通过的路，不是必须顺序；按实际情况调整。
> **规范性**：只有标「（规范性）」的章节；它们引用 L0-L2，不新增、不放宽闸口。

- **适用**：生产出现崩溃、监控异常或验收失败，用户考虑把生产恢复到上一个可用版本。
- **一条走通过的路**：停住上报 → 收集证据与回滚目标 → D7 → 批准后重新部署上一个 tag / 产物 → 记录结果 → 走 bug / hotfix。
- **失败模式**：自动回滚；回滚目标 tag 不存在；从失败目标 tag 推断真实生产基线；删除或移动失败 tag；回滚后抹掉失败证据。
- **证据**：异常证据（监控 / 日志 / 验收失败）、目标 tag / 快照与可用性、D7 记录、回滚后验证、发布记录更新。
- **注意**：这是示例，不是必须顺序；闸口相关章节是规范性的，不能自行放宽；改动闸口证据须用户批准。

## 一条走通过的路（示例非必须）

1. **停住上报**：异常出现时停止受影响动作，报告事实；不自动回滚、不静默重试、不把失败改写成通过（L0-4）。
2. **收集证据**：监控 / 日志 / 验收失败记录；确认影响范围；确认目标 tag / 快照存在，且其树与打算恢复的生产状态一致。
3. **D7 回滚决定**：卡列目标 tag / 快照、范围、影响、异常证据、回滚目标可用性；用户选「回滚 / 不回滚」，默认不回滚。
4. **执行**：批准后重新部署上一个生产 tag 或可用产物；首次发布没有上一个 tag 时，用部署前快照或项目原恢复方案。
5. **记录**：回滚结果、失败原因、回滚目标、后续动作写进发布记录；发布记录保持 open 直到收口。
6. **后续**：线上问题开 bug 单或走 [hotfix playbook](hotfix.md)；不推进成功快照，不抹掉失败证据。

## 失败模式（示例非必须）

- 监控崩溃后自动回滚；用户还没决定，失败已被掩盖。
- 回滚目标 tag 不存在：全仓只有一颗 tag 时，「回滚到上一个 tag」是一条想象出来的路（#158 链一）。
- 从失败目标 tag 反推真实生产基线；恢复到一个从未成功过的版本。
- 删除 / 移动失败或废弃 tag；事后无法重现当时状态。
- 回滚后直接宣布恢复完成；没有验证实际产物 / 部署端身份和健康。
- 用回滚替代 bug 单 / hotfix；根因没有 owner。

## 证据（示例非必须）

| 时点 | 证据 |
|---|---|
| 停住 | 异常监控 / 日志 / 验收失败原文；受影响范围 |
| D7 前 | 目标 tag / 快照、可用性、与生产树一致性；首个发布时的部署前快照 |
| 回滚后 | 部署单元与时间、验证结果、发布记录更新 |
| 收口 | bug / hotfix 链接、遗留项、关单或继续观察的结论 |

## 闸口（规范性）

- **D7 回滚**：触发、证据、选项与默认以 [20-decisions](../20-decisions.md) D7 为准；异常范围变化或目标快照不可用 / 与生产树不一致时批准失效。
- **L0-4**：失败、崩溃、监控异常停住上报；不自动回滚、不静默重试。
- **L0-1**：回滚属不可逆 / 高风险动作，必须用户明确确认；生产写、tag 移动 / 删除同一口径。
- **发布安全不变式**（[10-stages](../10-stages.md) §三）：回滚目标来自不可变 tag / 可用产物；不覆盖生产分支快照；不删除失败 tag。
- **不新增闸**：本页不新增决定类型或完成条件；与 L0-L2 冲突时以 L0-L2 为准。
