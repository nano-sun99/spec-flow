# Playbook: 新需求开 spec

> **示例非必须**：本页的走法是一条走通过的路，不是必须顺序；按实际情况调整。
> **规范性**：只有标「（规范性）」的章节；它们引用 L0-L2，不新增、不放宽闸口。

- **适用**：新需求值得设计（多端、承重规则、外部契约、不可逆动作），或用户选择开 spec 而不是直接干。已合并 spec 的续接、既有 issue 的实施委托不按本页开场。
- **一条走通过的路**：澄清 → 定范围与结构 → 骨架 → 对照 → 终稿 → 审核修订 → 合并 → 开执行 issue → 停，等实施委托。
- **失败模式**：跳过澄清直接写 spec；把骨架或对照版送去合并；把「方案确认」当送审 / 合并 / 实施授权；spec 写成步骤或固定模板；承重未知留到实施期；在已合并 spec 上改正文。
- **证据**：澄清记录、spec 与 PR、审核结论、修订记录、文档检查结果、spec 合并提交、执行 issue。
- **注意**：这是示例，不是必须顺序；闸口相关章节是规范性的，不能自行放宽；改动闸口证据须用户批准。

## 一条走通过的路（示例非必须）

1. **入口澄清**：加载可用的澄清工具（推荐 `grilling-cards`：读 `grilling` 原文、输出选项卡、每轮最多 4 题）。工具不可用才退回手动提问，并在澄清记录写明原因。记录轮次、每轮问题、用户原话或卡片选择。
2. **定范围与结构（D1）**：给出目标、范围、非目标、验收；有 spec 时另含页面 / 无页面、拆 / 不拆、观察式例外（如适用）；承重未知（数值 / 接口 / 权限 / 数据）逐条列出。
3. **公共骨架**：用最少内容承接已确认的目标、范围、非目标与可判验收；把未解决的设计、接口、业务口径和验收问题标出来。骨架与后续版本是同一份 spec、同一个 PR，不另开设计 PR。
4. **对照**：有页面时，等用户设计稿到位，再沿实际行为梳理角色、交互、状态、数据、异常、权限、接口读写；不代画、不猜完整接口。无页面时，用真实输入输出样例、决策表或契约样例对照；方法见 [spec playbook](spec.md)。
5. **终稿**：把对照结果回写同一正文；承重规则、接口 / 数据、异常 / 兼容、验收与自定选择彼此一致；验收能判对错并覆盖正常、异常、边界和必要回归。
6. **送审与合并（D2 / D3）**：一次列齐「确认 / 改 / 重做」、审核档位、修订范围；审核与修订按 [review playbook](review.md)；结论原样贴 PR 评论；合并 spec 后开执行 issue。
7. **停**：spec 合并 + 执行 issue 已建后，等用户明确实施委托（D0）。方案合并、开单、已有锁、审核通过都不算委托。

## 失败模式（示例非必须）

- 澄清记录只写结论，没有轮次和用户原话；送审 / 合并时看不出需求是怎么定的。
- 把骨架版或对照版当合同送去合并；实施者照未定稿的图纸开工。
- 「方案 Yes」被当成「可以送审」「可以合并」「可以实施」；三者是独立授权（L0-5）。
- spec 按固定章节或步骤排版，读的人看不出这条需求从哪里走到哪里。
- 把页面判错当成接口缺口；CLI 输出、导出报表、接口响应本身不算页面。
- 承重问题写成「实施时再定」；到实施期才发现数值 / 接口 / 权限 / 数据没有 owner。
- 新需求来了直接在已合并 spec 上改正文；旧批准不再覆盖新范围。

## 证据（示例非必须）

| 时点 | 证据 |
|---|---|
| 澄清完成 | 澄清记录：轮次、每轮问题、用户原话与可核时间或卡片选择；未用结构化澄清的原因 |
| 终稿完成 | spec 正文、验收清单、数据迁移 / 回滚 / 兼容 / 外部契约影响（或写不适用及事实理由） |
| 送审前 | 文档检查三态之一：绿 / 红 + 摘要 / 无入口；本次 diff 引入的红已修复 |
| 审核后 | 审核结论原样贴 PR 评论；修订记录；仍有阻断 / 高时不合并 |
| 合并后 | spec 合并提交；执行 issue 链接；交接区字段 |

## 闸口（规范性）

- **D1 范围与结构**：触发、证据、选项与默认以 [20-decisions](../20-decisions.md) D1 为准。页面 / 无页面、拆 / 不拆、观察式例外都在 D1 一次列齐；结构实质变化回 D1。
- **D2 设计与规格确认**：触发、证据、选项与默认以 D2 为准。审核档位与修订范围是 D2 的选项，不是本 playbook 新增的闸。
- **D3 spec 合并**：触发、证据、选项与默认以 D3 为准。改已合并 spec 时走 D3 的条件分支：默认不动冻结正文；新增、取消或改变范围 / 验收含义一律新开一份。
- **D0 实施委托**：spec 合并 + 执行 issue 已建后停下；委托识别以 D0 为准。
- **澄清记录可核**：[15-records](../15-records.md) 第 2 类；只写结论或缺失时，设计段完成条件不成立。
- **文档检查**：摆派审卡前在交付物自己的工作区跑；三态与处置见 [review playbook](review.md) 的文档检查节。
- **授权边界**：审核、修订、合并、实施是不同权限（L0-5）；标签、检查绿、零发现、另一个 agent 的意见都不是用户批准。
- **v1 差异**：`grilling-cards` 从 v1 的硬依赖降为推荐做法（B1 盘点 G1；v1 丢弃项 D4）；不设安装卡，不因缺工具阻断路径，但缺工具要记录原因。

本页不新增铁律、阶段合同或决策类型；与 L0-L2 冲突时以 L0-L2 为准。
