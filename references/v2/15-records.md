# v2 记录与证据（L1）

> 本页是「交付与授权要留什么」的唯一正文。阶段完成条件见 [10-stages](10-stages.md)，用户决定见 [20-decisions](20-decisions.md)，铁律见 [00-constitution](00-constitution.md)。
>
> 记录沿用原 issue 的交接/交付区；没有 issue 的直接干任务由任务 PR 承接。已有字段足够就引用，不另抄正文、不新建台账或固定报告文件。

## 一、11 类交付 / 授权记录

| # | 信息组 | 必要内容 | 维护责任与时点 |
|---|---|---|---|
| 1 | 获批依据 | spec 仓内路径、获批版本完整提交、方案 PR；批准修订的适用版本 | 方案作者开单时填；实施者开工核当前应实施版本 |
| 2 | 澄清记录 | 澄清的轮次、每轮问题与用户决定；未用结构化澄清时写原因 | 方案作者写 spec 时填；直接干由任务 PR 承接 |
| 3 | 预期交付 | 实现成果/模块、必要测试入口、配套文档明确落点、所需共享约定 | 从获批 spec 提取；实施确定真实位置时同步 |
| 4 | 全部实际来源 | 所有相关实现/补充 PR 与各自完整合入提交；文档真实位置，含改名/归档 | 实施者每次相关 PR 合入回填，保留此前来源，不只留最后一份 |
| 5 | 必要依赖 | 候选/发布所需 issue、共享 spec/契约、版本、就绪条件与满足证据 | 开单沿用 spec；实施者补实际满足结果；无则记无及原因 |
| 6 | 就绪证据 | 通过的测试/验收结果及链接；本任务是否仍有部署义务 | 实施者验证后填；仅命令、失败记录或标签不冒充通过 |
| 7 | 候选结果 | 挑选 PR、合入候选分支完整结果提交；四类逐项结论 | 分拣者核当前实际候选、合入后回填 |
| 8 | 合入预演 | 预演分支/提交、staging 基线、合并后构建与本 issue 验收证据 | 实施者在 D5 前填；失败重做 |
| 9 | 四类核对 | spec、实现/测试、文档、依赖逐类结果与证据 | 实施者在 D5 前填；发布记录引用 |
| 10 | 标签证据 | 当前标签、事实与证据、用户确认记录 | agent 每次动作后提议；「待上线 / 待验证 / 关单」必须用户确认后才能换 |
| 11 | 授权记录 | 见下节 | 认领前写；只追加不篡改 |

**「不适用及原因」的语义**：描述真实未发生/不需要的对象，不是免掉已发生动作的证据。任务已进入候选却缺 PR/结果提交，补原记录，不能把字段标不适用来关单；来源存于另一原记录时引用其可核位置，不猜值、不另造账。

## 二、授权记录（8 字段）

- 对象：执行 issue 编号，或无 issue 的直接任务及其范围。
- 方式：`issue-direct` / `same-window-handoff` / `takeover`；无 issue 任务记当场明确入口。
- 用户原话与可核记录时间。
- 本次范围；相对获批依据的缩小明确记出，不借记录扩大范围。
- 同窗口入口摘录交接报告中的 Spec / 执行 issue / 下一步；定向入口记不适用。
- Spec 合并 commit 核对：固定完整提交与当前应实施版本是否相符；无规格旧任务记不适用。
- 基线与锁核对：实际 `git fetch`、`git status`、`git worktree list` / `git branch --list 'issue/<N>'` 摘要。
- 生效状态：生效 / 未生效 / 已撤销及原因；接管追加新记录并链接旧记录，不同时保留两份生效授权。

## 三、4 类补充记录

| 信息组 | 必要内容 | 维护责任与时点 |
|---|---|---|
| 原任务字段 | 流程状态、阶段/停止点、接手条件、交接报告要点、测试记录（输入/预期/实际/证据/结论/范围） | 暂停、恢复、接管、交接时更新；无 issue 由任务 PR 承接 |
| PR 关联 | 只用「关联 issue：#N」；不写 Closes / Fixes / Resolves 等自动关单关键词 | 每次开 PR 时写；防合并瞬间跳过关单与标签收尾 |
| 事故记录 | 仓内真实事故记录的文件位置与摘要；无则写「无」 | 首次出现时登记；B3 建案例库时迁入 |
| 收尾/关单 | 验收项是否全勾、遗留项、观察式例外、发布记录链接 | 收尾者按下方关单判据填 |

## 四、文档载体与读序

四种记录各管一件事，一个事实或决定只设一个正文 owner：

| 载体 | 回答的问题 | 什么时候更新 |
|---|---|---|
| 现状文档（含运维说明） | 系统现在是什么、现在怎么操作 | 事实或操作变化时改唯一 owner；其他地方只链接 |
| spec | 这一次批准了什么需求、准备怎样验收 | 批准前可修订；spec PR 合并且实施 issue 建立后成为基线，此后只加状态、勘误标记与链接，不改正文 |
| ADR（项目已采用时） | 用户作了什么跨任务、长期有效的决定，为什么 | 决定改变时新增 ADR 取代旧 ADR，不静默改正文 |
| issue / PR | 这次实施做到哪了、改了什么、验证证据在哪 | 随实施持续更新 |

**读序**：先核现状文档和生效 ADR（若采用）；实施前必须读当前获批 spec 与验收；只有历史 spec、调研、事故复盘在追溯时按需读。历史记录头部一行写明「历史快照（日期）：现状见 X」，被取代时新旧互链。历史记录与实测冲突时以现状文档及实测为准，不据此取消当前获批目标或改现行 ADR；承重冲突报告来源交用户（L0-7）。

## 五、关单判据

完成是**有限承诺**：约定功能/成果已交付，相关正常、异常、边界和回归测试通过，无未处理的已知阻断缺陷，必要证据齐全。不是保证永远不出 bug，也不是「没测过所以没问题」。

- 以获批范围与预期交付对照真实产物及全部来源，不看实现 PR 合并、某次 diff、标签或一句 PASS。
- 本任务需要的代码、测试、规格、配套文档及必要依赖均已满足；不适用的对象写原因，不补造产物。缺失、未知、失败的证据仍是未完成。
- 本页的适用必要记录同属交付：已走候选却缺挑选 PR/候选完整结果提交，不能先判完成再称「待补但不阻塞」。
- 实现合并只证明实现合并，不证明候选齐全或已部署成功。
- 已采用发布模块的无部署义务文档，所需分支交付（含进入候选）和验收完成后可关单，内容留候选随下次正常版本进快照，不单独造文档热修/tag/部署。
- 仍需部署但本次暂不发的代码不能冒充无部署义务；按实际影响判断，不按 docs 标签或文件后缀豁免。
- 关单前核适用验收与来源/证据真实齐全，只勾已满足项，回填原任务，再放锁。遇缺口补原记录或补交付并验证，不把验收删掉让任务看起来完成。

## 六、观察式例外

「上线后观察 N 天」「等真实用户用后再确认稳定」这类只有「没出事」的条目，默认不写验收、不当关单条件，也不自动开观察单。需要线索可记「不在本单验收」及何时核对；上线后真出问题再开 bug 单并链接。

只有下列三类可在**方案期**请求纳入（D1），批准需写清验什么/异常信号、为什么替代不了、明确截止时间、可判定通过条件：

| 类型 | 适用事实 |
|---|---|
| 真实时间 | 结论本身依赖时间流逝，模拟时间替代不了 |
| 合规要求 | 外部合规/审计明确要求观察或留存期 |
| 必要持续负载测试 | 结论需要长时真实负载，回放或压测不能替代 |

纳入后挡关单，直到有通过或失败结论；到期无结论就报告请用户定，不默认顺延或判通过。实施期新冒出的观察需求走正常可判验收或另开任务，不事后自行补批。三类之外不擅自扩成常驻例外；拿不准不自判。

## 七、#158 三判据

作为发布与关单的验收例子（`#158` 是「线上这版带没带某个改动说不清」的事故）：

1. `git diff --quiet <tag> origin/master` = 0——生产快照与 tag 树一致，可复现。
2. 能回答「线上这版带没带 #N」——从 tag 到 issue 的全部实际来源可追。
3. 出事时有确定动作——回滚目标 tag/快照已列明，只按 D7 由用户批准执行。

三判据都是可核命令或可核记录，不是「应该没问题」。
