# Case: 2026-11-07 审核驱动的范围扩散

- **情况**：taoxi-system PR #977，一场发布流程 spec 审了六轮、累计 60 多条发现。机制数从初稿 9 条涨到 R3 后的 19 条，文档从 1 份 431 行涨到 4 份 + 1 ADR；砍掉整份 S03、部署对齐、批次 0、台账双表后，机制回到 14 条，文档 3 份 366 行。
- **预期**：每条「走不通」都修掉，修完就闭环。
- **实际**：两个引擎同时把范围推大。引擎一：每条洞都当成必修项 → 加规则 → 规则之间又冲突 → 再加规则。引擎二：分不清设计缺陷与同步失误——甲类（闭环外，同步不住）约三分之二，乙类（闭环内，机制固有）约四分之一，丙类（岔路没拍）少数；三分之二的同步失误被升级成设计变更。
- **意外**：纠缠最久的三个阻断（「窗口无落点」「`EXECUTING` 死路」「批次 0 达不到目的」）在砍掉相关部分后自己消失。链一里「回滚找不到上一个 tag」——全仓只有一颗 tag，这条路今天本来就不存在；链三的规则与 `AGENTS.md` 正面冲突，加规则前读一遍就能看见。
- **学到什么**：这次形成的处置是——审核报告加成因与「能不能不修」两列；修订卡加「砍路径 / 写不保证」；甲类只做五问对账，不新增规则；每轮做范围检查（本轮新增规则里有几条是原问题必需）；每批设轮次上限，触发就停；轮次绑 PR、不绑文件。复杂度本身就是障碍，规则越多，两两冲突的组合越多。
- **影响提议**：无。五机制已进 [review playbook](../30-playbooks/review.md)；本案例不构成新增规则或授权的依据。
- **用户是否批准偏离**：是。用户在修订卡上选「砍」，原话「请你为我复述我们要解决的是什么问题，然后应该砍哪些东西」。
- **被哪条规则覆盖 / superseded_by**：覆盖于 `30-playbooks/review.md` #158 五机制；superseded_by：无。
