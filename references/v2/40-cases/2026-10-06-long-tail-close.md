# Case: 2026-10-06 长尾验收把单挂住

- **来源**：v1 rationale R14、R18；`docs/specs/2026-10-06-close-on-release.md`、`2026-10-15-done-criteria-and-longtail-closeout.md`

- **情况**：taoxi-system #588（开放平台客户建档）9-29 写路由已发生产，剩下的验收项都要等某家合作方第一次真实调用；该单先后挂过「受阻」「待上线」，10-06 才改成「待验收」，「下次看」滚到 10-13。另有 #458、#490、#431 等观察期单。仓内 48 张 open 单里当时没有一张「待验证」。
- **预期**：等外部方或观察期的项留在单里，直到确认稳定再关。
- **实际**：功能单一挂几周；「受阻（等外部条件）」和「待验收（等真实事件）」定义重叠，都套得上「等合作方来接」。owner 原话：「凭据不应该作为收阻项，如果这样，那大部分开放平台的 issue 都会受阻，因为开发了不一定马上有人用」。
- **意外**：上线后出的问题本来就该开 bug 单，原单守着没有增加信息；十天后（10-15）又发现，判据住在选修标签备忘录里，未采用仓读不到，采用仓又把它复述成第二份。
- **学到什么**：上线那一刻的判据是一句「这条现在能不能由我们自己动手验」；能验的留下，不能且未批准的转出、不挡关单；只有真实时间、合规要求、必要持续负载测试三类可在方案期批准纳入。什么算完、观察式条目怎么办、例外谁批属于阶段合同与记录，不属于选修标签。
- **影响提议**：无。已进 [labels playbook](../30-playbooks/labels.md) 上线分拣、[15-records](../15-records.md) §六 与 [10-stages](../10-stages.md) 交付段。
- **用户是否批准偏离**：是。owner 拍板「发上线我们的 feat issue 的使命就结束了，后续有 bug 那也是 bug issue 的事情」；判据从选修提进正文。
- **被哪条规则覆盖 / superseded_by**：覆盖于 `30-playbooks/labels.md` 上线分拣、`15-records.md` §六；superseded_by：无。
