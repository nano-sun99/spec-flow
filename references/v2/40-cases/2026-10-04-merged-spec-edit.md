# Case: 2026-10-04 在已合并 spec 上改新需求

- **情况**：jasmine-lottery 全仓只有一份 spec；09-30 建档 448 行，10-04 长到 762 行。`git log --follow` 共 17 个提交改过它，回填首个 Issue 号之后又有 15 个提交，只有 1 个是纯元信息回填，其余 14 个改了正文，其中至少 4 个是实施 PR。
- **预期**：新需求继续在同一份 spec 上同步引用和口径，保持「一份真相」。
- **实际**：2026-10-04 会话里，新需求拍板后 agent 回报「正在写需求文档的修订，同步各处引用『8 位码』和后台外观的地方」，准备直接改旧 spec；用户打断：「我们这是新需求，写新的 spec 和 adr，别老是改以前的 spec，越改越乱」。
- **意外**：「定稿冻结、新需求另起 spec」当时只写在可选的文档生命周期备忘录里，该仓只启用了 ADR，这条对它不生效；第 5 步的「全文同步所有落点」没有限定只在合并前，会话里「同步各处引用」正是照它在做。
- **学到什么**：spec 是获批需求的快照，不是跟着代码更新的活文档。合并并建立实施 issue 之后，这份 spec 成为基线：小修正留在 issue / PR，原文事实写错才加带日期的勘误；新增、取消或改变范围 / 验收含义的，走另起一份 spec 的路径。判据住在选修模块里时，未采用仓读不到，采用仓又会抄成第二份。
- **影响提议**：无。已进 L0-1「改已合并 / 冻结 spec 正文」、D3 条件分支与 [new-spec playbook](../30-playbooks/new-spec.md)。
- **用户是否批准偏离**：是。owner 否掉「拿不准才问」，选客观触发「改已合并 spec 正文就问」。
- **被哪条规则覆盖 / superseded_by**：覆盖于 `20-decisions.md` D3、`30-playbooks/new-spec.md`；superseded_by：无。
