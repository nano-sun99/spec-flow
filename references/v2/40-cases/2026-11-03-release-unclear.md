# Case: 2026-11-03 发布说不清线上是哪一版

- **情况**：taoxi_system 发版时「要发的」和「实际发出去的」对不上，事后说不清线上是哪一版。该仓只有 `master` 一条主线，功能分支 PR 直接合 master，发布从 master 取码；曾手工切 `release/873-875-no-608` 绕开未完成功能。
- **预期**：发版清单与实际部署一致，线上版本可追。
- **实际**：缺少发布线定义、发布记录账本和就绪门槛；`待上线` 只是标签，没有通过的测试结果或验收评论；`待测试` 已合主干，打 tag 必然带上；`docs` / `chore` 与依赖项没有过滤判据；发布后只有标签转换，没有验证结果、失败回滚和 hotfix 回流的固定落点。
- **意外**：用户要的不是更完整的流程，而是三条可核判据——`git diff --quiet <tag> origin/master` = 0；能回答「线上这版带没带 #N」；出事时有确定动作。A 方案（单主线 + 不可变 tag + 合并闸 + hotfix 从 tag 切 + 大功能开关）只作为选修，理由原话是「不是每个项目都那么复杂」。
- **学到什么**：这次形成的形态是：发布记录作为唯一账本；「待上线」带通过证据；主干对齐把可发 / 未就绪 / 非部署 / 搭车分开，未就绪与搭车默认阻塞；失败与 hotfix 回到同一张记录。复杂度是成本，简单项目零负担靠选修化。
- **影响提议**：无。已进 [release playbook](../30-playbooks/release.md)、D6 与 [10-stages](../10-stages.md) 发布段。
- **用户是否批准偏离**：是。owner 拍板 A 方案作为选修备忘录。
- **被哪条规则覆盖 / superseded_by**：覆盖于 `30-playbooks/release.md`、`20-decisions.md` D6；superseded_by：无。
