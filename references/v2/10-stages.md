# v2 阶段合同（L1）

> 本页是「什么算完成」的唯一正文。4 段各写目标、完成（全部为真）、证据、出口、常见失败；段内顺序由 agent 按这一单的情况决定，本页不规定步骤。铁律见 [00-constitution](00-constitution.md)，用户决定见 [20-decisions](20-decisions.md)，记录字段见 [15-records](15-records.md)。
>
> 对外仍是两段：澄清 + 设计 = 方案期，交付 + 发布 = 实施期。4 段是内部分细，只用于判断这一单在哪一段、能不能出段。

## 一、术语（L0-L2 自足）

| 术语 | 定义 |
|---|---|
| 四类 | spec、实现/必要测试、配套文档、必要依赖 |
| 页面 | 只有可交互 GUI 才算；CLI 输出、导出报表、接口响应本身不算。判错只影响是否等用户设计，不影响接口与业务缺口分析 |
| 合入预演 | 把当前 staging 合入 issue 分支（或临时预演分支），在真实 merge 树上构建并跑本 issue 验收；记录预演分支/提交、staging 基线、合并后构建与验收结果。允许 rebase/CI，但必须证明结果树与真实 merge 树一致，否则不算预演绿 |
| 批次测试 | 在当前 staging HEAD 上构建、部署测试环境，跑回归和跨 issue 验收；之后有新合入即失效，打 tag 前重跑 |
| rc 验收 | 从 rc 附注 tag 构建、部署测试环境跑验收；不做 15 分钟监控 |
| 生产监控 | 从最终 tag 构建、部署生产后启动 Monitor 15 分钟；崩溃 HALT，停住上报，不自动回滚 |

## 二、四段合同

### 澄清

- **目标**：把需求变成可判断的范围、验收和约束。
- **完成（全部为真）**
  - 改哪里 / 怎么改 / 带来什么能力或优化，具体到能被否掉。
  - 范围与非目标明确。
  - 验收可判对错：有命令、断言、截图或人工确认入口。
  - 页面 / 无页面、拆 / 不拆、观察式例外（如适用）已由用户定。
  - 承重未知已闭合：数值、接口、范围、权限、数据无悬空。
- **证据**：澄清记录（轮次、每轮问题与用户决定）、需求摘要、验收清单。
- **出口**：用户确认进入设计（D1），或用户选直接干。
- **常见失败**：澄清记录只写结论不写轮次；验收写成「功能正常」；把接口当页面；承重问题留给实施期。

### 设计

- **目标**：把方案变成可执行的 spec / 计划。
- **完成（全部为真）**
  - 方案、备选及代价、验收、依赖、数据库变更清单齐备。
  - 承重规则与已确认做法一致；澄清记录可核（只写结论不算）。
  - 行为有触发、响应及必要的失败/空态处理。
  - 验收能判对错，覆盖正常、异常、边界和必要回归。
  - 数据迁移、回滚、兼容、外部契约影响已写明，或写不适用及事实理由。
  - 已采用 ADR 时当前决定/取代链与正文一致；未采用不新增前置。
  - 审核档位与修订范围已选（D2）；审核与修订已按所选完成。
  - 文档检查已跑（绿 / 红+摘要 / 无入口）。
- **证据**：spec、审核记录、修订记录、文档检查结果。
- **出口**：spec 合并（D3）+ 执行 issue 已建 + 等待明确实施委托（D0）。
- **常见失败**：spec 写步骤不写状态；审核档位从规格期沿用；文档检查在派审卡之后才跑；把「用户没反对」当合并批准。

### 交付

- **目标**：把实现变成可验收的 PR / 分支。
- **完成（按项目形态取适用分支，全部为真）**
  - 有 issue：issue 分支验收通过；四类核对逐项有结果与证据。
  - 无 issue（直接干）：task 分支部署测试环境验收通过。
  - 采用 release/staging：候选按项目分支形态冻结（staging 线 = 整条 issue 已合入 staging 且分支冻结）。
  - 不采用 release：交付验收后本段即完成，不新增分支、tag 或发布义务。
  - 文档改动已跑文档检查。
- **证据**：PR 列表、构建结果、验收证据、四类逐项、worktree/锁记录、文档检查结果。
- **出口**：整条合入 staging（仅 staging 线，D5）/ 任务 PR 合并（D4）/ 无发布义务任务关单。
- **常见失败**：实现 PR 合了就报 issue 完成；四类用「没改就是不需要」填；预演没在真实 merge 树上跑；文档检查只在主仓跑。

### 发布

- **目标**：把候选变成可复现的生产版本。
- **完成（仅采用 release/staging 的项目，全部为真）**
  - 批次测试通过（当前 staging HEAD；打 tag 前重跑）。
  - rc 验收通过（从 rc tag 构建，不做 15 分钟监控）。
  - 生产发布已获用户批准（D6）。
  - 生产监控按项目手册执行并留下结果。
- **证据**：批次记录、rc tag、最终 tag、监控结果、发布记录。
- **出口**：生产验证 + main 快照 + 关单。
- **不适用**：不采用 release/staging 的项目本段跳过——跳过是「不适用」，不是「未完成」，也不因此补 tag 或部署。
- **常见失败**：从 HEAD 构建；rc tag 后不重跑批次测试；监控崩溃后自动回滚；移动或删除生产 tag。

## 三、交付前置条件

- 文件变更在独立 worktree；同一 issue 的分支锁名唯一（如 `issue/<N>`）；撞锁停，不双写同一工作区。分支命名可以自由，但锁键不能自由。
- 直接干无 issue：分支 `task/<slug>`，分支名唯一即锁。
- 批次修复 `fix/<N>-<slug>`；hotfix 从生产 tag 切 `hotfix/<tag>-<slug>`。

**发布安全不变式**（仅采用 release/staging 的项目；违反任一条即是 L0-1 的不可逆动作）：

- 只从不可变 tag 构建，不从任何 HEAD 构建。
- 生产分支的树必须等于最近成功生产 tag 的树；不用 merge / reset / read-tree 覆盖生产快照。
- 生产 tag 不移动、不删除；打错 tag 保留并在发布记录标废弃。
- 不在生产分支 revert 未上线内容；不在共享主仓切分支或做快照；不直改另一个 worktree 已检出的引用。
- 保护分支直推不在普通授权范围内。

## 四、入口与跳过

- 这一单从哪段进：新需求从澄清进；已有获批 spec 的执行单从交付进；直接干从澄清或交付进（跳过设计）。
- 跳过不等于免验收：跳过的段没有完成条件，但所到之段的完成条件照旧；L0-6 的计划说明不因跳过而免。
- 段与段之间没有固定顺序要求；同一段可多次进入（如返修回到设计），完成条件不因重复进入而降低。
