# v2 阶段合同（L1）

> 本页是「什么算完成」的唯一正文。4 段各写目标、完成（全部为真）、证据、出口、常见失败；段内顺序由 agent 按这一单的情况决定，本页不规定步骤。铁律见 [00-constitution](00-constitution.md)，用户决定见 [20-decisions](20-decisions.md)，记录字段见 [15-records](15-records.md)。
>
> 设计来源：v2 设计总纲 §六。术语与发布安全不变式在本页写成运行正文；与设计来源不一致时按 L0-7 报告。唯一例外：v2 设计总纲 §八的「澄清记录」一行已由[获批规格](../../docs/specs/2026-11-20-remove-external-clarification-skills.md)取代，现行字段见 [15-records](15-records.md) 第 2 类。对外仍是两段：澄清 + 设计 = 方案期，交付 + 发布 = 实施期；4 段是内部分细，只用于判断这一单在哪一段、能不能出段。

## 一、术语（L0-L2 自足）

| 术语 | 定义 |
|---|---|
| 四类 | spec、实现/必要测试、配套文档、必要依赖 |
| 页面 | 只有可交互 GUI 才算；CLI 输出、导出报表、接口响应本身不算。判错只影响是否等用户设计，不影响接口与业务缺口分析 |
| 候选 | 三层：候选分支（如 staging）的当前 HEAD；staging 线：staging HEAD；单主线：生产主线 HEAD |
| 合入预演（仅 staging 线） | 把当前 staging 合入 issue 分支（或临时预演分支），在真实 merge 树上构建并跑本 issue 验收；记录预演分支/提交、staging 基线、合并后构建与验收结果。允许 rebase/CI，但必须证明结果树与真实 merge 树一致，否则不算预演绿 |
| 批次测试 | 在当前候选上构建、部署测试环境，跑回归和跨 issue 验收；候选有新合入即失效。最终 tag 的提交必须是最近一次通过的批次测试所基于的候选 HEAD |
| rc 验收 | 从 rc 附注 tag 构建、部署测试环境跑验收；不做 15 分钟监控 |
| 生产监控 | 从最终 tag 构建、部署生产后启动 Monitor 15 分钟（项目手册另有规定的按手册）；崩溃或异常 HALT，停住上报，不自动回滚 |
| 生产分支快照 | 单主线：主线前进到同一提交并打 tag；三层/staging：生产分支的树等于该成功 tag 的树，不 merge / reset / read-tree 覆盖 |
| 搭车项 | 候选里未列入本批、来源未登记的改动 |
| 交接区 | issue 正文的「spec-flow 交接」区或等价字段；无 issue 时由任务 PR 承接 |
| 授权方式 | `issue-direct`：用户点名执行 issue；`same-window-handoff`：agent 交接报告是最后一条 agent 消息且用户开始意图紧接；`takeover`：接管已认领工作，需新用户委托 |
| 审核档位 | 不审 = 0 个 agent（主 agent 按 diff 自查）；轻审 = 1 个；重审 = 2 个（规格符合性 + 对抗）；重审 + 变异 = 重审 + 主 agent 换错判据跑相关测试（文档类无可跑测试则如实报无法变异） |
| 严重度 | 阻断 = 走不通 / 必要证据不可执行 / 同一决定多 owner / 承重选择未定 / 数据安全权限；高 = 导致返工或跨份不一致但可修；中、低不挡合并，留未处理项 |
| 文档检查 | 入口按序发现：项目指令自报且真实存在 → `scripts/check-docs.sh` → `scripts/check-doc-links.sh` → 无入口（自报路径不存在落一档；存在但跑不起来 = 红，不冒充无入口）。三态：绿 / 红+摘要 / 无入口；本次 diff 引入的红须修复，存量红注明数量/摘要与不相关依据 |
| 跨切面需求 | 同一行为在多个入口/调用方/数据范围重复出现，或访问控制按项目自定义维度（如角色、租户、记录范围）分层；权限/入口/调用方/字段/数据范围是常见范围类型 |
| 范围盘点表 | 跨切面需求的逐项范围正文；一行 = 一个可枚举项（入口、菜单、实际写入/保存入口，或角色/租户/记录范围等，项目自定义来源；代码入口作交叉引用）；D1 可先 seed，D2 确认前展开到逐项并冻结；改造范围/分期是它的视图；白名单 / 覆盖矩阵 / 验收清单 / 附录 A.x 也是它的视图（回指规则见 [15-records](15-records.md)） |
| 枚举口径 | 项目自定义的枚举来源（如路由、菜单、实际写入/保存入口、角色/租户/记录范围）与匹配规则；D1 冻结，D2 确认前按它展开并数量对账 |
| 数量对账 | 每个枚举来源的条目数与范围盘点表行数逐项核对；差异逐条写明处置，结果作为 D2 证据 |
| 决定索引 | 采用 ADR 时，spec 中只列 ADR 的 ID、一句话结论、ADR 链接 + 来源 / 状态 / 覆盖（章节 / 验收 / 范围盘点表）；未采用 ADR 时，spec 设决定节，字段相同（ID、一句话结论、来源、状态、覆盖），另含适用范围、重开条件；采用 ADR 的项目里，未写入 ADR 的短期决定另设 spec 决定节（字段同上）；索引 / 决定节不复述 ADR 自身的状态 / 范围 / 重开条件。ADR 与 spec 决定节引用同一个决定 ID，不各编一套；升级 / 取代 / 存量迁移的旧 ID 只作别名；闸口 ID 不属于决定 ID 空间。摘要 / 总纲不是决定正文，只是索引的视图；范围盘点表在「范围枚举」上是唯一正文，在「处置 / 阶段 / 授权 / 例外规则」上只是索引的视图；权威顺序与摘要规则见 [15-records](15-records.md)「摘要、总纲是决定索引的视图」 |
| 冻结/解冻 | D1 冻结范围与枚举口径；D2 确认前冻结展开后的范围盘点表；解冻 = 表新增/改行：D2 确认前重跑数量对账并更新 D2 卡，D2 确认后回 D2，已合并走 D3 新 spec |

## 二、四段合同

### 澄清

- **目标**：把需求变成可判断的范围、验收和约束。
- **完成（全部为真）**
  - 改哪里 / 怎么改 / 带来什么能力或优化，具体到能被否掉。
  - 范围与非目标明确。
  - 验收可判对错：有命令、断言、截图或人工确认入口。
  - 页面 / 无页面、拆 / 不拆、观察式例外（如适用）已由用户定。
  - 承重未知已闭合：数值、接口、范围、权限、数据无悬空。
  - 跨切面需求且开 spec 时，有一张范围盘点表（D1 可先 seed），写清项目自定义的枚举来源与匹配口径、以及数量对账计划（每个来源的取数命令与总数）；D1 seed 允许不完整，但每个枚举来源至少一行真实项；只有组名/来源名的行不算 seed。表是跨切面范围枚举的唯一正文；改造范围 / 分期是它的视图，不另建清单；非跨切面范围仍由 D1 的目标/范围/非目标承接。直接干不建表，按 D1 确认的范围交付并写不适用及事实理由。
  - 入口（直接干 / 开 spec）已判定并报告；用户可按 L0-6 否决。
- **证据**：需求摘要、验收清单、决定及其来源（[15-records](15-records.md) 第 2 类）、范围盘点表 seed 与项目枚举口径（跨切面且开 spec 时）。只有实际追问才记问答；已有答案可直接引用。
- **出口**：用户确认范围（D1），agent 判定直接干或进入设计并报告。
- **常见失败**：找不到范围决定的来源；把未答的推荐项写成用户决定；验收写成「功能正常」；把接口当页面；承重问题留给实施期；跨切面需求只列组级或口头清单，不写项目枚举口径与数量对账计划。

### 设计

- **目标**：把方案变成可执行的 spec / 计划。
- **完成（全部为真）**
  - 方案、备选及代价、验收、依赖、数据库变更清单（如适用）齐备。
  - 承重规则与已确认做法一致；关键决定均可追溯，无未解的承重问题。
  - 行为有触发、响应及必要的失败/空态处理。
  - 验收能判对错，覆盖正常、异常、边界和必要回归。
  - 数据迁移、回滚、兼容、外部契约影响已写明，或写不适用及事实理由。
  - 已采用 ADR 时当前决定/取代链与正文一致；未采用不新增前置。
  - 跨切面需求的范围盘点表已按项目枚举展开到逐项，数量对账完成，并在 D2 确认前冻结；D2 确认、D3 合并的是这张表。冻结不是停止查漏：影响本期已承诺场景的新发现，口径内漏项补表并回对应确认，口径外新增回 D1。视图回指与差异处置按 [15-records](15-records.md)；D2 证据含表行数 / 枚举来源数 / 未处置差异数。
  - 决定只有一个正文（ADR 或 spec 决定节），其他章节只引决定 ID；同一决定在两处出现冲突的结论/范围/条件 = 阻断。摘要 / 总纲含规范性句子或自称最高权威 = 多 owner 阻断（定义见 [15-records](15-records.md)）。
  - 决定索引含编号 / 来源 / 状态 / 覆盖图，且同一决定只有一个活动 ID（跨 ADR 与 spec 引用同一 ID；升级 / 取代 / 迁移别名与闸口 ID 另计）；规范性段落 / 验收行至少回指一个决定 ID（视图行改回指表行 ID）；摘要 / 总纲只作索引，不与索引争 owner。权威顺序按 [15-records](15-records.md)；文档组织对账按 [20-decisions](20-decisions.md) D2 的 owner 对账字段，作为 D2 证据。
  - 承重结论依赖的取值路径已用能判错的业务例子核过；未核部分标明（只核能推翻方案的承重路径，不是所有取值）。
  - 审核档位与修订范围已选（D2）；审核与修订已按所选完成，结论原样贴 PR 评论或对话。
  - 文档检查已跑：本次 diff 引入的红已修复；存量红已注明数量/摘要与不相关依据。
- **证据**：spec、范围盘点表（跨切面时，逐项）、决定索引或决定节（含编号 / 来源 / 状态 / 覆盖图；采用 ADR 时：长期决定索引 + 短期决定节；未采用 ADR 时：spec 决定节）、数量对账结果（来源清单 + 每来源条数 vs 表行数 + 差异处置）、承重取值路径核对记录（业务例子、入口、取值来源、未核项）、审核记录、修订记录、文档检查结果。
- **出口**：spec 合并（D3）+ 执行 issue 已建 + 等待明确实施委托（D0）。
- **常见失败**：spec 写步骤不写状态；审核档位从规格期沿用；文档检查在派审卡之后才跑；把「用户没反对」当合并批准；把逐项展开留到实施期，D3 先批 seed 再补表；同一决定在 spec 和 ADR 各写一份；把「冻结」当停止查漏，或反过来用新发现直接改设计。

### 交付

- **目标**：把实现变成可验收的 PR / 分支。
- **完成（按项目形态取适用分支，全部为真）**
  - 有 issue：issue 分支验收通过；四类逐项满足，或按事实记不适用及原因——缺失 / 未知 / 失败不算完成。
  - 有 issue 且 staging 线：合入预演绿（结果树与真实 merge 树一致）；无未合入的实现 PR。
  - 无 issue（直接干）：按项目实际需要完成可判定验收；有测试环境则部署验收，无则写不适用及事实理由。
  - 开 spec 且有冻结范围盘点表时，实施只交付表内行；表外新增按 L0-6 路由（口径内回 D2/D3，口径外回 D1）。直接干、hotfix、批次修复或非跨切面无可冻结表时，写不适用及事实理由，按已确认范围交付。
  - 采用 release：候选就绪——单主线 = 待合入主线的任务分支；三层 = 待挑入候选分支的任务 PR；staging 线 = 待合入 staging 的 issue 分支；四类已核。
  - 不采用 release：交付验收后本段即完成，不新增分支、tag 或发布义务。
  - 文档改动已跑文档检查（同上三态口径）。
- **证据**：PR 列表、构建结果、验收证据、四类逐项、合入预演结果（staging 线）、worktree/锁记录、文档检查结果、审核结论与修订记录；有冻结范围盘点表时另含表行核对，无表时写不适用及事实理由。
- **出口**：整条合入 staging（仅 staging 线，D5）/ 任务 PR 合并（D4）/ 无发布义务任务关单。
- **常见失败**：实现 PR 合了就报 issue 完成；四类用「没改就是不需要」填；预演没在真实 merge 树上跑；文档检查只在主仓跑。

### 发布

- **目标**：把候选变成可复现的生产版本。
- **完成（仅采用 release 的项目，全部为真）**
  - 批次测试通过（当前候选；最终 tag 前重跑）。
  - rc 验收通过（从 rc tag 构建，不做 15 分钟监控）。
  - 生产发布已获用户批准（D6）。
  - 生产监控正常通过；崩溃或异常按 L0-4 停住上报，不进入完成。
- **证据**：批次记录、rc tag、最终 tag、监控结果、发布记录。
- **出口**：生产验证通过 + 生产分支快照；用户确认后关单（D7/标签规则）。
- **不适用**：不采用 release 的项目本段跳过——跳过是「不适用」，不是「未完成」，也不因此补 tag 或部署。
- **常见失败**：从 HEAD 构建；rc tag 后不重跑批次测试；监控崩溃后自动回滚；移动或删除生产 tag。

## 三、交付前置条件

- **独立 worktree**：文件变更在独立 worktree 完成，不在共享主检出上改；用户当场明确要求直接改 / 不开 worktree 的除外，须记录理由。直接干、批次修复、hotfix 同样适用。
- **分支起点与 PR 目标按项目形态**：staging 线从 `origin/staging` 开 `issue/<N>`，实现 PR 回该 issue 分支；三层从 `origin/<集成>` 开任务分支，PR 回集成分支；单主线从 `origin/<主线>` 开短期分支，PR 回主线。实际映射以项目指令为准；映射不明按 L0-7 问。
- **锁键 = 精确分支名**：`issue/<N>`（无 slug、无前缀），worktree 目录 `issue-<N>`；该分支已被检出 = 有人在做，撞锁停，不双写同一工作区。
- 直接干 `task/<slug>`；批次修复 `fix/<N>-<slug>`（直接干 `fix/<slug>`）；hotfix 从生产 tag 切 `hotfix/<tag>-<slug>`，修复提交打临时 tag、从该 tag 构建，不立即打生产 tag，跟下一班车。
- **发行安全不变式**（仅采用 release 的项目；违反任一条即是 L0-1 的不可逆动作）：
  - 只从不可变 tag 构建，不从任何 HEAD 构建。
  - 三层/staging：生产分支的树必须等于最近成功生产 tag 的树；不用 merge / reset / read-tree 覆盖生产快照。单主线不要求主线树等于旧 tag，只要求 tag 不可变、构建自 tag。
  - 生产 tag 不移动、不删除；打错 tag 保留并在发布记录标废弃。
  - 不在生产分支 revert 未上线内容；不在共享主仓切分支或做快照；不直改另一个 worktree 已检出的引用。
  - 保护分支直推不在普通授权范围内。

## 四、入口与跳过

- 这一单从哪段进：新需求从澄清进；已有获批 spec 的执行单从交付进；直接干从澄清或交付进（跳过设计）；hotfix 从交付段进，修复完成后走 D4 按形态合回主线/集成/staging。
- 入口由 agent 判定并报告，用户可按 L0-6 否决；不把已砍掉的「入口选择卡」装回来。
- 跳过不等于免验收：所到之段的完成条件照旧。L0-6 的「说明改动面」是一句说明。比如已经有符合要求的导出件，本轮只须核对并指出它，改动面为零，可直接交付。核对现有结果不触发计划卡。确有新的工作要执行时，按 [入口的运行循环](SKILL.md#运行循环) 判断计划卡及交互方式。
- 段与段之间没有固定顺序要求；同一段可多次进入（如返修回到设计），完成条件不因重复进入而降低。
