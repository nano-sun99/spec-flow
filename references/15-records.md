# 记录与证据（L1）

> 本页是「交付与授权要留什么」的唯一正文；阶段完成条件只在 [10-stages](10-stages.md)。
> 记录沿用原 issue 交接区，无 issue 由任务 PR 承接；已有字段足够就引用。除 change manifest 外，不新建台账或固定报告文件。全页共 15 类（11 类核心 + 4 类补充）。

## 一、11 类交付 / 授权与决定记录

| # | 信息组 | 必要内容 | 维护责任与时点 |
|---|---|---|---|
| 1 | 获批依据 | spec 路径、获批完整提交、方案 PR；批准修订的适用版本 | 方案作者开单填；实施者开工核版本 |
| 2 | 澄清记录 | 决定及可核来源（用户原话、获批材料、项目事实出处）；有追问才记问答，未答记待定；已有答案只引来源 | 写 spec 时填；直接干由 PR 承接 |
| 3 | 预期交付 | 实现成果 / 模块、必要测试入口、配套文档落点、共享约定 | 从 spec 提取；实施确定位置同步 |
| 4 | 全部实际来源 | 所有相关实现 / 补充 PR 与完整合入提交；文档真实位置（含改名 / 归档） | 每次 PR 合入回填，保留此前来源 |
| 5 | 必要依赖 | 候选 / 发布所需 issue、共享契约、版本、就绪条件与满足证据 | 开单沿用 spec；实施补满足结果 |
| 6 | 就绪证据 | 通过的测试 / 验收结果及链接；是否仍有部署义务 | 实施验证后填；失败或仅命令不算 |
| 7 | 候选结果 | 挑选 PR、候选完整结果提交；四类逐类三态（本次纳入 / 已在核验 / 不适用及原因） | 分拣者核当前候选并合入后回填 |
| 8 | 合入预演 | 仅 staging 线：预演分支 / 提交、staging 基线、合并后构建验收及「结果树 = 真实 merge 树」证明 | 实施者 D5 前填；失败重做 |
| 9 | 四类核对 | spec、实现 / 测试、文档、依赖逐类结果与证据 | 采用 release 时 D5 / D6 前填 |
| 10 | 标签证据 | 当前标签、事实与证据、用户确认记录 | 换标签时记（三确认项须留证） |
| 11 | 授权与决定 | D0 授权（8 字段见 §二）；D1–D7 拍板（对象、原话、时间、范围、结论） | 认领前写授权；硬闸后追加决定 |

**「不适用及原因」语义**：仅描述真实未发生 / 不需要的对象，不可免掉已发生动作的证据；来源在另一原记录时引用其位置，不猜值、不另造账。

## 二、授权与决定记录（只追加不篡改）

### D0 授权（8 字段 + 生效状态）

1. **对象**：执行 issue 编号，或无 issue 直接任务范围。
2. **方式**：`issue-direct` / `same-window-handoff` / `takeover`（定义见 [10-stages](10-stages.md) 与 [20-decisions](20-decisions.md) D0）。
3. **用户原话与可核记录时间**。
4. **本次范围**：相对获批依据的缩小须写明，不借记录扩范围。
5. **同窗口摘录**：摘录交接报告的 Spec / issue / 下一步；定向入口记不适用。
6. **Spec 合并 commit 核对**：固定完整提交与当前应实施版本相符；无规格旧单记不适用。
7. **基线与锁核对**：`git fetch`、`git status`、`git worktree list` / `git branch --list 'issue/<N>'` 摘要及分支映射核对。
8. **生效状态**：生效 / 未生效 / 已撤销及原因。

### D1–D7 拍板

- 记决定 ID（D1–D7）、对象（issue / PR / 批次）、版本或完整提交（审核类另记 `base/head` 完整 SHA）、用户原话与可核时间、本次范围、结论。
- 载体为原 issue 或 PR 评论；评论不代替合并。状态变更用追加新记录写「取代 `<旧记录>`」并给原因，旧正文不改不删；不同时保留两份生效授权。

## 三、4 类补充记录

| 信息组 | 必要内容 | 维护责任与时点 |
|---|---|---|
| 原任务字段 | 流程状态（4 段 + `paused`/`cancelled`/`completed`）、停止点、暂停/恢复原因与受影响范围、工作区/分支/当前提交、未做项、接手条件、交接要点、测试记录（输入/预期/实际/证据/结论/范围） | 暂停、恢复、接管、交接时更新 |
| PR 关联 | 只写「关联 issue：#N」（无 issue 写任务范围）；**不写** `Closes` / `Fixes` / `Resolves` 等自动关单词 | 每次开 PR 时写 |
| 事故记录 | 仓内真实事故记录位置与摘要；无则写「无」 | 首次出现登记；后续迁案例库 |
| 收尾 / 关单 | 验收全勾情况、遗留项、观察式例外、发布记录链接 | 收尾按 §五 填 |

- **交接报告要点**：方案已交付、实施是否获委托、spec 永久链接 / 完整版本、执行 issue、范围、批次安排、未做与限制、下一步由谁做。
- **审核 / 发布载体**：审核结论与修订处置贴 PR 评论（无 PR 贴对话），spec 末尾可追加审核修订记录；批次与发布记录由项目现有发布记录承接，直接干任务手工列入（分支、PR、commit、验收证据）。

## 四、文档载体、读序与替换处置

### 1. 四种载体与读序

| 载体 | 回答什么 | 更新口径 |
|---|---|---|
| 现状文档（含运维） | 系统现在是什么、怎么操作 | 事实变化时改唯一 owner，他处只链接 |
| spec | 本次批准了什么需求与验收 | 批准前可修订；合并且开执行单后冻结，默认只加状态、勘误与链接（改旧须 D3 确认） |
| ADR（若采用） | 跨任务长期决定与原因 | 变化时新 ADR 取代旧 ADR，不静默改旧正文 |
| issue / PR | 实施做到哪、改了什么、证据在哪 | 随实施持续更新 |

- **读序**：先核现状文档与生效 ADR（若采用）；实施前必读当前获批 spec 与验收；历史 spec / 调研 / 复盘按需读。历史记录头部标「历史快照（日期）：现状见 X」，与实测冲突时以现状和实测为准，承重冲突交用户（L0-7）。
- **基线后修正**：不改获批范围与验收含义的小修记 issue/PR 并链 spec；**勘误只限原文事实写错且误导读者**，加带日期勘误链接；改变范围或验收含义一律新开 spec 走 D3。
- **规格内部治理**：同一决定单 owner、唯一活动 ID、范围盘点表、摘要 / 视图回指与权威顺序见 [25-spec-governance](25-spec-governance.md)。

### 2. 替换式变更载体处置表（唯一正文）

| 载体 | 处置 | 证据 |
|---|---|---|
| 未合并、未冻结草案 / 现行文档 | 原位删或替换旧句；同一决定只留一个正文 | diff + manifest 规则行 |
| 已合并 / 冻结 spec 正文 | 默认不改；用户明确确认「改旧的」按 D3 执行；事实错走勘误；范围 / 验收变化走新 spec | 勘误链接或 D3 记录 |
| 拍板 / 授权 / 审核 / 修订记录 | 只追加不篡改；新记录写「取代 `<旧记录>`」 | 追加记录链接 |
| 历史记录 / 案例 / 旧规格 | 保留；头部标「历史快照（日期）：现状见 X」并互链 | 标记 + 链接 |
| 迁移别名 / 旧 ID | 只留「原 `<旧>` → `<新>`」迁移行或别名字段，不作现行引用 | 迁移行链接 |
| 外部契约 / 已发布 API | 不静默删旧名；加兼容层或废弃公告并标「已废弃」 | 契约 / 公告链接 |

## 五、关单收尾

**关单 = [10-stages](10-stages.md) 交付段完成条件已满足 + 下列核对完成**（缺失 / 未知 / 失败不算完成）：

- 以获批范围和预期交付核真实产物与全部来源，不看实现合并、单次 diff、标签或一句 PASS。
- 必要记录同属交付：已进候选却缺挑选 PR 或结果提交，须补原记录再关单。
- 采用 `release` 的无部署义务文档，完成所需分支交付（含进候选）与验收即可关单，随下次正常版本进快照，不另造热修 / tag；仍需部署的代码不得借 docs 标签豁免。
- 关单前只勾已满足验收项，回填原任务再放锁；缺口补交付或补原记录，不删验收项凑完成。

## 六、观察式例外

「上线后观察 N 天」类仅靠「没出事」判定的条目，默认不写验收、不当关单条件、不自动开观察单；需要线索记「不在本单验收」及核对时机，真出事另开 bug 单。

仅以下三类可在**方案期**申请纳入（D1），批准须写明验什么 / 异常信号、不可替代原因、截止时间与可判通过条件：

| 类型 | 适用事实 |
|---|---|
| 真实时间 | 结论本身依赖时间流逝，模拟时间不可替代 |
| 合规要求 | 外部合规 / 审计明确要求观察或留存期 |
| 必要持续负载测试 | 需长时真实负载，回放 / 压测不可替代 |

纳入后挡关单，到期无结论交用户定（不默认顺延或判通过）；不免掉当前可判定的生产验证或已承诺部署。实施期新冒出的观察需求不事后补批。

## 七、#158 三判据（发布与关单验收例）

1. `git fetch` 后 `git diff --quiet <tag> <生产分支>` = 0（三层 / staging 源码树与 tag 一致）。
2. 能回答「线上这版带没带 `#N`」：从 tag 到 issue 全部来源可追；直接干手工列入发布记录。
3. 出事有确定动作：回滚目标 tag / 快照已列明，只按 D7 执行。
