# 闸的细则（派审核、跑文档检查、确认及执行合并前读）

> 本文件是主文件闸的执行细则；派审核、跑文档检查、确认及执行合并前必须读。不可见或版本已变时动作前重读，不新增档位（依据：rationale R25）。

## 一、审核怎么执行（任一档）

- 只读审、不许改文件——审核产出是发现清单，不是改好的文件
- 要求逐条核对 spec 里的每个 `file:line` 引用和「现状是 X」断言——实测这样能抓出作者自己没发现的事实错误（依据：rationale R4）
- 给 subagent 足够上下文：当前获批 spec、代码工作区、实际 diff 基准、已实测且无需复核的数据；主 agent 准备相关项目 / 域入口、已采用规则、现行 ADR 链接与本次沿用 / 新增 / 取代 / 无及原因的证据（旧任务放当前 PR / issue，不回写冻结正文）。未选审核自己核，不借此增派（依据：rationale R25）。
- 已采用约束按路线核：规格符合性（含 spec 期轻审）核当前目标、现行 ADR、两张清单和既有文档分工；实施对抗检查找具体违反获批约束的行为。发现 spec 绕过现行 ADR，报告冲突和来源，不替用户裁业务或自动改决定。范围外对账仍只报越界，不扩为质量意见或要求新防御层。
- **审核档位不跨阶段继承**：方案期选过的档位不自动沿用到实施期；每份实施交付物合并前重新由用户点。交接机制见 `references/phase-handoff.md`，不新增审核档位。
- 轻审只有 1 个 agent，**定位按阶段劈**：spec 期审的是文档，严重发现压倒性是事实/符合类；实施期审的是代码，压倒性是对抗类（依据：rationale R3）。重审两路俱全不用劈；摆卡时按当前阶段直接写对应定位。
- spec 期审核对应加一条核对项：**两张清单都在**——机制清单在 spec 里、自定细节节在末尾（它后面只剩「审核修订记录」不算违规；缺任一 = 违规）；再逐条对，spec 里的机制 ↔ 机制清单对不上、清单外有机制 = 漏报。
- 审完先由主 agent 把审核结论（含变异结果）原样贴成 PR 评论（无 PR 可走的贴对话），再用一张修订卡问用户「改 / 不改」：不许自动改，没答或选不改不合并；零发现只贴评论、不摆修订卡，「不审」档免的是审核产物；两者都不免合并卡；处置记进 spec 末尾「审核修订记录」表格（# / 严重度 / 发现 / 处置）——转述会弱化不利发现（依据：rationale R11）
- 范围外对账**只报「spec 改动面之外的变更」**，不扩展成质量意见——审核 prompt 写狠了会反向逼实施方加防御层（依据：rationale R5）
- spec 期及开执行单前核对**体量评估与结构选择**：草案成形后已给实际拆法、推荐理由和拆 / 不拆选项；多阶段已提醒，子件仍多阶段也有用户选择；普通编码 / 测试 / PR 步骤与三项就绪不误判。决定未过期，未答不新开执行单；不以必须并行代替尽可能并行，也不自动退为单 spec 下的多张阶段单（依据：rationale R28）。
- **本次交付物含多份子 spec 时，核拆分依赖清单**——地图每份都有产出 / 消费 / 独占 / 不碰 / 开始、合入、发布三项就绪；台账每条边有方向、类型、产物、就绪条件、验收证据、owner、波次。允许明确的先后依赖，硬前置不伪装可并行、软协调不伪装阻塞；未解的实施循环或归属 / 前提不清先修拆法，同批合入 / 发布已指定批次 / 收尾份并登记。子件上下游声明与台账相符，共享约定一个 owner、本份测试与跨份验收有归属。稳定组标识、子件编号、文件 / spec / issue 对得上；总纲与父单不重复派执行任务，父子归属不冒充阻塞，仅部分产物或发布相关不误挡整个开发。原生关系未建如实报告。细则见 `references/split-large-spec.md`，**不新增审核档位、agent 数或派发路线**（依据：rationale R15、R28）。

## 二、文档检查

- **文档检查入闸**：交付物含文档改动（口径见下）时，摆闸卡前先在交付物自己的工作区跑目标仓的文档检查入口，把结果写进闸卡——固定一行「文档检查：绿 / 红+摘要 / 无入口」；无论用户点哪档（含「不审」）都先跑再摆卡。
- 触发口径：交付物本身是 spec / 交付型文档（纯文档 PR）→ 必跑；代码 PR 的 diff 含文档文件改动 → 也跑（宽口径）；免过闸的机械文档变更 → 免跑（免过闸者优先——免过闸者本无闸卡，检查挂在「摆闸卡前」，自然不沾）。归边不明照旧——闸卡附带一问摆给用户，**检查先照跑**。
- 入口发现（约定优于配置）：① 目标仓指令文件（AGENTS.md / CLAUDE.md）里自报的文档检查入口（**须指向真实存在的路径**；自报路径不存在 = 该档失效，落到下一档）→ ② 约定路径按序取第一个存在的：`scripts/check-docs.sh`、`scripts/check-doc-links.sh` → ③ 都没有：闸卡该行写「该仓无文档检查入口」，不算红。
- 红的行为：红按归因分两类——本次交付物 diff 引入的红 → 修完重跑转绿后重摆闸卡再合并；仓内既有存量红（与本次改动面无关）→ 摘要行标注「存量红 N 处，与本次改动面无关」，**不阻本次合并**，同卡报给用户处置。脚本存在但无法执行 / 跑崩溃也算红（原因写进摘要行——存在但跑不起来 = 检查能力坏了，标「无入口」是把坏装成没有）；用户可在闸卡上当场明示豁免一次，豁免理由写进卡。文档检查红转绿、存量红标注或当场豁免都不等于合并授权。

## 三、一卡盖批

- **一卡盖批须声明**：一次出 N 份实施 PR，允许一张卡盖本批，但卡上必须写明「共 N 份 × 该档 = 约 X 个 agent / Y 分钟」（X 按档位表逐份算：不审 0 / 轻审 1 / 重审 2），并列明批次成员（PR / 分支清单）；未声明份数的，每份各过一道；批卡时每个触发文档检查的成员各在自己的工作区跑一次，结果行逐成员列出（如「A 绿 / B 红+摘要」）。

只限实施期同批 PR；spec 期多份子 spec 照常按份数叠加。审核批卡只管审核，不授权合并；每份 PR 仍单独摆合并卡。

## 四、合并确认

- **覆盖所有 PR**：合入任何目标分支都须单独摆合并卡，纯 spec、普通文档、配置、资源、机械回填同样适用；删除「只含 spec / 文档的 PR」长期豁免，不新增批量合并卡。免方案期、免 worktree、免审核都不免合并确认。没有 PR 可走的平台回填与无 PR 交付不新造 PR 或合并动作，照既有收尾规则处理。
- **三种回答分别授权**：审核卡只定是否审、哪档；修订卡只定按发现改不改；合并卡只授权当前列明的 PR、目标与最终改动。不审、零发现、检查绿、需求可以、同意修改、已修完都不构成合并同意；审核 agent 的「可以合并」也不是用户授权。
- **顺序与停止**：审核或自查完成 → 发现按用户决定修订并验证 → 单独摆合并卡 → 用户明确选择合并 → 执行。审核有发现且用户选不改：不自动修改、不合并，不把合并卡当作绕过待决修订的出口。合并卡未答、被关闭、选先不合，或用户暂停、撤销、要求重审：停止合并，保留当前 PR，不催答，不把沉默当同意。
- **同意失效**：新增实质内容、换目标、返修、暂停、撤销、重审都会令旧同意失效；重新满足审核、修订及验证条件后，对最终版本重新摆卡。任何尚未满足的既有阻断条件不会因用户选择合并而自动消失；出现冲突时报告。
- **卡上对象与最终状态**：至少列出 PR 链接或编号、目标分支、最终改动摘要、验证结果与已知未处理项；用当前提交标识定位版本，不新增授权数据库或固定报告文件。执行前重新核对实际目标、版本与改动；版本变化而尚未核清差异时先停下，不能凭旧卡执行。
- **禁止绕行**：取得明确同意前，不得立即合并、提前启用自动合并、加入稍后自动合入的队列，或直推目标分支。批准本份合并后，仍遵守既有 Git 危险操作、分支保护、验证与收尾规则。
- **审核批卡不授权合并**：一卡盖批只覆盖审核成本，某份的合并同意不扩展到同批下一份。

依据：rationale R30。
