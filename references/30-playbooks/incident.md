# Playbook: 生产应急（热修 hotfix / 回滚 rollback）

> **适用条件**：仅对已采用 `release` 的项目生效；本页为参考走法，硬闸与安全不变式以 L0–L2 及 [release playbook](release.md#一发布安全不变式) 为准。

## 一、热修（hotfix）

**适用**：生产确认缺陷且已有至少一个真实生产 tag，需从生产基线切最小修复。

1. **确认基线**：从最近真实生产 tag 切 `hotfix/<tag>-<slug>`（独立 worktree），**不从 staging / 集成 / 生产分支 HEAD 切**。
2. **最小修复**：只修这一缺陷，不夹带候选下一批改动。
3. **临时 tag 与验证**：在修复提交打临时 tag（如 `v2026.11.03-hotfix.1`），只从该 tag 构建并在可用环境验证，证据贴原发布记录。
4. **D4 合回**：按项目形态走 D4 合回主线 / 集成 / staging；卡上列生产 tag、修复提交、临时 tag 与验证证据。
5. **跟下一班车发版**：修完不立即打生产 tag，跟下一班车走 rc / 批次 / D6；三层在 hotfix tag 验过后补同口径成功快照再 merge 回集成与候选，不用 cherry-pick 断 tag 祖先链。
6. **回填**：继续更新原发布记录并标明已上线 / 排除，避免下轮重复纳入。

## 二、回滚（rollback）

**适用**：生产出现崩溃、监控异常或验收失败，考虑恢复至上一个可用版本。

1. **停住上报（L0-4）**：立即停止受影响动作并报告事实；**不自动回滚、不静默重试、不把失败改写成通过**。
2. **收集证据与核目标**：汇总监控 / 日志 / 验收失败原文与影响范围；核目标 tag / 快照真实存在且树与拟恢复状态一致（首次发布无上一 tag 时核部署前快照或项目原恢复方案）。
3. **D7 回滚确认**：按 [20-decisions](../20-decisions.md) D7 摆卡，用户明确选「回滚」后才执行（默认不回滚）。
4. **执行与验证**：从获批上一生产 tag 或可用产物重新部署，并验证实际部署端身份与健康；不删除或移动失败 tag，不推进成功快照。
5. **记录与收口**：将回滚结果、失败原因与目标写进原发布记录（保持 open 直到收口）；根因另开 bug 单或走 §一 hotfix。

## 三、常见坑

- 监控崩溃后自动回滚掩盖现场；或删除 / 移动失败 tag 导致事后无法复现。
- 全仓只有一颗 tag 时虚构「回滚到上一 tag」，或从失败目标 tag 反推基线。
- 首次发布前尚无生产 tag 就开 hotfix；或 hotfix 顺手夹带其他需求直接打生产 tag 跳过 D6。
- 三层热修用 cherry-pick 回灌导致 tag 祖先链断裂。
