# Playbook: ADR（决策记录，选修）

> **适用**：默认关闭，不因项目复杂自动启用；仅项目已声明采用或用户本次明确要求时执行。

## 一、三种使用状态

| 状态 | 判定 | 行为 |
|---|---|---|
| 未启用（默认） | 用户未提且项目未声明 | 不建 ADR、不加前置 / 字段 / 检查、不追问是否启用 |
| 本次一次性 | 项目未采用，用户说「这次写一条 ADR」 | 仅写本次记录并从 spec 链接，不升格为项目制度 |
| 项目级采用 | 用户要求启用或项目规则已声明 | 复用项目已有规则页、目录、命名与字段 |

## 二、参考走法

1. **开工检索并遵守**：开工前按业务词 / 表名 / 接口 / 组件 / ID 搜现行 ADR 及取代链（未命中记检索词与结论）。现行 ADR 与 spec 冲突时 ADR 为正文——未合并 spec 原位替换，已合并走 D3 新开；若 ADR 自身需变或无法唯一推导停交用户（L0-7）。
2. **何时写入**：须先有用户明确拍板（「倾向 / 先试试」先发选项卡确认），且命中任一长期影响：① 影响其他 issue / spec / worktree；② 改对外接口、数据范围 / 结构、组件边界、安全、部署或长期约束；③ 明确否决未来易再提的合理方案；④ 取代 / 改已有 ADR。
   - **不写**：可实测事实、局部实现、命名、普通重构、进度、临时排障、未拍板候选。
3. **最小格式与取代链**：决定、依据、否决方案、接受代价、重开条件；稳定 ID（默认 `ADR-YYYYMMDD-<slug>`）、状态（`生效中`/`已被取代`）、范围、取代关系。取代时新建 ADR 互链，**旧 ADR 正文不改只改状态与链接**，两端同提交；历史 spec / 已完成 issue 不回写。
4. **索引、收尾与中途升格**：spec 决定索引共用活动 ID（[25-spec-governance](../25-spec-governance.md) §一），分清沿用 / 新增 / 取代 / 无及理由；issue 只链 spec；收尾核现行与取代一致。
   - 审核中途新增 / 取代 ADR 按 §五 先过 L0-6 + #158 原位升格组件 2（留迁移别名）；仅取代 PR `base` 旧 ADR 或改既有规则时当轮切入组件 3 manifest `--draft`，**纯新增 ADR 不触发 manifest**。

## 三、常见坑与指针

- **坑**：拿复杂或旧文件当已启用；把局部实现写进 ADR 或改已取代正文；一次性写入顺手改项目制度。
- **指针**：[25-spec-governance](../25-spec-governance.md) §一 / §五、[15-records](../15-records.md) §四、[10-stages](../10-stages.md) 设计段、[50-adapters](../50-adapters/README.md) §三。
