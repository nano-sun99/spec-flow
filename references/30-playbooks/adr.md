# Playbook: ADR（决策记录，选修）

> **适用条件**：默认关闭，不因项目复杂自动启用；仅在项目已声明采用或用户本次明确要求时执行。

## 一、三种使用状态

| 状态 | 判定 | agent 行为 |
|---|---|---|
| 未启用（默认） | 用户未提且项目规则未声明 | 不建 ADR、不加前置 / 字段 / 检查、不反复追问是否启用 |
| 本次一次性 | 项目未采用，用户明确说「这次写一条 ADR」 | 只写本次记录并从当前 spec 链接，不升格为项目制度 |
| 项目级采用 | 用户明确要求项目启用或项目规则已声明 | 复用项目已有规则页、目录、命名、状态与语义字段 |

## 二、参考走法

1. **开工先检索**：需求调查、旧 issue 或免方案期首次实施前，按业务词、表名、接口名、组件名与已知 ID 搜现行 ADR，读命中记录及取代链；未命中记检索词与结论，不把「没搜到」说成历史无决定。
2. **命中即遵守**：同一决定上现行 ADR 与 spec 不一致时，ADR 是正文——未合并 spec 按现行 ADR 替换条款，已合并 spec 走 D3 新 spec；若 ADR 本身需变或无法唯一推导，停下报告交用户（L0-7）。
3. **何时写入**：须先有用户明确拍板（「倾向 / 先试试」先用选择卡确认），且命中任一长期影响条件：
   - 影响其他 issue、spec 或 worktree；
   - 改变对外接口、数据范围 / 结构、组件边界、安全、部署或长期运行约束；
   - 明确否决未来很可能再被提出的合理方案；
   - 取代或改变已有 ADR。
4. **不写进 ADR 的**：可实测客观事实、局部实现、命名、普通重构、进度、临时排障、未拍板候选。
5. **最小格式与取代链**：决定、依据、否决方案、接受代价、重开条件；稳定 ID（默认 `ADR-YYYYMMDD-<slug>`，避免并行抢号）、状态（`生效中` / `已被取代`）、适用范围、取代关系。取代时新建 ADR 并互链，**旧 ADR 正文不改、只改状态与链接**，两端同一变更；历史 spec / 已完成 issue 不回写。
6. **spec 只链不抄与收尾**：spec 决定索引引用同一活动 ID（规则见 [25-spec-governance](../25-spec-governance.md) §一），分清沿用 / 新增 / 取代 / 无及原因；issue 默认只链 spec（一跳达 ADR）。收尾核引用现行、取代两端一致与已拍板长期决定已落地。
7. **审核中途升格与 manifest 边界**：审核修订中首次确认新增或取代 ADR 时，按 [25-spec-governance](../25-spec-governance.md) §五 先过 L0-6 + #158 并原位升格组件 2（不重编底座 ID，留迁移别名）；仅取代 PR `base` 旧 ADR 或修改 PR `base` 既有规则 / 判据 / owner 时须在当轮修订切入组件 3 manifest `--draft`，纯新增 ADR 不触发 manifest。

## 三、常见坑

- 把「项目复杂」或「目录里曾有旧文件」当成已启用 ADR 的授权。
- 把所有局部实现选择都写进 ADR，或静默篡改已取代 ADR 正文。
- 用户只说「这次写一条」，结果顺手改了项目指令和模板。
