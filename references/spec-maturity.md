# 一份 spec 的三个阶段（方案期）

> 本文件展开 `SKILL.md` 段一第 2–4 步。三个阶段是同一份 spec 的成熟度，不是三份文档，也不是三个实施阶段：同一个文件、同一个 PR，只有实施版过闸、可合并（依据：rationale R34）。

## 一、先判页面

- 判据只看一件：用户 / 操作者是否需要看见或点击**可交互 GUI 页面**。CLI 的 stdout、导出报表、接口响应不算页面，走无页面路径。
- 判不了才摆**页面卡**：`出设计稿` / `不出，用样例`，推荐前者。页面卡只定「要不要出设计稿」，不代替机制卡、拆分卡、改旧 spec 卡。
- **页面卡没答：停住，等用户选**，不按任何默认往下走。这仍是「没答不加码」，只是不加码表现为停住，而不是替你选另一项。
- **「复杂」**（无页面时可选 Draft PR 的判据）：跨模块、多状态、多方合同、数据迁移，任一项成立即算。

## 二、骨架版

同一份 spec 的第一段，一页。**骨架版 = 路的第一屏**：先写 `起点：…`、`终点：…` 各一句，再放主路表（步｜触发 → 响应｜失败 / 空态｜落点 · 依据 · 证据）；写法与方案页见 `references/one-path.md`〈一〉〈二〉。方案页的四个选择（页面 / 机制 / 例外 / 改旧 spec）各自独立点，再加 3 句：起点对不对 / 岔路选哪个 / 终点是不是你要的。

| 路径 | 写什么 |
|---|---|
| 有页面 | 角色、状态、触发、主路径、异常路径、未定清单 |
| 无页面 | 调用方、输入、输出、状态 / 数据对象、异常路径、未定清单 |

- 未定项列在文末，每项写「谁拍 / 截止 / 不决定的后果」；不散在聊天里。
- **有页面**：用户确认骨架后，由 agent 开 Draft PR，写设计需求（页面、状态、宽度、要回答的问题），并把用户确认的原话 / 时间写进 PR 描述；设计到位前不合并。
- **无页面**：不强制 Draft PR；复杂时可用同一 PR 保管骨架和样例。另用 3 个真实例子或 1 张决策表把规则说清（定义见 §三）；一次性脚本可压成一段话 + 一次真实运行。
- **两张清单**（机制清单 / 自定细节）：骨架版 / 对照版至少留占位和未定项，最晚在实施版齐备。
- **设计稿一直不来**：等待期届满、用户问进度、或设计链接长期无更新时，再摆页面卡（等待分支：继续等 / 转样例 / 关闭），不新增卡型；转样例按无页面路径走。

## 三、对照版

设计稿 / 样例 = 路的**可视 / 可执行靶子**：把主路每一步的触发、响应、失败填实，让「走不走得通」能被看见或跑出来。

固定表头，2A / 2B 共用主路四列：**步 | 触发 → 响应 | 失败 / 空态 | 落点 · 依据 · 证据**。旧四列（流程节点 / 界面或样例 / 数据或接口 / 验收）不再单独存在，界面 / 数据 / 验收折进这四列。

### 2A 有页面

设计稿到位后，在同一 Draft PR 里补：

- 设计稿链接与版本；
- 按主路四列填对照；
- 设计未覆盖的节点、流程未落地的界面、数据缺口；
- 待拍板项与「本期不做」。

对照不是设计评审会；是把空格变成决定或明确的非目标。

### 2B 无页面

用最便宜的「能判对错」的样例代替设计稿：

| 类型 | 用什么当设计稿 | 必须回答 |
|---|---|---|
| 单出脚本 | 一次真实运行的命令 + stdout / 退出码 + 一次失败样例 | 输入输出、失败怎么办、重跑会怎样 |
| 后端架构 | 时序图 + 请求 / 响应样例 + 状态转移表 + 一条端到端薄切片 | 谁调用、数据从哪来到哪去、哪步会失败 |
| 数据 / 报表 | 一张带真实数字的样例表 + 边界口径 | 指标口径、边界值、异常数据 |
| 集成 | 请求 / 响应样例 + 失败矩阵 | 双方契约、重试 / 降级、版本兼容 |

- **3 个真实例子**：正常输入输出、边界 / 异常、失败或重跑（二选一，在骨架的未定清单里注明选了哪个）；**1 张决策表**：条件组合表。二选一，写进骨架的未定清单旁边。
- 同样按主路四列填对照；样例回答不了上面三问，不算合格。

## 四、实施版与 DoR

- 把对照结果写回正文，删掉所有「待定」；补规则、数据 / 接口、验收、迁移 / 回填 / 回滚、兼容、观测。
- **机制清单 + 自定细节**在实施版齐备；缺任一，不算实施版。
- **决策依据**：项目已采用 ADR 的链接 ADR；未采用的写「不适用」，不引入新制度。
- **过 DoR 且用户点头后**：有 Draft PR 的 Draft 转 Ready（不另开正式 PR）；无 Draft PR 的，实施版完成后开普通 PR（非 Draft）；然后摆闸卡。骨架版 / 对照版不过闸、不合并。

**DoR 七条**（第 1–4 条不得写「不适用」；第 5–7 条可写「不适用」并说明原因，由审核者接受）：

1. 承重规则只有一个结论，没有 TBD。
2. 每一步有触发 → 响应与失败 / 空态，或明确「无界面」。
3. 每条写路径单一入口；每个状态有字段、有读侧。
4. 每条验收可执行（命令 / 截图 / 断言）。
5. 数据迁移、回填、回滚、兼容都写了。
6. 外部合同（报表 / 开放平台 / 消息通道等）影响与版本写了；无则「不适用」。
7. 项目已采用 ADR 的，supersede 链清楚且正文同步；未采用写「不适用」。

## 五、Draft PR 与合并

- 有页面：用户确认骨架后开 Draft PR；设计到位前不合并。
- 无页面：不强制 Draft PR；复杂时可开，用于保管骨架和样例。
- 设计稿 / 样例到位后，在同一 PR 里补对照和实施版；不另开设计 PR、修订 PR。
- **Draft 转 Ready** 只在实施版过 DoR 且用户点头后发生，不是另开一个 PR。无 Draft PR 的无页面路径，实施版完成后开普通 PR（非 Draft）。
- **同一 PR**：有 Draft PR 时指骨架时开的那张；无 Draft PR 时指实施版开的普通 PR。
- 只有实施版才摆闸卡；合并卡、审核档位、修订卡照旧。Draft PR 不是批准，设计稿不是验收。

## 六、时点与既有规则

- **状态机**：骨架版 / 对照版仍在 `DESIGNING`；只有实施版过 DoR 且用户点头才进 `SPEC_REVIEW`，再摆闸卡。
- **拆分**：拆分卡在骨架版成形后摆一次，不在方案页提前定；三阶段不是「多阶段实施」，范围 / 结构没实质变化就不重复摆。
- **既有卡**：机制卡、拆分卡、改旧 spec 卡照旧；三阶段不触发改旧 spec 卡。
- **豁免**：改一行、纯查事实、用户说「直接干」按主文件豁免，不套。

## 七、边界

- 不要求每个需求都出设计稿；页面卡选「不出」时用样例。
- 不强制 ADR；不新增步骤编号（段一 1–6、段二 7–9 不动）。
- 设计稿 / 样例是同一份 spec 的输入或章节，不是独立文档。
- 只有实施版过闸、可合并。
