# 一份 spec 的三个阶段（方案期）

> 本文件展开 `SKILL.md` 段一第 2–4 步。草稿（骨架）、对照与终稿（实施版）是同一份 spec 的成熟度，不是三份文档或实施阶段：同一个文件、同一个 PR，只有终稿过闸、可合并。V2 方案确认与页面选择在草稿之前（依据：rationale R34、R36）。

## 一、方案 Yes 后由用户选页面

- 新需求先选入口；选择开 spec 后由 grill-me 辅助澄清、spec-flow 汇总同一份方案，详见 `references/one-path.md`〈二〉。首次方案 Yes 前不写 spec；No 按反馈继续同一循环，不另问固定三句。
- **方案 Yes 后立即摆页面卡**：`有页面` / `无页面`。agent 解释并推荐，最终由用户选，不因自己能判就跳卡。
- 判据只看用户 / 操作者是否需要看见或点击**可交互 GUI 页面**；CLI stdout、导出报表、接口响应不算页面。
- **页面卡没答停住**，不代选、不写草稿。页面选择不包含拆分、送审、合并或实施授权；例外、改旧 spec 按各自触发条件处理。
- 无页面的复杂需求可用 Draft PR 保管草稿：跨模块、多状态、多方合同、数据迁移，任一成立即算；不是额外审批。

## 二、骨架版

草稿是同一份 spec 的第一段：承接已确认的目标、范围与可执行验收；用 `起点：…`、`终点：…` 与主路表（步｜触发 → 响应｜失败 / 空态｜落点 · 依据 · 证据）呈现路的第一屏。它们是写作格式，不另构成起点 / 岔路 / 终点确认闸口。写法见 `references/one-path.md`〈一〉〈二〉。

| 路径 | 写什么 |
|---|---|
| 有页面 | 目标、验收、范围、设计需求及待设计验证的角色 / 状态 / 交互；不猜完整页面或接口契约 |
| 无页面 | 目标、验收、调用方、输入 / 输出、状态 / 数据对象、规则样例及异常路径 |

- 未定项列在文末，每项写「谁拍 / 截止 / 不决定的后果」；不散在聊天里。
- **有页面**：草稿形成后开同一 Draft PR，写设计需求（页面、状态、宽度、要回答的问题），PR 正文记录入口与有效方案确认原话 / 时间；不额外重问骨架。单独摆拆分卡，选定结构后暂停，等用户自行完善并提供设计。未拿到设计不继续猜终稿、不代画、不自动转无页面。
- **无页面**：草稿配规则样例，形成后单独选拆分，再完善终稿；不进入设计等待。不强制 Draft PR，复杂时可用同一 PR 保管；用 3 个真实例子或 1 张决策表说清规则（§三），一次性脚本仍须有可判对错的成功及失败 / 重跑证据。
- **方案说明 / 自定细节**：同一份已确认方案承接原机制清单，不另造汇总或机制卡；草稿 / 对照允许标未定，终稿必须齐备。
- 两路拆分互斥，各只在所选分支的草稿后摆一次；未选不进入终稿或设计等待。结构未变不重问；用户明确改变目标 / 范围 / 能力才回同一方案确认循环，仍有效的设计不要求重交。

## 三、对照版

设计稿 / 样例 = 路的**可视 / 可执行靶子**：把主路每一步的触发、响应、失败填实，让「走不走得通」能被看见或跑出来。

固定表头，2A / 2B 共用主路四列：**步 | 触发 → 响应 | 失败 / 空态 | 落点 · 依据 · 证据**。旧四列（流程节点 / 界面或样例 / 数据或接口 / 验收）不再单独存在，界面 / 数据 / 验收折进这四列。

### 2A 有页面

用户提供设计后，agent 借助 grill-me 对照已确认目标和验收，在同一 Draft PR / spec 里补：

- 设计链接与版本；逐页梳理交互、状态、数据、异常和权限，按主路四列填对照。
- 每项页面行为所需接口是复用、修改还是新增；写清请求、响应、错误、读写关系及权限，不只罗列接口名。
- 设计未覆盖的节点、流程未落地的界面、数据缺口与待决定接口口径交用户补齐 / 决定，不猜；明确「本期不做」。
- 结果直接写回同一份终稿，不另造澄清文档。实质方案变化回同一 CONFIRM；只补齐既定决定不重问，仍适用的设计继续复用。

至少用一条真实页面行为把请求 → 响应 / 错误及权限走通。对照不是设计评审会，是把空格变成决定或明确非目标；设计前不能声称已完成接口分析。

### 2B 无页面

用最便宜的「能判对错」的样例代替设计稿：

| 类型 | 用什么当设计稿 | 必须回答 |
|---|---|---|
| 单出脚本 | 一次真实运行的命令 + stdout / 退出码 + 一次失败样例 | 输入输出、失败怎么办、重跑会怎样 |
| 后端架构 | 时序图 + 请求 / 响应样例 + 状态转移表 + 一条端到端薄切片 | 谁调用、数据从哪来到哪去、哪步会失败 |
| 数据 / 报表 | 一张带真实数字的样例表 + 边界口径 | 指标口径、边界值、异常数据 |
| 集成 | 请求 / 响应样例 + 失败矩阵 | 双方契约、重试 / 降级、版本兼容 |

- **3 个真实例子**：正常输入输出、边界 / 异常、失败或重跑（二选一，在骨架的未定清单里注明选了哪个）；**1 张决策表**：条件组合表。二选一，写进骨架的未定清单旁边。
- 同样按主路四列填对照；样例回答不了上面三问，不算合格。

## 四、实施版与 DoR

- 把对照结果写回正文，删掉所有「待定」；补规则、数据 / 接口、验收、迁移 / 回填 / 回滚、兼容、观测。
- **已确认方案说明 + 自定细节**在终稿齐备；前者承接原机制清单，新增做法及理由须与正文一致，不再有独立机制确认。缺任一，不算实施版。
- **决策依据**：项目已采用 ADR 的链接 ADR；未采用的写「不适用」，不引入新制度。
- **过 DoR 且用户点头后**：有 Draft PR 的 Draft 转 Ready（不另开正式 PR）；无 Draft PR 的，实施版完成后开普通 PR（非 Draft）；然后摆闸卡。骨架版 / 对照版不过闸、不合并。

**DoR 七条**（第 1–4 条不得写「不适用」；第 5–7 条可写「不适用」并说明原因，由审核者接受）：

1. 承重规则只有一个结论，没有 TBD。
2. 每一步有触发 → 响应与失败 / 空态。
3. 每条写路径单一入口；每个状态有字段、有读侧。
4. 每条验收可执行（命令 / 截图 / 断言）。
5. 数据迁移、回填、回滚、兼容都写了。
6. 外部合同（报表 / 开放平台 / 消息通道等）影响与版本写了；无则「不适用」。
7. 项目已采用 ADR 的，supersede 链清楚且正文同步；未采用写「不适用」。

## 五、Draft PR 与合并

- 有页面：方案 Yes、页面选择后写草稿并开 Draft PR，单独选拆分再暂停等用户设计；设计分析完成前不形成终稿、不合并。
- 无页面：不强制 Draft PR；复杂时可开，用于保管骨架和样例。
- 设计稿 / 样例到位后，在同一 PR 里补对照和实施版；不另开设计 PR、修订 PR。
- **Draft 转 Ready** 只在实施版过 DoR 且用户点头后发生，不是另开一个 PR。无 Draft PR 的无页面路径，实施版完成后开普通 PR（非 Draft）。
- **同一 PR**：有 Draft PR 时指骨架时开的那张；无 Draft PR 时指实施版开的普通 PR。
- 只有实施版才摆闸卡；合并卡、审核档位、修订卡照旧。Draft PR 不是批准，设计稿不是验收。

## 六、时点与既有规则

- **状态机**：骨架版 / 对照版仍在 `DESIGNING`；只有实施版过 DoR 且用户点头才进 `SPEC_REVIEW`，再摆闸卡。
- **拆分**：在所选页面分支草稿后摆一次，不在方案确认前提前定；三阶段不是「多阶段实施」，范围 / 结构没实质变化不重复摆，具体判据不变。
- **条件性卡**：例外、改旧 spec 按原条件触发；同一未合并 spec 的成熟度变化不触发改旧卡。独立机制卡与固定三句已由同一方案确认替代。
- **豁免与接续**：直接干只免方案期，不免实现交付；既有任务按当前阶段 / 有效委托接续，不以改动小自动替新需求选入口。

## 七、边界

- 页面由用户选；无页面用样例，有页面必须等用户设计后分析，不因等待而自动降为无页面。
- 不强制 ADR；不新增步骤编号（段一 1–6、段二 7–9 不动）。
- 设计稿 / 样例是同一份 spec 的输入或章节，不是独立文档。
- 只有实施版过闸、可合并。
