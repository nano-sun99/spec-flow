# 工作指南：同一份 spec 的成熟度

> 这是可替换的工作方法，不另立流程、审批或完成判据。当前先后次序见 [one-path](one-path.md)，可实施/送审判据见 [gate-details](gate-details.md)。草稿、对照、终稿是同一文件/PR 的成熟度，不是新增阶段（依据：rationale R34、R37）。

## 一、公共骨架怎么写

用最少内容承接已经确认的目标、范围、非目标与可判验收；把尚未解决的设计、接口、业务口径和验收问题标出来，方便分支分析回填。不必提前猜页面分支、完整接口或最终拆法。

可用“起点/终点 + 路径表”把路说清，也可用段落、时序图、决策表或其他充分表达。以下仅是便于核对的写法，不要求固定列数、岔路数量或每条挂步号：

| 行为 | 对照材料 | 可核结果 |
|---|---|---|
| 用户提交导出请求 | 参数与权限示例 | 返回任务标识；无权限不写入 |
| 工具重跑同一请求 | 前次结果/状态 | 明确幂等、覆盖或拒绝的口径 |

未定项宜集中写“待决定什么、影响哪里、由谁补齐”；有真实期限再写期限，不虚构时间承诺。方案说明与 agent 自定细节尽量一处可识别，末尾是方便扫读的位置，不是任意排版闸。

## 二、把设计或规则当对照材料

### 有页面

结合用户提供的设计版本与骨架，沿实际行为梳理角色、交互、状态、数据、异常和权限；grill-me 的职责与介入位置由流程正文规定。本指南不代替用户设计，不把未拿到的设计写成已分析。

接口分析可以按行为串起来：用户点击什么 → 复用/修改/新增哪项接口 → 请求/响应/错误 → 哪些数据被读写 → 谁可操作。缺页、关键状态、合同或验收空白集中返回公共缺口，不以猜测填满文档。仍适用的设计复用，不因换了表格要求重交。

### 无页面

规则和接口同样可能有缺口。选最便宜且能判对错的材料，例如：

- 脚本：实际输入、命令、输出/退出码，加失败或重跑行为。
- 后端/集成：调用顺序、请求/响应、错误与重试/兼容约定。
- 数据/报表：带实际口径的输入输出表、边界与异常数据。

“正常、边界、失败或重跑”是覆盖风险的提示，不是固定三个例子；一张充分的决策表、可跑断言或其他材料均可。不要为了凑数量虚构数据，也不要用“无页面”跳过接口/业务分析。

## 三、细化为可实施终稿

公共缺口与结构已经处理后，把对照结果回到同一正文；让承重规则、接口/数据、适用异常/兼容、验收与自定选择彼此一致。不同形态的规格可按最清楚的方式组织：纯文档不编造状态机，脚本不硬套页面清单，多服务合同宜显式描述读写与版本影响。

检查有没有“文字说做了、落地物其实没有”、验收无法执行、同一决定多个正文、范围外新增承诺等真实缺口。可实施性、同意送审、Draft/Ready 与合并均回 gate-details 判，不由指南增加另一道检查或要求采用某一张表。

## 四、复用而非堆文件

设计链接、规则样例、事实证据可作为同一 spec 的章节或引用，不另造澄清汇总、设计 PR 或实施计划。较大材料用索引链接，保持设计决定一处正文；结构分析方法见 [split-large-spec](split-large-spec.md)，修订定位见 [spec-revision-sync](spec-revision-sync.md)。
