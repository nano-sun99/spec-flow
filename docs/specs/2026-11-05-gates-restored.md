### 1.3 反例

#147 的 agent **读到了** `gates.md` 的「每份 PR 单独点」，仍把「转 Ready / 合并 / 实施委托」压成一张卡并推荐跳过审核。失效不在「读没读到」，在那句话描述的是习惯，不是可判定的状态。只补字句、不补触发与顺序，会重现同一个洞——这一点见 §9。

### 1.4 原始触发逻辑（本次恢复的基准）

基线取 `75c11fd^`（瘦身前、含 R30 修补）。

| 授权点 | 触发 | 没回答 | 授权范围 |
|---|---|---|---|
| 方案页四格 | 需求确认后，逐格独立点 | 页面判不了就停，其余按 `one-path.md:35-40` 的默认 | 只定方案形状 |
| 拆分卡 | 骨架成形后；结构实质变化时重评 | 不定结构、不开执行单（`split-large-spec.md:22`） | 只定拆不拆 |
| 派审卡 | 每份交付物合入目标分支前；无 PR 的交付前照摆，diff 随卡 | 按「不审」走，不阻塞、不追问 | 只定审不审、哪一档 |
| 修订卡 | 审核有发现（零发现不摆） | 不合并 | 只定改哪些 |
| 合并卡 | 每次合入目标分支，含纯文档 / 机械回填 | 不合并，沉默不算同意 | 只授权该 PR、该目标、该最终改动 |
| 实施委托 | spec 合并、issue 开完并报告后 | 不开工 | 只授权实施 |

三条容易恢复错的：

1. **摆卡与点档是两件事**：派审卡摆了没点 → 按不审继续；压根没摆 → 不算过闸。修订卡、合并卡未答 → 不合并。
2. **顺序是三张卡依次、且一次只摆一张**：派审 →（有发现才有）修订 → 合并。瘦身前 `SKILL.md:8` 已有「按顺序走，不跳步、不合并步骤」，缺的是「不得连摆两张」。
3. **Ready 不是闸**：原始第 4 步是「开 PR → 过闸」，没有 Ready。Ready 是 Draft PR 引入后的 PR 状态，把派审卡绑上去会造出「没 Ready 不必审」。

### 1.5 外部依据

- Skills 分层：description 常驻、body 触发时加载、references 第三层按需（[Anthropic](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。判定属前两层。
- 执行意图比目标意图有效（[Gollwitzer & Sheeran 2006](https://www.sciencedirect.com/science/chapter/bookseries/abs/pii/S0065260106380021)）：「每份合并前 → 摆派审卡」是可执行事件，「审核由用户点档」不是。

## 2. 目标与非目标

### 目标

- 闸的五条判定与三卡顺序进 `SKILL.md`，且只有一个出处。
- description 恢复合并前点档的触发摘要（判定仍只在正文）。
- 每轮第一行四格；动过文件或要合并的轮次加一行交付摘要。
- 机制清单 3 条上限，超了先砍，砍不动按拆分卡重评。

### 非目标

- 不追求 100% 合规；衡量看用户当场抓到漏闸的次数。
- 不新增卡片、档位、章节、reference、脚本、钩子。
- 不改审核四档、2 轮上限、建议池、阻断 / 高规则。
- 不改 `gates.md`（55 行已满）。
- 不改行数 / 字符预算（60 行、2,800 字符）。

### 6.3 恢复的五条判定（落地后逐条可 grep）

1. 每份交付物合入目标分支前摆派审卡；无 PR 的交付前照摆。
2. 派审卡摆过算过、没摆不算；未答按「不审」走。
3. 修订卡、合并卡未答不合并，沉默不算同意。
4. 派审卡落定前不得摆合并卡；三卡不得并卡、不得连摆两张。
5. 机械变更只免派审卡；合并卡每次都要，过闸不授权合并。

### 6.4 明确不复原的两处

- **不复原** 10-17 版「只含 spec / 文档的 PR 长期合并授权」：R30 已删。
- **不复原**「Ready 是闸」：Ready 只是 Draft 转可合的状态。

### 6.5 自定细节

- 判定只在〈闸〉一处；第 5 步、第 9 步、`project-integration.md:13` 都只留指针。`gates.md` 仍是审核协议（四档 / 轮次 / 严重度），不复制判定。
- 闸格三种值；「待点」在派审卡上不阻塞，在修订卡、合并卡上即停。
- 交付行的触发：动过文件，或本轮要问合并卡。方案期纯讨论轮写「本轮无交付」。
- 一行报备的判据固定五项（契约 / 字段 / 空值 / 权限 / 数据结构），任一命中就摆卡；报备不是许可，用户可当场叫停。
- 机制上限计数：三条上限对一切机制生效；本 spec 自己也是三条。
- 「汇报行」与「机制上限」属用户 2026-11-05 点名要的改动（同 R37 口径的用户点头例外）：前者替换原「每轮第一行」，后者替换原「骨架后评估拆分」的触发条件，均非净增章节。
