## 一、问题

spec-flow 现在是一个**流程编译器**：把流程知识编译成固定步骤、固定闸口、固定标签。

- 核心流程约 332 行（`one-path` 127 + `gate-details` 138 + `phase-handoff` 67）。
- 18 种闸口决定、25 步主流程、40+ 个图节点、`rationale` 61,220 字 / 40 条 R。
- 运行方式：agent 照着步骤走。

编译器只能输出它被写过的路径。没写过的路径，输出不了。于是：

1. **越写越细，越细越脆**：每遇到一个岔路就加一条规则，规则之间开始冲突，组合爆炸。
2. **agent 的智力用错了地方**：它把注意力花在“记住并执行步骤”，不是“判断当前情况该怎么走”。
3. **规则变成表演合规**：卡片点了、步骤走了，但没人对结果负责。

#158 已经记录了这个失败模式：一场发布流程审了六轮、60 多条发现，最后砍掉约三分之一的规则，反而更接近目标。根因不是规则数量，是**规则的编译目标**。

## 二、目标与非目标

### 目标

1. 把编译目标从“步骤”换成五层：铁律、阶段合同、决策目录、playbook、案例库。
2. agent 自己规划路径；只在不可逆点设硬闸。
3. 核心规则压到：铁律 ≤60 行、阶段合同 ≤200 行、决策目录 ≤100 行；硬闸 = 8 类用户决定。
4. 把已经演练出的知识保留为案例库，不丢；但案例不是法条。
5. 让“遇到没写的情况”有一条统一出口，而不是每个岔路补一条规则。
6. **v2 是替代品，不是 v1 的并行副本**：B1 必须产出“保留 / 归档 / 丢弃”处置表，明确哪些旧规则被砍掉、为什么砍、砍了以后不保证什么。

### 非目标

- 不做 P7 试跑、P8 切换；本期只交付 v2 文档。
- 不删除或移动旧文件；旧文件留在 `references/`，legacy 迁移属于 P8。
- 不替换根 `SKILL.md`；v2 入口写到 `references/v2/SKILL.md`，切默认属于 P8。
- 不引入新工具、CI、脚本、配置语言或授权平台。
- 不改项目接入形态、发布手册或现有 adopt 行为；v2 的 adopt 适配只做形态映射，五个选修模块和只指向式契约保持不变。

## 三、权威边界与双轨

## 四、架构：五层 + 一个循环

| 层 | 内容 | 维护者 | 加载方式 | 预算 |
|---|---|---|---|---|
| L0 铁律 | 8 条，上限不增长；不可逆动作、用户确认、证据、失败停住 | 用户批准，agent 只能提议 | 每次先读 | ≤60 行 |
| L1 阶段合同 | 4 段：澄清 → 设计 → 交付 → 发布；每段写“什么算完成 + 证据” | 用户批准 | 每次先读 | ≤200 行 |
| L2 决策目录 | 8 类只有用户能拍的决定（D0-D7）；每个写触发、证据、选项、默认 | 用户批准 | 每次先读 | ≤100 行 |
| L3 Playbook | 9 条常见走法；示例，不是必须；闸口相关章节是规范性的 | agent 维护，改闸口证据须用户批准 | 按需读 | 不限 |
| L4 案例库 | 演练、事故、项目适配；叙述 + 提议，不是法条 | agent 维护 | 按需查 | 首版 ≤15 条 |

### 运行循环

```
读事实 → 定阶段 → 出计划（按触发）→ 执行
   ↑                                      ↓
   └── 异常协议 ←── 硬闸摆证据 ←──────────┘
```

1. **读事实**：项目、issue、分支、标签、证据、锁。
2. **定阶段**：这单从哪段进、到哪段出；直接干可以跳过澄清/设计。
3. **出计划（按触发）**：只有满足下列之一才摆计划卡：新任务且范围不平凡；即将发生不可逆动作；预计要问用户超过 3 次。直接干、单行改动、纯文案修改默认不摆计划卡，agent 一句话说明计划后直接做。
4. **执行**：agent 自己选路径；每到一个硬闸，摆事实 + 证据 + 选项。
5. **异常**：先查 playbook / 案例和事实；非不可逆且存在安全默认 → 采用默认并报告；不可逆、无安全默认或多 owner → 停、给 2-3 个选项 + 推荐、等用户选。
6. **收尾**：写案例；只有发现铁律缺了一条，才提议替换/合并一条铁律；否则只记案例。

### 重读触发

任何不可逆动作前，重读 L0-1 和当次决策卡。长任务被压缩后，不假设自己还记得铁律。

## 五、铁律（8 条）

> 上限 8 条；新增必须先替换或合并一条，并经用户批准；不因案例或事故自动增长。每条必须一页装得下；装不下就不是铁律，是流程。

### L0-1 不可逆或高风险动作必须用户明确确认

- **条文**：下列动作必须用户明确确认。非穷尽清单：合并、发布、回滚、删分支、force push、生产写、不可逆数据迁移/回填、删数据、外部契约变更、权限/密钥变更、依赖安装、保护分支直推、移动/删除 tag、改已合并/冻结 spec 正文。
- **兜底**：拿不准是否不可逆，按不可逆处理。
- **为什么**：这些动作错了很难回头；自动回滚、批量授权、默认继续都可能放大损失。
- **执行**：用户确认卡 + 分支保护/权限/生产授权；skill 正文不代替 harness 权限。

### L0-2 事实 agent 查，决定用户拍

- **条文**：agent 负责查事实、给证据、给推荐；用户负责目标、范围、结构、审核、修订和授权。
- **为什么**：agent 的结论不能代替用户的决定；猜、借名、越权都会让用户失去控制。
- **执行**：卡片列事实和选项；没有卡片时给等价明确选项。

### L0-3 证据先于结论

- **条文**：每个阶段出口必须有用户能核、可复现的证据；“我做了”不算证据。
- **为什么**：状态断言必须可核；没有证据的“完成”是表演合规。
- **执行**：阶段合同的证据清单；测试/验收/构建/监控记录。

### L0-4 失败停住上报，不自动恢复

- **条文**：失败、崩溃、监控异常时停住上报；不自动回滚、不静默重试、不把失败改写成通过。
- **为什么**：自动恢复可能掩盖问题；回滚是用户的决定，不是 agent 的默认动作。
- **执行**：HALT + 报告 + 用户选项；回滚只按 L0-1 走。

### L0-5 每份 PR / 每次合入独立确认

- **条文**：一份 PR、一次合入、一个批次，各自独立确认；不批量授权、不互相替代。
- **为什么**：一份同意不覆盖另一份；批量点头会让用户失去对单个对象的控制。
- **执行**：合并卡列对象、目标、提交、验证、未处理项。

### L0-6 范围变了回确认

- **条文**：新增实质内容、换目标、返修、暂停、撤销或要求重审，旧批准不再覆盖；回对应确认。
- **为什么**：批准绑定当次列明的对象、范围和版本；旧批准覆盖新范围等于偷授权。
- **执行**：差异核对；回对应卡片。

### L0-7 承重缺口停下来给选项

- **条文**：遇到承重缺口、无安全默认、多 owner 或不可逆动作，停、查、给 2-3 个选项 + 推荐、等用户选。
- **边界**：非承重的方法/写法差异，agent 自主决定并报告；能自己查、自己判的先做完，不用问题占位。
- **为什么**：猜错的成本高于问一句；但不能把每个小选择都变成问题。
- **执行**：异常协议；不硬走、不静默假设。

### L0-8 铁律只能由用户改

- **条文**：agent 可以提议替换/合并/新增铁律，但不能自己改；用户批准后才生效。
- **为什么**：防止规则膨胀、自授权和“为了修上一条而加一条”。
- **执行**：铁律变更卡；变更记录写原文件；新增必须同时替换或合并一条。

## 六、阶段合同（4 段）

> 每段只写“什么算完成 + 证据 + 出口”，不写步骤。段内顺序由 agent 按这一单的情况决定。澄清 + 设计 = 方案期；交付 + 发布 = 实施期；4 段是内部细分，不改对外“两段流程”。

| 阶段 | 目标 | 完成（全部为真） | 证据 | 出口 |
|---|---|---|---|---|
| 澄清 | 把需求变成可判断的范围、验收和约束 | 改哪里/怎么改/带来什么能力；范围与非目标；验收可判；页面/拆分/观察式例外已定；承重未知闭合 | 澄清记录、需求摘要、验收清单 | 用户确认进入设计，或直接干 |
| 设计 | 把方案变成可执行的 spec/计划 | 方案、备选代价、验收、依赖、数据库变更清单；审核档位与修订范围已选；审核/修订完成 | spec、审核记录、修订记录 | spec 合并 + 执行 issue + **等待明确实施委托** |
| 交付 | 把实现变成可验收的 PR/分支 | 有 issue：issue 分支验收通过 + 四类核对；无 issue 直接干：task 分支部署测试环境验收通过；采用 release：候选按项目分支形态冻结；不采用 release：交付验收后结束 | PR 列表、构建结果、验收证据、四类逐项、worktree/锁记录 | 整条合入 staging（仅 staging 线）/ 任务 PR 合并 / 无发布义务任务关单 |
| 发布 | 把候选变成可复现的生产版本 | 仅采用 release/staging 的项目：批次测试通过；rc 验收通过；生产批准；监控按项目手册 | 批次记录、rc tag、最终 tag、监控结果、发布记录 | 生产验证 + main 快照 + 关单；不采用 release：本段跳过 |

### 交付前置条件

文件变更在独立 worktree；同一 issue 的分支锁名唯一（如 `issue/<N>`）；撞锁停，不双写同一工作区。分支命名可以自由，但锁键不能自由。

### 术语定义（L2 自足）

- **四类**：spec、实现/必要测试、配套文档、必要依赖。
- **合入预演**：把当前 staging 合入 issue 分支（或临时预演分支），在真实 merge 树上构建并跑本 issue 验收；记录预演分支/提交、staging 基线、合并后构建与验收结果。允许 rebase/CI，但必须证明结果树与真实 merge 树一致，否则不算预演绿。
- **批次测试**：在当前 staging HEAD 上构建、部署测试环境，跑回归和跨 issue 验收；之后有新合入即失效，打 tag 前重跑。
- **rc 验收**：从 rc 附注 tag 构建、部署测试环境跑验收；不做 15 分钟监控。
- **生产监控**：从最终 tag 构建、部署生产后启动 Monitor 15 分钟；崩溃 HALT，停住上报，不自动回滚。

## 七、决策目录（8 类，D0-D7）

> 只列“只有用户能拍”的决定。agent 能判的（入口/落点、非关键标签、预演做法、分支命名/提交格式）不进目录，进 playbook。硬闸 = 这 8 类决定类型；每类可多次触发，但类型不增。

| ID | 决定 | 触发 | 证据 | 选项 | 默认 |
|---|---|---|---|---|---|
| D0 | 实施委托 | spec 合并 + 执行 issue 已建 | spec 版本/合并提交、issue、范围、当前锁 | 委托 / 先不委托 | 不委托 |
| D1 | 范围与结构 | 需求/变更进入 | 目标、范围、非目标、验收、页面/无页面、拆/不拆、观察式例外（如适用） | 确认 / 调整 / 不做 | 不做 |
| D2 | 设计与规格确认 | 方案/规格草稿完成 | 方案、备选代价、验收、数据库变更清单、审核档位、修订范围 | 确认 / 改 / 重做；审核档位：不审/轻审/重审/重审+变异；修订范围：全改/只改阻断+高/不改 | 不送审、不合并 |
| D3 | spec 合并 | 审核/修订完成 | 审核结果、修订记录、最终版本、目标分支 | 合并 / 先不合；改已合并 spec：新开一份 / 改旧的（默认不动冻结正文） | 不合并 |
| D4 | 每份 PR 合并（含 hotfix 合回） | PR 审核/验证完成 | PR、目标分支、完整提交、验证、未处理项；hotfix 另加：基于生产 tag、修复提交、验证证据 | 合并 / 先不合 | 不合并 |
| D5 | 整条 issue 合入 staging | issue 分支验收 + 预演 + 四类完成；仅 staging 线 | issue #N、`issue/<N>`、完整提交、预演分支/提交、staging 基线、合并后构建 + 本 issue 验收、四类逐项、未处理项、目标 staging 完整提交 | 合入 / 先不合 | 不合入 |
| D6 | 生产发布 | 批次 + rc 验收通过；仅采用 release | 批次范围（上一个生产 tag..staging）、排除项、未知搭车项处置、必要依赖、rc tag、最终 tag（同一提交）、产物/部署单元、验证、回滚目标、直接干任务清单 | 发布 / 先不发 | 不发布 |
| D7 | 回滚 | 生产异常 | 目标 tag/快照、范围、影响 | 回滚 / 不回滚 | 不回滚 |

### 标签与观察式例外

- **标签**：标签是视图，不是状态机；agent 读事实、提议。至少「待上线 / 待验证 / 关单」必须用户确认；其余标签无歧义时 agent 可换 + 报告，有歧义时问。P0-P6 不改现有 adopt 行为。
- **观察式例外**：纳入 / 不纳入，默认不纳入；触发和字段见 §八。

## 八、记录与证据（15-records）

> 这是 `phase-handoff` 的新载体，不是阶段合同的子节；保留六类交付信息和授权记录，防止“线上这版带没带 #N”再次说不清。

| 信息组 | 必要内容 | 维护责任与时点 |
|---|---|---|
| 获批依据 | spec 仓内路径、获批版本完整提交、方案 PR | 方案作者开单时填；实施者开工核版本 |
| 澄清记录 | `grilling-cards` 轮次、每轮问题与用户决定；未用原因 | 方案作者写 spec 时填；直接干由任务 PR 承接 |

| 收尾/关单 | 验收项是否全勾、遗留项、观察式例外、发布记录链接 | 收尾者按 done 判据填 |

### 关单与 #158 三判据

- 关单判据：约定交付及必要验收完成；回填、关单、放锁收尾；不把缺失/未知/失败证据改写成已通过。
- #158 三判据作为验收例子：① `git diff --quiet <tag> origin/master` = 0；② 能回答“线上这版带没带 #N”；③ 出事时有确定动作。

## 九、Playbook 与案例库

### Playbook（9 条）

1. 新需求开 spec
2. 直接干（无 spec/issue）
3. 续已有 issue 分支
4. 发布（批次 → rc → 生产）
5. hotfix
6. 回滚
7. 批次失败 → fix
8. main 分叉/快照
9. 审核与修订（含 #158 处置机制）

每条格式：

```
# Playbook: <name>
- 适用：...
- 一条走通过的路：...
- 失败模式：...
- 证据：...
- 注意：这是示例，不是必须顺序；按实际情况调整。闸口相关章节是规范性的，不能自行放宽。
```

### 审核与修订 playbook（#158 机制）

- 审核报告加两列：**成因**（甲同步 / 乙设计 / 丙岔路）和**能不能不修**（必须加规则 / 可砍路径 / 可写明本期不保证）。
- 修订卡选项加：**砍掉相关路径**、**写明本期不保证**。
- 甲类同步失误只允许五问对账，不允许为此新增规则。
- 每轮后做范围检查：本轮新增规则里，有几条是原问题必需？答不出来就是扩了。
- 每批设轮次上限；触发上限停，由用户选重画/砍范围/停。

### 案例库

格式：

```
# Case: <date> <name>
- 情况
- 预期
- 实际
- 意外
- 学到什么
- 影响提议：无 / 铁律 / 阶段合同 / playbook（默认无；只是提议，不自动生效）
- 用户是否批准偏离：是/否/不适用
- 被哪条规则覆盖 / superseded_by
```

规则：

- 案例只许叙述 + 提议，不许写祈使句；案例不能被引用为授权。
- playbook 改动若改变闸口证据，须用户批准；案例不能自授权。
- 案例库有索引（case 名 + 何时读 + 关键词）；只在 L0-L2 找不到落点或异常时检索。
- 首版 ≤15 条；每条必须有“改变了什么行为”或“教了什么失败”；B1 处置表标保留/归档/丢弃。

## 十五、依据

- Kaplow, *Rules Versus Standards: An Economic Analysis*, 42 Duke L.J. 557 (1992)：规则写在前、标准判在后；规则起草贵、容易过宽或过窄。
- 美陆军 ADP 6-0 *Mission Command* (2019)：只给意图和约束，怎么打由现场按情况决定。
- Snowden & Boone, *A Leader's Framework for Decision Making*, HBR 2007：复杂问题用 probe-sense-respond，不套最佳实践。
- WHO Surgical Safety Checklist：19 项、3 个暂停点，不是手术步骤手册。
- Anthropic, *Building Effective Agents*：先找最简单解；workflow 是预设路径，agent 自己决定路径。
- Claude Code Best Practices：每一行都占注意力；只写模型自己看不出来的；不能有例外的规则用 hook/权限。
- Kubernetes 对象管理与控制器：声明式写“要什么状态”，控制器循环把实际状态拉向期望状态。
