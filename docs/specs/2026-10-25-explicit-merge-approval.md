## 2. 目标与边界

### 目标

- 所有 PR 均在本份审核、自查及必要修订结束后，单独取得合并卡上的明确同意。
- 代码、spec、普通文档、配置、资源和机械回填使用同一个合并确认规则，不让 agent 按内容轻重自行免问。
- 审核、修订、合并分别授权，未答审核卡的默认值不能扩展为合并授权。
- 授权只覆盖用户实际看到的那份 PR、目标分支和最终改动；内容变化、重新审核与暂停有明确的停止条件。
- 主文件保留紧凑判据，执行细节落在既有闸细则；同步说明、历史取代关系和验收证据。

### 非目标

- 不新增卡型、审核档位、审核 agent、长期授权登记表或生命周期状态。
- 不新增 Hook、CI、脚本、机器人、GitHub 保护规则或其他运行时拦截。
- 不改变审核卡未答按“不审”继续的默认值，不增加强制审核。
- 不改变既有修订卡的处置流程、已知阻断缺陷的完成标准、worktree 锁或实施委托规则。
- 不把 issue 评论、平台验收勾选等非 Git 合并动作也变成合并卡；它们照已有收尾规则执行。
- 不重写已合并规格正文，不修改下游项目指令、不建立采用名单。

## 3. 机制清单

**无新增机制。** 本次复用既有合并卡、审核卡、修订卡和闸细则，只收紧合并卡的覆盖、时点及授权边界；不增加新的审批工具、记录载体或自动化能力。

| 既有机制的调整 | 解决什么 / 不做会怎样 |
|---|---|
| 合并卡覆盖全部 PR，删除文档长期豁免 | 取消按文件类型自动合并的出口；否则文档和机械回填仍可能免问 |
| 审核、修订、合并分别授权 | 保留不审选择，同时不让“审核结束”变成“批准合并” |
| 合并卡明确 PR、目标与最终改动 | 防止把上一份、上一版或另一个目标的同意挪用到本次 |

## 4. 合并确认规则

### 4.1 覆盖范围

凡要将 PR 合入目标分支，都须走本规则，不仅限于默认分支，也不因目标分支未受保护而免问。纯 spec、普通文档、配置、资源、回填 issue 号、状态、索引、勾验收等机械改动形成 PR 时同样适用。

删除“只含 spec / 文档的 PR（长期授权）”这项合并卡豁免。本次不保留机械回填的合并卡例外；机械变更免审核闸的既有规定仍可保留，但免审核不等于免合并确认。

“直接干 / 别走流程”只免方案期；“直接改 / 不开 wt”只作用于工作区。两者均不能被推导为合并授权。

没有 PR 可走的实施成果继续按既有交付闸处理，本次不为其新造 PR、目标分支或合并动作。

### 4.2 三种用户回答的权限

| 卡片 | 只授权什么 | 不包含什么 |
|---|---|---|
| 审核卡 | 当前交付物是否审核、用哪档 | 采纳发现、代码实施或合并 |
| 修订卡 | 按当前发现进行修订 | 修完后直接合并 |
| 合并卡 | 当前列明的 PR 按最终改动合入列明目标 | 其他 PR、后续版本、实施下一份需求或生产发布 |

“不审”“零发现”“检查全绿”“同意修改”“已修完”“需求可以”都不构成合并同意。审核 agent 的“可以合并”等建议也不是用户授权，不能替用户回答合并卡。

### 4.3 顺序与停止条件

正常顺序为：本份审核或自查完成 → 发现按用户决定修订并验证 → 单独摆合并卡 → 用户明确选择“合并” → 执行合并 → 按既有规则回填与交接。

- 审核卡未答或选择不审：按既有默认值完成自查，然后进入合并确认，不得直接合并。
- 审核零发现：照旧贴审核结论，不摆空修订卡；随后仍须摆合并卡。
- 审核有发现：先原样贴结论并摆修订卡；用户未答或选择“不改”时不自动修改、不合并，不把合并卡当作绕过待决修订的出口。
- 用户批准修订：完成修订与相关验证后再问合并；“改”不具有预授权合并的效果。
- 合并卡未答、被关闭、选择“先不合”，或用户暂停、撤销、要求重审：停止合并，保留当前 PR；不得催答，也不得将沉默当成同意。
- 重审或新增修订后，重新满足审核、修订及验证条件，再针对最终版本摆合并卡，不能沿用重审前的同意。
- 任何尚未满足的既有阻断条件不会因用户选择合并而自动消失；出现冲突时报告，不把合并卡当作测试或完成标准的默认豁免。

### 4.4 合并卡上的对象与最终状态

合并卡至少让用户看清 PR 链接或编号、目标分支、最终改动摘要以及验证结果与已知未处理项。用当前提交标识定位卡片所指的版本，不新增授权数据库或固定报告文件。

执行前重新核对 PR 的实际目标、版本与改动。新增实质内容、更换目标、用户要求返修或重审时，旧合并同意失效，重新完成受影响的核对并摆卡。版本变化而尚未核清差异时先停下，不能凭旧卡执行。

现有“一卡盖批”是审核批卡，不是合并授权。每份 PR 仍单独确认，某份的同意不扩展到同批下一份；本次不新增批量合并卡。

### 4.5 禁止绕行

没有取得上述明确合并同意之前，不得执行立即合并，也不得提前启用自动合并、加入会导致稍后自动合入的队列，或通过直接更新目标分支、推送主干等方式绕开确认。

这里约束的是合入结果及其预先安排，不仅是某条命令的名字。用户批准本份合并后，仍须遵守项目既有的 Git 危险操作、分支保护、验证与收尾规则，不因此获得绕过检查、强推或发布生产的权限。

## 7. 验收标准

- [ ] 所有 PR 合入任何目标分支都适用独立合并卡，文档与机械回填不再免问。
- [ ] 审核卡、修订卡、合并卡分别授权；不审、零发现、检查绿、同意修订不能代替合并同意。

- [ ] 审核批卡与其他 PR 的授权不替代本份合并卡；无授权时不提前启用自动合并、排入自动合入队列或直推目标分支。

## 8. 体量评估与结构选择

本需求的成果是一套一致的合并授权规则，中央正文、闸细则、双语说明与历史取代必须相互对应；没有需要分批验收或另行安排节奏的实施里程碑。普通写规则、验证和提 PR 不作为多个阶段。

真实候选拆法如下；用户已在 2026-10-25 拆分卡选择“不拆”，按单份规格与单张执行 issue 交付。

| 方案 | 交付组成 | 依赖与代价 |
|---|---|---|
| 不拆（推荐） | 1 份 spec、1 张执行 issue | 一次交付一致规则，不需要父单或跨份同步 |
| 拆 | 1 份总纲、2 份执行 spec、2 张执行 issue、1 张仅跟踪父 issue | S01 交付中央授权规则与验收，S02 交付双语说明及历史取代；S02 消费 S01，部分共享依据文件需单一 owner，增加跨份协调 |

推荐不拆：说明和历史取代不是独立业务成果，拆后仍须与核心规则一致合入，收益低于增加的协调成本。用户已在 2026-10-25 选择“不拆”；没有保留多阶段里程碑。若后续范围或结构发生实质变化，重新评估并摆拆分卡，不沿用本次选择。执行 issue 仍须等规格 PR 合并后创建。
