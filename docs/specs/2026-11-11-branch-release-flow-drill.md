## 一、主流程

| 步 | 做什么 | 产出 / 闸口 |
|---|---|---|
| 1 | 用户描述需求，必须调用 `grilling-cards` 澄清 | 三块内容；确认术语映射；澄清记录（轮次/问题/决定）随 spec 或原任务 PR |
| 2 | 选入口：直接干 / 开 spec | 用户选 |
| 3 | 写 spec | spec 文件；含三块内容 + 数据库变更清单 |
| 4 | 选 spec 审核档位 | 不审 / 轻审 / 重审 / 重审 + 变异 |
| 5 | 审核结果 → 选修订范围 | 全改 / 只改阻断 + 高 / 不改；有阻断或高不改，不合并 |
| 6 | spec 合并确认 | 用户单独确认，审核通过不等于合并同意 |
| 7 | 开执行 issue，写交接 | issue #N、交接区；状态 `SPEC_READY` |
| 8 | **停**：等用户发实施委托 | 本人或另一个 agent 发委托；不自动继续 |
| 9 | 记实施委托，认领 worktree | 标签「进行中」、`issue/<N>` |
| 10 | 实施完成，开实施 PR（提到 issue 分支） | PR；不直接进 staging |
| 11 | 选实施 PR 审核档位 | 不审 / 轻审 / 重审 / 重审 + 变异 |
| 12 | 审核结果 → 选修订范围 | 全改 / 只改阻断 + 高 / 不改 |
| 13 | 实施 PR 合并确认 | 用户单独确认；合并进 `issue/<N>` |
| 14 | issue 分支测试 | 验收证据贴 issue；标签「测试完成」 |
| 14a | 合入预演：把当前 staging 合入 issue 分支，构建并跑本 issue 验收 | 预演提交/证据；绿了才进闸 |
| 14b | 四类核对：spec、实现/测试、文档、依赖 | 缺项不放进闸 |
| 15 | 整条合入 staging 闸口 | 用户确认整条合入 |
| 16 | 合入 + 标签 | 真 merge；标签「待上线」；分支冻结 |
| 17 | 批次测试 | 通过 → rc；失败 → `fix/N`，标签保持「待上线」 |
| 18 | rc 标签 | 附注 tag；固定已测提交 |
| 19 | rc 验收测试 | 从 rc tag 构建、部署测试环境、跑验收；通过 → 最终 tag |
| 20 | 最终标签 | 与 rc 同一提交打正式版本 |
| 21 | 生产发布批准 | 用户明确批准；首次发布无上一个生产 tag |
| 22 | 部署 + 监控 | Monitor 15 分钟无崩溃；崩了 HALT，不自动回滚 |
| 23 | 收尾 | main 快进、issue 关单、清分支、发布记录 |

第 3 步的数据库变更清单至少写清三样：新表、新字段、现有表新增行（例：`sys_menu` / `menu_role_relation`）。没有就写「无」，不省略。

### 直接干路径（无 spec、无 issue）

1. 入口澄清后选直接干：不补 spec、不补执行 issue；从 staging 切 `task/<slug>`。
2. worktree 目录 `task-<slug>`；没有 issue 锁，分支名即锁。
3. 改动和测试在 task 分支上完成；PR 提到 staging，但先不合。
4. 把 PR 分支部署测试环境，跑验收；通过才进合并闸口。
5. 合并闸口由用户单独确认；合并后直接进 staging，不经过 issue 分支，也没有 issue 标签。
6. 发布记录手工列直接干任务（分支、PR、commit、验收证据）；标签查询查不到它们。
7. 批次测试失败时切 `fix/<slug>`；不回到已合并的任务分支。

## 二、分支、worktree、提交

| 用途 | 命名 | 例子 |
|---|---|---|
| issue 集成分支 | `issue/<N>` | `issue/1` |
| worktree 目录 | `<wt根>/issue-<N>` | `.claude/worktrees/issue-1` |
| 同 issue 并行 PR（可选） | `issue/<N>/<slug>` | `issue/1/audio-engine` |
| staging 批次修复 | `fix/<N>-<slug>` | `fix/1-disk-full` |
| hotfix | `hotfix/<tag>-<slug>` | `hotfix/v2026.11.11-crash` |

- N 是 issue 号，不补零；不加日期、owner、版本。
- 一个 issue 一条集成分支；`<slug>` 只在同一 issue 真要并行 PR 时才加。
- 分支名就是锁；worktree 目录用连字符，避免嵌套目录。
- 现行 `worktree-lock.md` 写的是分支和目录都叫 `issue-<N>`；采用本口径要改一句：分支 `issue/<N>`、目录 `issue-<N>`，锁仍以分支名为准。
- 并行按 issue 分：一个 issue 一个 worktree。同一 issue 内要并行多个 PR，再单独定。

提交标准：

- PR 标题或 squash 提交：`type(scope): summary (#N)`。
- 分支里的 WIP 提交随意，合进 issue 分支前 squash 掉。
- 直接提交到 issue 分支时：每个提交 `type(scope): summary`，一个提交一件事；不必每条带 `#N`。
- 合入 staging 用真 merge，不用 squash，保留 PR 级提交。

## 三、标签生命周期

现有阶段标签：未开始、进行中、待测试、待上线、待验证；卡点标签：等拍板、受阻。本次新增 **测试完成**，共 8 个标签。

| 时点 | 事实 | 标签 |
|---|---|---|
| spec 合并后开单 | issue 已建，未认领 | 未开始 |
| 认领 worktree | worktree 和分支已建 | 进行中 |
| 开发完成 | 预期交付都有对应 PR 且已合入 issue 分支，构建通过 | 待测试 |
| issue 分支测试通过 | 验收路径有通过证据 | 测试完成 |
| 合入 staging | merge commit 存在 | 待上线 |
| 批次测试失败 | 失败指向本 issue，切 `fix/N` 修 | 待上线（不变） |
| 上线成功 | 有留下的验证项 | 待验证 |
| 验收项全勾 | 无遗留项 | 关单 |

规则：

- agent 每次动作完成后读事实：issue 正文的预期交付和验收、关联 PR 状态、测试证据、merge commit、发布记录。
- 够条件就提议转标签，证据不足就提议补证据；不猜。
- 提议卡列出事实和证据，用户确认后才换标签。
- 「待上线」不可逆：批次测试发现问题就切 `fix/N` 修，标签不回退。

## 四、闸口清单

| 闸口 | 谁决定 | 不满足时 |
|---|---|---|
| spec 审核档位 | 用户选档 | 不派 agent；合并卡照旧 |
| spec 审核修订范围 | 用户选 | 有阻断或高不改，不合并 |
| spec 合并 | 用户单独确认 | 保留 PR |
| 实施 PR 审核档位 | 用户选档 | 不派 agent；合并卡照旧 |
| 实施 PR 修订范围 | 用户选 | 有阻断或高不改，不合并 |
| 实施 PR 合并 | 用户单独确认 | 保留 PR |
| 整条 issue 合入 staging | 用户确认 | 留在 issue 分支 |
| hotfix 合回 staging | 用户确认 | 留在 hotfix 分支 |
| 生产发布 | 用户明确批准 | 不部署，保留 tag |
| 回滚 | 仅用户批准 | 停住上报，不自动回滚 |

## 五、验证与发布

- **深度验收**：在 issue 分支按 spec 的验收路径做。taoxi_system 例：两条线入口和权限、旧链接带参数重定向、按线计数、移动端两个图标、发起入口回归。
- **批次测试**：staging 上这一批作为整体构建、部署测试环境，跑回归和跨 issue 验收。它回答「这批能不能发」，不是「这个 issue 做没做对」。
- **rc 标签与验收**：rc tag 固定已测提交；从 rc tag 构建、部署测试环境，跑验收测试（功能/回归），不做 15 分钟监控。通过后才打最终 tag；rc 与最终 tag 指向同一提交。
- **生产监控**：从最终 tag 构建，部署生产，启动 Monitor 15 分钟；有崩溃事件则 HALT，停住上报，由用户决定当场修还是回滚。
- **首次发布**：没有上一个生产 tag，回滚目标是部署前快照或原恢复方案。
- **main**：生产验证通过后快进到最终 tag 的同一提交；分叉时按快照方法，不用 reset 覆盖。

### 批次收口与搭车项

- 批次可以手动收口；每次往 staging 合新改动，之前跑的批次测试失效，打 tag 前要重跑。
- 批次范围按「上一个生产 tag..staging」核；来源未知的搭车提交必须显式决定纳入或移出，不能静默放行；纳入的要在发布记录列明。

## 六、新项目起步

- 先建项目仓，同时有 `main` 和 `staging`。
- spec 作为第一个 PR 合入 `staging`；再开执行 issue，从 `staging` 切 `issue/<N>`。
- 首次发布前没有生产 tag，hotfix 线不可用；hotfix 要等第一次生产 tag 之后。

## 九、多 PR 需求如何保证整体到达（2026-11-13 结论）

用户提出的问题：一个需求 PR 很多时，怎么保证整体到 staging 并被发布。对照 dev+pick 与 issue 集成分支两条路线，结论是它们解的是同一个问题的三层：分支管「单元」，预演管「合入」，tag 管「发布」。

### 三层与五个动作

| 层 | 问题 | 做法 |
|---|---|---|
| 集成单元 | 多份 PR 怎么算一个整体 | issue 分支把需求变成可测试、可合并、可引用的 git 对象；dev+pick 的单元是文档清单，靠人重建 |
| 合入安全 | 这个整体能不能安全进 staging | 合入预演：把当前 staging 合入 issue 分支，在合并后的树上构建并跑本 issue 验收 |
| 发布可复现 | 发布的是不是测过的 | 批次冻结 + rc tag + 从 tag 构建验收 + 同一提交打最终 tag |

五个动作：单元存在、对着目标预演、原子落地（真 merge 不 squash）、清单留痕（issue 交付区 + 发布记录）、从不可变 tag 发布。

### 两条路线的差别

- dev + 分拣：集成在主线上持续发生，需求是发布时按清单重建的；单元在文档里，靠人核。适合松耦合、小 PR、能独立上线。
- issue 分支：集成在分支上发生，需求本身是 git 对象；单元在 git 里，靠机制保证。适合紧耦合（DB 迁移、权限拆分、跨端契约）、需要独立验收。
- 判据：这些 PR 能不能拆开单独上线而不影响用户？能走主线，不能走集成分支。
- 第三条：stacked PR，一条依赖链逐层合，适合有先后依赖但不需要独立验收的情况。

### 行业对照

- GitHub merge queue：用目标分支最新 + 排在前面的 PR 一起测，解决「每个 PR 单独绿、一起红」。
- Gerrit `submitWholeTopic`：单仓内 topic 原子提交；跨仓只尽力。
- Chromium CQ：先跑 trybots 再提交。
- trunk-based + feature flag：短分支 + 开关，替代长集成分支。
- stacked PR：依赖链替代集成分支。

staging 线取「集成分支 + 原子合入 + 预演」三件，不引入 merge queue 的 CI 改造，也不要求全量 feature flag。

### 本轮补进流程的两处

1. 合入预演（主流程 14a）：预演回答「能不能安全合进去」，批次测试回答「这一批能不能发」；预演绿了才进整条合入闸。
2. 四类核对前移（主流程 14b）：spec、实现/测试、文档、依赖从发布分拣前移到合入闸；缺项不放进闸。

### 落点判定：新请求属于哪条分支

| 事实 | 归属 |
|---|---|
| 在某个 open issue 的已批准范围内，且分支未合入 staging | 续该 issue 分支 |
| 命中多个 issue | 列候选给用户选 |
| 无命中，改动边界清楚 | 直接干，开 task 分支 |
| 无命中，有独立验收或需设计 | 开新 issue，必要时开 spec |
| issue 已合入 staging 或已关单 | 不续；走 `fix/<N>` / `fix/<slug>` 或新 issue |

agent 查事实、给推荐，用户确认；不猜。证据来源：分支名、PR 正文「关联 issue：#N」、commit `(#N)`、issue 交接区、worktree 锁、发布记录。
