## 1. 起点、终点与主路

**起点**：用户提出新需求，或明确委托实施已获批的 issue。

**终点**：交付按规格验收，审核与修订按用户选择闭合，并对最终 PR 取得合并授权（含条件式授权）；否则停在清晰命名的待决定状态。

| 步 | 触发 → 响应 | 失败 / 未答 | 落点与证据 |
|---|---|---|---|
| 1 需求 | 新代码需求 → 核对是否已有获批 spec；动笔前核工作区、范围、目标与 diff（R2-11） | 无获批规格 → 先完成方案；不得按大小自判豁免 | spec 链接 / 当前 issue |
| 2 方案 | 方案页四格各自独立点；新机制先单摆机制卡（R2-10）；判页面，判不了停 | 用户未批准 → 不写代码；纯事实查询不造 spec | 用户回复 + spec 版本 |
| 3 交接 | spec PR 合并 → 报 `SPEC_READY` → 开执行 issue 与交接区 | issue 建失败留在 `SPEC_REVIEW` 重试 | `phase-handoff.md` 交接区字段 |
| 4 授权 | 用户按闭集表述委托（「开始实施 #N」等） | 表述不在闭集（「继续」「开始吧」）→ 不开工 | `phase-handoff.md:105-108` 闭集；授权记录 |
| 5 实施 | 一次授权覆盖整份 spec，agent 自行组织批次；步骤不跳、不合并（R2-9） | 只在六个停止点停：新岔路/新决定、生产写、不可逆迁移、外部契约变更、范围变化、闭环破裂（`phase-handoff.md:56` 原文，不复制） | 变更与验收证据 |
| 6 审核档 | 每份交付物合并前摆派审卡，卡上带「文档检查」一行 | 卡未展示不算过闸；展示后未答按「不审」自查（范围见 R2-1），仍不得省合并卡 | 机制 1 的留痕记录 |
| 7 修订 | 有 findings → 按项分类，摆修订卡；改判据/定义/常量/术语前读 `spec-revision-sync.md`（R2-13） | 未答、阻断/高未闭合 → 不合并 | 每条 finding 的落点与证据 |

## 2. 授权边界

### 2.1 卡片留痕（机制 1）

- 审核卡与合并卡摆出后，把这一行写进 PR 评论（没有 PR 写进对话）：`卡：<卡名> · <时间> · 对象 <PR/head> · 选项 <列出的选项> · 文档检查 <绿/红+摘要/无入口>`；用户答完补 `用户：<原话>`。
- 没有这一行 = 卡未展示，「未答按不审」不成立；合并卡缺这一行 = 未取得合并授权。
- 一卡盖批（`gate-details.md:40`）记一条，写明「N 份 × 档位」与成员清单。
- 项目禁的审核档（`project-integration.md:37`）在卡上写「项目禁档：不摆、不派」，视同已展示已答，不派 agent。
- 拿不准算不算要摆卡时不自判，摆卡并在卡上写明归属（R2-4）。

### 2.2 条件式合并授权（机制 2）

- 用户对同一 PR 说过「改完再合并」「修好就合」这类条件式指令，视为对该 PR 的合并授权；修订完成后不再重复摆合并卡。
- 合并前贴一行：`按原授权合并：<用户原话> · head <sha> · 改动仅含 <修订项>`。
- 出现下列任一情况即失效，重新摆卡：修订引入原话以外的内容；换目标分支；用户改口或撤回；head 变化后核对出差差异超出修订项。
- 这不豁免合并前的验证与文档检查，也不把「条件式」扩到同批其它 PR。

### 2.3 委托与停止点

- 委托入口按 `phase-handoff.md:105-108` 的闭集判断，不写「等价的明确委托」；礼貌前缀不改变闭集判断。
- 一次授权覆盖整份 spec 的全部阶段；阶段完成不是停点，停止点以 `phase-handoff.md:56` 的六项为准，本 spec 不复制该表。

## 3. 越界与 findings 分类

- 越界 = 停 + 变更单；修订卡只处理已批准范围内的 findings。
- 范围外的增强与更优解进建议池，不阻断本单（`gates.md:44` 已写，本 spec 不重复）。
- 严重度仍按 `gate-details.md:20`（阻断 / 高 / 中 / 低），不新增分类法。
- 「闭环前提未定」只在两个条件同时成立时才用：缺该前提则某条 AC 不可验证；能指出缺的是什么证据。否则按范围内缺陷处理。

## 4. E5 修正（机制 3）

1. **缺「改」清单 fail closed**：给了 `--base`/`--diff` 且 diff 非空、spec 没有「改」清单时，E5 报红（现为 warn），提示「闸一 E1–E4 不受影响；转 Ready 前必须补清单」。没给 `--base`/`--diff` 时仍为「跳过」，骨架期照旧不受影响。
2. **「不改」参与比对**：diff 命中「不改」路径即报红。同一文件同时命中「改」与「不改」时更具体者胜（pattern 段数多者；段数相同取字符串更长者；仍相同则「不改」胜）。
3. **路径归一化**：清单项先剥句末标点再剥反引号，避免 `` `references/rationale.md`。 `` 解析成带反引号的路径而不命中自己；补一条「清单每项必须命中自己」的 fixture。
4. **不判语义**：仍只按路径检查，不假装识别业务语义越界、用户是否批准或执行顺序。

## 7. 风险与代价

- 细则回到 `gate-details.md` 后，只在派审 / 合并时读到；开工期靠 `gates.md` 三行触发句兜底，覆盖不到「核影响」「机制卡」两步——那两步在 `one-page.md` 与 `one-path.md`。
- 条件式授权会让「head 变了但内容没超范围」不再二次确认；兜底是「按原授权合并」一行记录 + 超范围即失效。不是机械拦截。
- 留痕靠写评论；漏写即视为没摆卡，会误伤认真摆过卡的 agent——接受，因为「可核」比「少写一行」重要。
- E5 仍按路径，不判语义；「不改」里的散文项（如「业务仓」）不参与比对，只人工核。
- 本仓把「改一行」入口收紧为用户点名，比全局 `~/.agents/AGENTS.md` 的同名条更严；是否同步全局由用户定，本 spec 不改那个文件。
- 12 条里 R2-7/R2-8/R2-9 是老版本主干句，恢复后 `gates.md` 仍是 55 行，代价是删两条与新细则重复的句子；被删句在 `gate-details.md` 有等价表述。
- 行为回放不列为 AC，「agent 是否真照做」仍靠事后抽查。
