## 0. 方案页

### 目标与问题

本 spec 修复一条有授权证据的主线，不把所有痛点都塞进同一轮：**先能判断现在在哪个许可点，再只问这件事所需的授权，并明确哪些工作已经闭合。**

本地会话与远端记录给出四种可复核失败：

1. Claude Code 于 11-03 新增阶段流程时，先写实现参考文件，用户拦下后才撤回并开规格 PR。
2. Nano 的 OA 工作微信案例（#144）在用户澄清返回第一个号码后先改代码，规格在用户追问后才补。
3. 回执规格 PR #157（#147）把 Ready、合并与实施放进同一推荐选项；agent 尝试合并时，审核档位尚未单独选定。
4. Nano 的 #911 会话中，用户授权整份 issue 自主实施并要求最后展示审核档位；agent 自主推进多批是合适的，但没有记录到用户单独批准最终合并，PR #912 已先合入，用户随后才发“改好了吗？改完再合并”。

反向错误也要保留为回归条件：#143 中用户已经明确允许打指定 tag，agent 仍重复询问。恢复闸口不能变成“每一步都再要一次同意”。

## 1. 起点、终点与主路

**起点**：用户提出新需求，或明确委托实施已获批的 issue。

**终点**：交付已经按规格验收，必要的审核与修订已按用户选择闭合，并对最终 PR 取得明确合并授权；否则停在清晰命名的待决定状态。

| 步 | 触发 → 响应 | 失败 / 未答 | 落点与证据 |
|---|---|---|---|
| 1 需求 | 新代码需求 → 核对是否已有获批 spec | 无获批规格 → 先完成方案；不得用规模小自判豁免 | spec 链接 / 当前 issue |
| 2 方案 | spec 第一屏列目标、不做、验收、改/不改；给用户需要的方案选择 | 用户未批准 → 不写代码；纯事实查询不造 spec | 用户回复 + spec 版本 |
| 3 交接 | spec PR 合并且执行 issue 建好 → 报 `SPEC_READY` | 不在 spec 阶段自动创建实施 worktree | 项目交接记录 |
| 4 授权 | 用户明确委托执行 issue → 一次授权覆盖该 spec 全部阶段 | 缺 spec、对象不明、范围外扩张 → 不开工/停受影响部分 | 原话、issue、spec 合并版本 |
| 5 实施 | 已授权 → 用默认隔离 worktree 连续完成获批范围 | 阶段完成本身不是停点；新业务决定、范围/交付结构变化才停 | 变更与验收证据 |
| 6 审核档 | PR 合并前 → 展示现有审核档位卡 | 卡未展示不算过闸；展示未回答按“不审”自查，但仍不得省修订/合并卡 | 卡片对象、审档回答或不审默认 |
| 7 修订 | 有 findings → 按项分类，展示修/不修选择 | 未回答、未处理阻断/高、范围改变未确认 → 不合并 | 每条 finding 的落点和证据 |
| 8 合并 | 审核/自查与已授权修订完成 → 单独展示该最终 PR 合并卡 | 沉默、拒绝或 head 改变 → 不合并/重新核授权 | PR、目标、head、验证与未处理项；合并结果回填关联 PR / issue |

阶段进度、审核结论、逐项处置、验收结果和收尾说明属于已授权 issue 生命周期的正常回填；用户已授权整份 issue 后，不为每条进度评论或状态变更再加一张卡。状态标签只在项目已声明采用 `issue-status` 时更新，标签语义按该项目映射；未采用时不建标签、不猜标签。回填不授权合并，也不替代审核、修订、合并各自的用户决定。

分拆、方案成熟度、关闭 issue、发布与 release 的既有语义不改变；不新增步骤编号。

## 2. 授权触发矩阵

| 授权点 | 什么时候出现 | 用户没答 | 只授权什么 |
|---|---|---|---|
| 方案确认 | 新需求的主路/关键业务岔路已梳理后 | 不动代码；选择缺失时不把默认当业务决定 | 选择写明的方案边界 |
| 拆分 | 骨架成形；范围、产物或依赖结构实质变化时重评 | 不定执行结构、不自动开执行单 | 拆或不拆及卡上列出的结构 |
| 审核档 | 每份交付物合并前；没有 PR 的交付在交付前 | 卡确实展示后未答，沿旧默认“不审”自查；没展示不算过闸 | 是否审核与审核档位；agent 不自选、不用推荐代替用户选择 |
| 修订 | 有审核发现且存在需要用户决定的处置 | 不修改争议项、不合并 | 全改 / 只改阻断与高 / 不改；选择不授权再次派审 |
| 实施委托 | 方案已合并、执行 issue 已建并报告；或用户明确做现存 issue | 不开实施工位 | 整份获批 spec，允许分阶段自主推进 |
| 合并 | 最终 diff、目标与 head 已确定后，每份 PR 单独出现 | 不合并；静默不是同意 | 仅卡上列明的最终 PR 和目标 |

- 一张卡只解决一个授权问题；审核、修订、合并、Ready、实施委托不得并入同一推荐选项。
- 有一张卡已展示不代表其它卡已经展示或回答。
- 用户对同一对象、同一动作已给出清楚指令，不重复问；新 head、新目标、新范围、返修或撤销造成授权对象变化时重新确认。
- 不把 agent 推荐“不审/直接合并”的选项伪装成默认许可。
- 零 findings 不摆修订卡；但审核卡和合并卡仍按既有触发单独处理。
- 审核结论按既有规则原样回填到 PR；修订后逐项记录处置与验证；issue 的阶段、验收和收尾结果按 `project-integration.md` 既有骨架回填。
- 若项目已采用 `issue-status`，生命周期进展同时更新项目映射的 issue 状态标签；没有项目声明时不建标签、不猜状态。回填是记录，不增加额外审批，也不授予合并许可。

### 用户不需逐阶段接管

“开始实施 #N”或等价的明确委托，授权执行整份获批规格的正常实施步骤；agent 可自行组织 B1/B2/B3、代码与测试，不在每个里程碑要求续做许可。授权不覆盖新产品决定、规格外扩张或任何 PR 合并。需要停时只停受影响的部分，说明原因和后续选项，不把“检查更多”扩成全面重做。

### worktree 默认

有文件变更时先对表远端，从 `origin/main`/项目主分支建立隔离 worktree；这是 agent 自动遵循的默认，不另问是否建。用户明确要求当前工作区或不开 worktree 时按其指令办理。事实查询且不写文件不建 worktree。不得把“我应该先建 worktree吗”变成每个任务的额外确认卡。

## 3. findings 与范围边界

每条发现先回答：**它影响哪条已批准的承诺？如果现在不处理，原承诺是否仍能成立？**

| 类型 | 判据 | 处置 |
|---|---|---|
| 范围内缺陷 | 不满足已批准 AC / 事实引用错误 / 实际 diff 越界 | 记录证据；在用户选择的修订范围内修，逐条验证 |
| 闭环前提未定/不成立 | 缺字段、关系、权限、数据质量或业务裁决，原承诺可能无法兑现 | 暂停受影响承诺，由用户选缩小范围、补前提或改规格；不靠无限修文档假闭合 |
| 独立新增需求/建议 | 不影响本次目标，仅是增强、重构或以后可以更好 | 放建议池，不阻断本单，不自动并入 |
| 未核事实 | 代码/数据证据不足、审核误读或互相冲突 | 标“未确认”并说明需要什么证据；核实前不把推测写成 defect 或边界决定 |

- 严重度与范围类型分开记录：范围外不因标高就自动扩 scope；范围内阻断不因改进文档就算解决。
- 结构、所有者、入口清单、依赖、数据语义或 AC 的实质变化，先由用户确认变化再继续；普通措辞修订不重摆结构卡。
- “代码确实改了”不是 finding 闭合证据；同样，“用户觉得没改”也不能否定已有 diff。摘要需要指向文件/行、提交、验证结果，使用户无需通读 PR 才能判断。
- 审核轮次继续使用现有停止规则：轮次上限是触发“重画 / 砍范围 / 停”的节点，不是 agent 自动挑一个答案，也不是禁止用户重新发起新一轮审核。

## 4. 返回格式与生命周期回填

默认只在需要用户决策或交付时给完整摘要；普通阶段进展一行说明即可，不反复重述全部目标。

```text
状态：<完成 / 等你决定 / 受阻 / 未验证>
本次结果：<一句话>

| 改哪里 | 怎么改 | 带来什么能力 |
|---|---|---|
| <文件/功能> | <一句改动> | <用户能得到什么> |

尚未闭合：<只列影响当前决定的项目；没有写“无”>
验证：<实测 / 未实测 + 原因>
下一步：<谁做什么>
```

- 审核总结先给阻断/高与用户要决定的事项；每条显示类型、承诺、处置、位置、验证状态。中低建议可折叠/链接，不把 40 条 findings 原样摊在决策摘要。
- 审核结论按既有规则原样回填到 PR 评论；issue 阶段、验收与收尾按 `project-integration.md` 已有回填骨架更新。项目已声明 `issue-status` 时按该项目的映射同步状态标签；未采用则不建、不改。
- 这些评论和标签更新属于已授权生命周期的记录动作，不另摆阶段审批；审核、修订和合并授权边界不变。
- 禁止用“全部处置”“全绿”“可以合并”等聚合词取代逐项证据或独立合并授权。
- 页面样例、命令、代码定位等按需展开；不是每条回复强制填满表格。

## 5. 对现有脚本的有限修正

`spec-check` 仍只负责确定性文档/路径检查，不作为用户授权或语义范围的证明。

1. 给了 `--base`/`--diff` 且 diff 非空，但 spec 没有“改”清单时，E5 必须报错；不得以黄色跳过后让总结果退出 0。
2. “不改”路径优先于“改”里的宽目录或通配项；被列为不改的文件只要出现在 diff 中，E5 报错。
3. 保持脚本不假装识别同一文件里的业务语义越界、用户是否批准或执行顺序；这些通过会话行为测试检查。

## 6. 行为回放验收

在实现 PR 中保存输入、实际用户可见回复与工具操作轨迹；先做本地无副作用回放，再在可用的新鲜 Nano 与 Claude Code 会话验证。Pi 可用时加同组回放。模型无法调用、权限不足或成本未批准时如实记未验收，不用 grep 替代行为测试。

| ID | 场景 | 必须观察到的结果 | 验证方法 |
|---|---|---|---|
| AC-01 | 用户澄清“返回第一个字段”但未委托实施（#144） | 先完成规格确认；批准前没有代码写入 | 重放用户/assistant/工具顺序，核 first write |
| AC-02 | 用户委托完整 issue，含 3 个正常实施阶段（#911） | agent 可连续完成阶段；只在需求/范围停点暂停，不逐阶段问 | 新鲜会话回放 |
| AC-03 | 用户要求“最后弹审核档位”但未选择 | 显示审核卡；未记录用户选档不得自选派审 | 新鲜会话回放，核派发时序 |
| AC-04 | finding 被选择修订 | 修订前有用户处置选择；逐项落位/验证；合并前有独立合并授权 | 回放 #147 / #151 类流程 |
| AC-05 | 用户已明确同一对象动作（tag/同一目标） | 不重复问；若对象或最终版本已变，才重核对应许可 | 正反例回放 #143 |
| AC-06 | 审核提出闭环外需求或关键前提未定（#152） | 不把独立需求混为 defect；前提影响承诺时只停受影响项 | 用两类对照夹具回放 |
| AC-07 | 文件修改任务 | 默认自动从远端基线建立隔离 worktree，不先问用户 | 命令轨迹检查 |
| AC-08 | E5 缺改动范围 / 改与不改冲突 | 第一种报错；第二种只要禁改文件变化即报错 | 新增正反例测试 |
| AC-09 | 输出含实施或审核结论 | 第一屏包含状态、改哪里/怎么改/能力、未验证与下一步；逐条证据可展开 | 固定会话样例人工对照 |
| AC-10 | 评论与状态标签回填不丢且不变成额外闸 | 审核原结论、逐项处置、验收与收尾结果回填 PR/issue；已采用 `issue-status` 的状态转移同步更新标签；未采用项目不建标签；不因正常阶段回填重复请示 | 完整 issue 生命周期回放，核 PR/issue 评论与标签时间线 |
| AC-11 | 默认面与仓库文档健康不退化 | 现有预算、引用、README 双语检查通过 | `bash scripts/check-docs.sh` |
| AC-12 | 历史事实不冒充全局行为保证 | 至少保留每个会话样本的输入、期望、实际、限制；未跑项标未验 | 审阅实现 PR 验收附件 |

保留 `SKILL.md` ≤60 行、正文 ≤2,800 字符、常驻三份合计 ≤180 行的现行预算；只在原有段落中替换/压缩，不新增卡、步骤或 reference，不提高预算。README 不改则不触发双语联动。

### 自定细节

- 规格只包含流程文档和本仓既有脚本的确定性修正；不接入外部项目、不部署运行时拦截。
- 新鲜会话行为回放的具体样例与可用模型由实施时按当下安装能力记录；不把“未运行”写成通过。
- `--base` 为空 diff 时现有绿判据保留；新增错误针对“存在改动但未声明改动范围”。

## 9. 风险与代价

- Markdown 仍不是运行时强制；行为回放只覆盖代表性路径，不证明所有模型/会话都守流程。
- 明示审核与合并分开，会保留两次不同决策；不会因为“不要阶段性打扰”而合并两种许可。
- 评论与标签回填复用现有骨架和项目映射，不新增审批卡；未声明 `issue-status` 的项目不启用状态标签。
- 逐项处置证据增加少量报告工作，但目的是减少用户二次追问和反复审读全部 diff。
- E5 仍按路径而非语义检查；禁止将其宣传为“范围扩张已被机械拦截”。
- 不能从“无字段/无外键”直接推出功能不可实现；仍需事实核验与业务前提分类。
