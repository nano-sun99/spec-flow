# spec：方案交付与实施委托——跨 agent 的生命周期交接

- 日期：2026-10-24
- Issue：待开
- 状态：草案，待审核
- 决策人：用户
- 决策来源：用户明确要求方案 agent 与实施 agent 可以不同；方案完成后必须停止，只有用户另行发起实施才进入实施期
- 相关事故：dsh-tui-nano 最新会话在 spec PR 合并、执行 issue 创建后，未获得新的人工实施指令就认领 issue 并修改代码

## 1. 背景：现在缺的不是一道闸

当前主线写成「需求 → spec → issue → 实施」，同时把「spec 合并后开 issue」和「实施期认领 issue」连续排列。用户在方案期点过需求、机制、拆分、审核、修订或合并，并不等于把代码实施委托给当前 agent；但流程没有一个正式的交接状态，agent 容易把连续步骤理解成自动执行链。

这会在不同项目里表现不一致：有的会话用户一开始就说「做 #N」，实施入口确实成立；有的会话只有需求和方案确认，agent 却把「用户没叫停」当成实施授权。问题不是某个项目少了一句提醒，而是方案期和实施期之间没有定义责任边界、持久状态和进入条件。

本次不把修复做成一句「实施前再问一次」。那只是把断点塞进现有线性清单，仍然无法回答：谁交接、交什么、哪个 agent 接手、哪些用户选择只对方案期有效、issue 是否已代表实施授权、何时算方案 agent 结束。

## 2. 目标

1. 方案 agent 可以独立完成需求确认、spec、审核、修订、spec 合并和执行 issue 创建，然后明确结束本轮。
2. 方案完成后形成可被另一个 agent 消费的持久交接物，不依赖原会话上下文。
3. 只有用户针对具体 issue / spec 明确委托实施，流程才从方案交接态进入实施期。
4. 用户在方案期做出的选择只授权对应的方案动作，不向后自动扩展成代码实施授权。
5. 实施 agent 从交接物进入，重新读取项目规则、获批 spec、issue、ADR 和当前基线，能够独立开工。
6. 实施审核档位、实施合并和收尾仍是实施期自己的动作，不继承方案期的档位或授权。
7. dsh、taoxi_system、jasmine-lottery 等采用项目只需消费中央规则，不各自复制一套交接制度。

## 3. 非目标与反目标

- 不把所有用户选择都改成一次新的确认卡；本次重点是生命周期和责任边界，不增加无意义点击。
- 不禁止方案 agent 自动创建执行 issue；issue 是跨 agent 的交接载体，不是实施授权。
- 不要求方案 agent 和实施 agent 必须是不同实例；同一个 agent 也必须经过用户明确委托才能跨状态。
- 不改变需求确认、机制卡、拆分卡、审核卡、修订卡、合并卡各自的业务含义。
- 不把 issue 的 `open`、`未开始`、PR 已合并或用户没有反对解释成实施授权。
- 不建立中央项目采用名单、统一项目标签或运行时调度服务。
- 不通过 Hook、CI 或脚本伪造强制执行；spec-flow 仍是 agent 读取的流程协议，但协议必须足够明确、可持久交接和可审计。

## 4. 机制清单

| # | 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|---|
| 1 | **生命周期状态**：方案进行中、方案已定待实施、实施已授权、实施进行中、实施待审核、已完成 | 让流程拥有明确的阶段边界和责任归属 | 线性步骤会把“下一步”误读成“现在就执行” |
| 2 | **方案交接记录**：spec 合并后在执行 issue 中写固定的交接字段 | 让不同 agent 能从持久载体接力 | 新 agent 只能依赖旧会话摘要，或把 issue 当普通待办猜测 |
| 3 | **授权作用域**：每个用户选择绑定对象、动作和阶段，不自动向后传递 | 区分“修 spec / 合并 spec”和“改代码” | “改”“合并”“轻审”会被拼成一次泛化授权 |
| 4 | **明确实施委托**：用户针对具体 issue / spec 说“开始实施 #N”等才转态 | 把实施决定留给真正有权决定的人 | “你没叫停”会继续冒充“你同意了” |
| 5 | **跨 agent 接手协议**：实施 agent 按交接记录和获批材料重新建上下文 | 让方案 agent 与实施 agent 解耦 | 实施只能由原 agent 记住上下文，换人就丢边界 |

## 5. 生命周期模型

### 5.1 状态与责任

| 状态 | 谁负责 | 可做什么 | 不可做什么 | 离开条件 |
|---|---|---|---|---|
| `DESIGNING` 方案进行中 | 方案 agent | 调研、确认需求、写 spec、摆方案期卡 | 写代码、认领实施 worktree | 需求和结构已确认，进入 spec 交付 |
| `SPEC_REVIEW` spec 审核 / 修订 | 方案 agent + 用户 | 选审核档位、审核、贴结论、按用户选择修订 | 把审核选择当实施授权 | spec PR 按方案期规则合并或停止 |
| `SPEC_READY` 方案已定·待实施 | 方案 agent 已交付 | 自动创建执行 issue、写交接记录、报告结果 | 创建实施 worktree、改实施 issue 状态、改代码、派实施 agent、跑实施任务 | 用户明确实施委托；方案 agent 的本轮消息结束 |
| `IMPLEMENTATION_AUTHORIZED` 实施已授权 | 用户触发，实施 agent 接收 | 读取交接物、核项目规则和当前基线、准备认领 | 在授权对象不明时自行扩大范围 | 认领 issue 成功并进入 worktree |
| `IMPLEMENTING` 实施进行中 | 实施 agent | 认领锁、改代码、测试、开实施 PR | 越过 spec 范围或擅自改长期决定 | 实施 PR 形成并准备交付 |
| `DELIVERY_REVIEW` 实施待审核 | 实施 agent + 用户 | 摆当次实施审核卡、处理发现、合并确认 | 沿用方案期审核档或自动合并 | 实施 PR 合并或用户选择暂停 |
| `COMPLETED` 已完成 | 实施 agent | 回填验收、issue、ADR、状态并放锁 | 把未完成观察或已知阻断伪装成完成 | 当前交付收尾完成 |

状态名是流程协议的稳定语义；项目是否把它映射成标签、字段或正文小节，随项目体例，不由中央维护标签名单。

### 5.2 状态转移规则

```text
DESIGNING
  -> SPEC_REVIEW
  -> SPEC_READY
  -> IMPLEMENTATION_AUTHORIZED   [用户明确委托]
  -> IMPLEMENTING
  -> DELIVERY_REVIEW
  -> COMPLETED
```

- `SPEC_READY` 是方案期的正常终点，不是“等待 agent 自己继续”的中间休息点。
- `SPEC_READY` 可以自动创建执行 issue，但创建 issue 只是在持久化交接，不产生 `IMPLEMENTATION_AUTHORIZED`。
- 没有用户委托时，`SPEC_READY` 不得跳到任何实施状态；方案 agent 应在交接报告后停止当前回合。
- 用户明确要求修改 spec、重新审核、调整拆分或关闭 issue 时，仍留在方案交接侧处理，不把这些话解释成实施授权。
- 用户说“继续”但未指明具体实施对象时，先确认对象和动作，不实施。
- 用户说“开始实施 #N”“按 #N 开工”“请做 #N”等明确绑定 issue 的话，可触发 `IMPLEMENTATION_AUTHORIZED`；具体语义变体按同一意图识别。
- “方案合并了”“改不改”“审核选轻审”“继续看看”“你没叫停”等话，不单独触发实施状态。

### 5.3 方案期 PR 与审核顺序

方案期审核必须有一个可持久评论的 PR 作为落点，顺序固定为：

1. 方案 agent 完成 spec 草案并开 spec PR；此时 PR 可以是待审核状态，尚未合并。
2. 用户选择 spec 审核档位后，审核结论原样贴到该 PR 的评论中；不另造只存在于聊天里的审核结论。
3. 审核有发现时，摆修订卡；用户选择“改”后在同一 PR 修订 spec，并把处置记录写进 spec；选择“不改”则不合并。
4. 方案 PR 合并后，才创建执行 issue 并写入 `SPEC_READY` 交接区。

“开 PR”是为了给审核建立持久落点，不代表 spec 已获批，也不代表实施已授权；“合并 spec PR”只结束方案期，不触发实施期。

## 6. 方案交接物

### 6.1 执行 issue 的固定交接区

方案 PR 合并后自动创建执行 issue，正文包含以下最小区块；项目自有 issue 体例可以扩展，但不能删除这五项的语义：

```markdown
## spec-flow 交接

- 流程状态：`SPEC_READY`
- 实施授权：`待用户明确委托`
- Spec：<合并后的永久链接>
- 方案 PR：<永久链接>
- 上游 / ADR：<链接或“无”>

### 实施范围
- 做什么：<获批范围>
- 不做什么：<明确排除项>
- 验收入口：<spec 验收节 / 证据要求>
- 已知限制：<未决、风险、未纳入项>

### 接手条件
- 实施前必读：项目 `AGENTS.md` / `CLAUDE.md`、获批 spec、现行 ADR（如项目已采用）、本 issue。
- 开工命令：用户必须明确绑定具体 issue，例如“开始实施 #N”；只有候选唯一也不能省略 issue 号。
- 当前状态：未创建实施 worktree，未修改实施代码。
- 授权记录：收到明确委托后，先把授权对象、用户原话和时间写回本 issue，再认领 worktree；这一步是机械留痕，不再向用户追加确认。
```

`SPEC_READY` 与“待用户明确委托”必须同时出现，避免只有一个标签或自然语言标题被误读。Issue 的 `open`、标签“未开始”和 worktree 是否存在分别表达不同事实，不能互相替代。

### 6.2 方案 agent 的最终交接报告

方案 agent 在 spec PR 合并、issue 创建和交接区写入完成后，只输出一次交接报告：

```text
方案阶段已完成，实施尚未授权。

Spec：<永久链接>
执行 issue：#N（未开始）
本次方案覆盖：<一行范围>
实施授权：待用户明确委托

下一步：如需实施，请明确说“开始实施 #N”。收到前我不会创建 worktree、修改代码或派实施 agent。
```

这条消息是方案 agent 的责任终点。报告之后不得继续调用工具做实施准备；不得用“我先看看代码”“我先建 worktree”“我先跑测试”绕过状态转移。

## 7. 授权作用域

### 7.1 方案卡的权限表

| 用户动作 | 授权对象 | 明确不包含 |
|---|---|---|
| 需求 / 机制 / 拆分选择 | 当前方案如何定义 | 写代码或认领 issue |
| 审核档位选择 | 当前交付物的审核成本和路线 | 采纳审核发现、实施审核或代码修改 |
| 修订卡选择“改” | 把审核发现纳入当前 spec 修订 | 实施 spec 里的代码范围 |
| spec 合并卡 | 当前 spec / 文档 PR 的合并 | 实施 issue 的认领与代码改动 |
| “自动开 issue”方案选择 | 创建交接用执行 issue | 开工、改 issue 为进行中、改代码 |
| “开始实施 #N” | 指定 issue 的实施阶段；随后授权记录写回该 issue | 超出 spec 的范围、生产发布或其他 issue |

### 7.2 授权不向后传递

每个用户回答只解决它对应的那一个问题。agent 可以基于已授权动作继续完成该动作的必要机械步骤，但不能把一次授权扩张到下一阶段。尤其是：

- “改 spec”不等于“按 spec 改代码”；
- “合并 spec”不等于“合并实施 PR”；
- “轻审”不等于“实施也轻审”；
- “开 issue”不等于“认领 issue”；
- “用户没反对”不等于“用户已委托”。

## 8. 跨 agent 接手协议

实施 agent 收到明确委托后，按以下顺序进入实施期：

1. 解析用户明确指向的 issue；实施授权必须绑定具体 `#N`，不能用“开始实施”或“继续”猜当前对象；如果 issue 不存在、对象不唯一或用户指向的不是 `SPEC_READY`，先停下确认。
2. 读取项目 `AGENTS.md` / `CLAUDE.md`，确认项目体例、已采用制度和工作区边界。
3. 读取 issue 的 `spec-flow 交接` 区、获批 spec、相关 ADR 和当前项目事实；不能只读用户转述。
4. 核对 issue 仍为 `SPEC_READY` / 未开始，spec 链接仍指向合并版本，实施范围没有被悄悄改写。
5. 在 issue 追加机械授权记录，再将流程状态更新为 `IMPLEMENTATION_AUTHORIZED`。记录至少包含：授权对象 `#N`、用户明确委托的原话、授权时间；不扩写用户没有授权的范围。
6. 从远端基线获取并认领 `issue-<N>` worktree；锁失败就按现有 worktree 规则停下。
7. 进入 `IMPLEMENTING` 后，才允许读写实施代码和测试；任何新长期决定、范围变化或 spec 事实错误，回到既有修订 / 改旧 spec / ADR 规则，不自行吞掉。

授权记录的最小形态为：

```markdown
- 流程状态：`IMPLEMENTATION_AUTHORIZED`
- 实施授权：用户明确委托实施 `#N`
- 授权原话：<用户原话>
- 授权时间：<记录时间>
```

如果交接区缺失、状态与 issue 标签冲突、spec 尚未合并或用户委托没有绑定对象，实施 agent 不能用“看起来应该可以”补齐授权；应报告缺口并停在交接态。

## 9. 对现有卡片和两段流程的整合

本次不是给现有卡片旁边再贴一个孤立的“实施确认”补丁，而是改变卡片的归属：

- 方案期卡片仍位于方案期，回答的是方案内部决策。
- `SPEC_READY` 是方案期的正式完成态，交接记录是段一到段二的产物。
- 实施期不从“方案期最后一个卡片的后续步骤”自动开始，而是从用户明确委托重新进入段二。
- 实施审核卡仍是每份实施交付物合并前的独立卡；方案期审核档不继承。
- “合并卡”只授权当下被点名的 PR 合并，不能覆盖后续交付物。
- 例外“直接干 / 免方案期”只影响是否出 spec 和开 issue；如果最终产生实施成果，仍然需要明确实施对象和实施期交付规则。

README 的流程图和 `SKILL.md` 主线应改成：

```text
需求确认
  -> 方案交付（spec 审核、修订、合并、开 issue）
  -> SPEC_READY：交接并停止
  -> 用户明确实施委托
  -> 实施交付（认领、代码、实施审核、合并、回填）
```

## 11. 验收标准

- [ ] 方案主线明确经过 `SPEC_READY`，不是 `spec 合并 → 自动实施`。
- [ ] spec 合并后可自动创建执行 issue，但 issue 交接区明确写出“实施授权待用户明确委托”。
- [ ] 方案 agent 的最终报告明确列出 spec、issue、范围、授权状态和开工命令。
- [ ] 交接报告之后没有任何实施工具动作：不建 worktree、不改 issue 为进行中、不改代码、不派实施 agent。
- [ ] “改 spec”“合并 spec”“轻审”“开 issue”等方案期回答不会被定义成实施授权。
- [ ] “开始实施 #N”及等价明确表达可以进入实施期，但必须绑定具体 issue；无 issue、对象不唯一、spec 未合并或状态不是 `SPEC_READY` 时必须停下确认。
- [ ] 实施 agent 在认领 worktree 前把授权对象、用户原话和时间写回 issue，并把状态更新为 `IMPLEMENTATION_AUTHORIZED`；这条记录不扩大授权范围。
- [ ] 实施 agent 能只凭 issue 交接区、获批 spec、项目规则、ADR 和当前基线建立上下文，不依赖方案会话记忆。
- [ ] 实施审核档位重新选择，不能继承方案审核档位。
- [ ] dsh、taoxi_system、jasmine-lottery 不需要增加项目级重复规则即可得到相同状态语义。
- [ ] README 中英文同步描述“方案交付后停止、用户委托后实施”。
- [ ] `scripts/check-docs.sh` 通过，且没有把交接规则藏入 frontmatter、第二份常驻正文或项目采用名单。
- [ ] 至少用三类会话演练：同 agent 方案后停止、不同 agent 按 issue 接手、用户未授权时 agent 尝试继续；第三类必须停在 `SPEC_READY`。

## 12. 自定细节

| # | 自定细节 | 理由 |
|---|---|---|
| D1 | 方案 agent 自动创建执行 issue，状态保持项目默认的“未开始” | 用户已选择；跨 agent 接力需要稳定载体，issue 不等于授权 |
| D2 | 状态采用稳定语义名 `SPEC_READY`、`IMPLEMENTATION_AUTHORIZED` 等，项目标签不由中央统一 | issue 标签体系属于项目体例，中央只规定事实语义 |
| D3 | 交接记录放执行 issue，而不是新建全局台账 | issue 已是 spec 永久链接和实施跟踪的既有载体，减少第二份状态源 |
| D4 | 实施授权必须绑定具体 issue，允许自然语言表达但不要求固定逐字口令 | 跨 agent 交接不能靠当前上下文猜对象；“开始实施 #N”是推荐表达，语义等价表达可识别 |
| D5 | 无对象的“继续”不自动实施，必要时回问具体 issue | 模糊表达不能承担跨 agent 的代码委托 |
| D6 | 方案 agent 的停止点发生在交接报告之后，即使同一个 Claude 会话仍然存在 | 防止连续步骤、工具队列或“顺手检查”绕过责任边界 |
| D7 | 不新增独立实施授权卡作为默认流程步骤 | 用户要求自然提示后自行开工；授权是状态转移事件，不是又一张方案成本卡 |
| D8 | `SPEC_READY` 的交接区允许项目自有字段扩展，但不允许删掉授权状态、spec、范围和接手条件 | 兼容项目体例，又保证跨 agent 的最小信息完整 |
| D9 | 本 spec 先作为单份中央规则交付，不拆成“状态模型”和“交接模板”两份 | 用户已选择不拆；两者必须同步演化，拆开会产生协议版本错配 |
| D10 | 用户授权后先向 issue 写入 `IMPLEMENTATION_AUTHORIZED`、原话和时间，再认领 worktree；方案期审核档位和审核结论继续由 spec / PR 链接承载，不另造授权台账 | 授权需要跨会话可查，但不应为审核信息制造第二份正文 |
| D11 | 方案 agent 首次交接报告必须给出具体 issue 和固定开工命令 | 让用户知道下一步如何委托，避免“方案好了”再次被解释成自动开工 |
