## 1. 背景：现在缺的不是一道闸

当前主线写成「需求 → spec → issue → 实施」，同时把「spec 合并后开 issue」和「实施期认领 issue」连续排列。用户在方案期点过需求、机制、拆分、审核、修订或合并，并不等于把代码实施委托给当前 agent；但流程没有一个正式的交接状态，agent 容易把连续步骤理解成自动执行链。

这会在不同项目里表现不一致：有的会话用户一开始就说「做 #N」，实施入口确实成立；有的会话只有需求和方案确认，agent 却把「用户没叫停」当成实施授权。问题不是某个项目少了一句提醒，而是进入条件只定义了「认领」，没有定义「用户是否授权实施」；方案期与实施期之间也没有正式的交接状态。

本次不把修复做成一句「实施前再问一次」。那只是把断点塞进现有线性清单，仍然无法回答：谁交接、交什么、哪个 agent 接手、哪些用户选择只对方案期有效、issue 是否已代表实施授权、何时算方案 agent 结束。

本协议不取消两条既有入口：用户对已有 issue 说「做 #N」仍可直接进段二；「直接干 / 别走流程」仍免方案期。两者见 §5.2.1、§5.2.2。

## 2. 目标

1. 方案 agent 可以独立完成需求确认、spec、审核、修订、spec 合并和执行 issue 创建，然后明确结束本轮。
2. 方案完成后形成可被另一个 agent 消费的持久交接物，不依赖原会话上下文。
3. 只有用户针对具体 issue 明确委托实施，流程才从方案交接态进入实施期。
4. 用户在方案期做出的选择只授权对应的方案动作，不向后自动扩展成代码实施授权。
5. 实施 agent 从交接物进入，重新读取项目规则、获批 spec、issue、ADR 和当前基线，能够独立开工。
6. 实施审核档位、实施合并和收尾仍是实施期自己的动作，不继承方案期的档位或授权。
7. 中央规则不复制到下游项目；项目体例差异由项目自己的指令承载，本仓不维护采用名单。

## 3. 非目标与反目标

- 不把所有用户选择都改成一次新的确认卡；本次重点是生命周期和责任边界，不增加无意义点击。
- 不禁止方案 agent 在结构决定已作出后自动创建执行 issue；issue 是跨 agent 的交接载体，不是实施授权。
- 不要求方案 agent 和实施 agent 必须是不同实例；同一个 agent 也必须经过用户明确委托才能跨状态。
- 不取消既有 issue 的「做 #N」入口；没有交接区的既有 issue 仍按原段二入口进入，见 §5.2.1。
- 不取消「直接干 / 别走流程」的免方案期豁免；该路径由用户当场指令授权，不需要 #N 或交接区，见 §5.2.2。
- 不改变需求确认、机制卡、拆分卡、审核卡、修订卡、合并卡各自的业务含义。
- 不把 issue 的 `open`、项目自有的未开始状态（若采用 `issue-status` 备忘录）、PR 已合并或用户没有反对解释成实施授权。
- 不建立中央项目采用名单、统一项目标签或运行时调度服务。
- 不通过 Hook、CI 或脚本伪造强制执行；spec-flow 仍是 agent 读取的流程协议，但协议必须足够明确、可持久交接和可审计。

## 4. 机制清单

| # | 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|---|
| 1 | **生命周期状态**：`DESIGNING`、`SPEC_REVIEW`、`SPEC_READY`、`IMPLEMENTATION_AUTHORIZED`、`IMPLEMENTING`、`DELIVERY_REVIEW`、`PAUSED`、`CANCELLED`、`COMPLETED` | 让流程拥有明确的阶段边界和责任归属 | 线性步骤会把“下一步”误读成“现在就执行” |
| 2 | **方案交接记录**：spec 合并后在执行 issue 中写固定的交接字段 | 让不同 agent 能从持久载体接力 | 新 agent 只能依赖旧会话摘要，或把 issue 当普通待办猜测 |
| 3 | **授权作用域**：每个用户选择绑定对象、动作和阶段，不自动向后传递 | 区分“修 spec / 合并 spec”和“改代码” | “改”“合并”“轻审”会被拼成一次泛化授权 |
| 4 | **明确实施委托**：用户针对具体 issue 说“开始实施 #N”等才转态；PR 号不触发 | 把实施决定留给真正有权决定的人 | “你没叫停”会继续冒充“你同意了” |
| 5 | **跨 agent 接手协议**：实施 agent 按交接记录和获批材料重新建上下文 | 让方案 agent 与实施 agent 解耦 | 实施只能由原 agent 记住上下文，换人就丢边界 |
| 6 | **方案 agent 交接报告与停止点**：报告列出 spec、issue、范围、授权状态和开工命令，之后不再做实施准备 | 给方案期一个可判定的责任终点 | 报告之后还会“顺手看看代码”“先建 worktree” |
| 7 | **机械授权记录**：认领前把授权对象、用户原话、时间、范围写回 issue | 让跨会话授权可查、可审计 | 授权只存在聊天里，换 agent 后无据可查 |

## 5. 生命周期模型

### 5.1 状态与责任

| 状态 | 谁负责 | 可做什么 | 不可做什么 | 离开条件 |
|---|---|---|---|---|
| `DESIGNING` 方案进行中 | 方案 agent | 调研、确认需求、用户点头后写 spec、摆方案期卡 | 写代码、认领实施 worktree | 用户点头且草案成形 → `SPEC_REVIEW` |
| `SPEC_REVIEW` spec 审核 / 修订 | 方案 agent + 用户 | 选审核档位、审核、贴结论、按用户选择修订 | 把审核选择当实施授权 | spec PR 合并 → `SPEC_READY`；用户关闭 → `CANCELLED`；继续修订 → 自环 |
| `SPEC_READY` 方案已定·待实施 | 方案 agent 已交付 | 创建执行 issue、写交接区（含流程状态字段）、报告结果、按用户指令关闭 issue | 创建实施 worktree、改代码、派实施 agent、跑实施任务；未经用户指令改 issue 生命周期状态或实施阶段标签 | 用户明确委托 → `IMPLEMENTATION_AUTHORIZED`；用户要求返修 / 重审 → `SPEC_REVIEW`；用户关闭 → `CANCELLED` |
| `IMPLEMENTATION_AUTHORIZED` 实施已授权 | 用户触发，实施 agent 接收 | 读取交接物、核项目规则和当前基线、写授权记录、准备认领 | 在授权对象不明时自行扩大范围 | 认领成功 → `IMPLEMENTING`；认领失败或用户撤销 → `SPEC_READY` |
| `IMPLEMENTING` 实施进行中 | 实施 agent | 认领锁、读写代码、测试、开实施 PR | 越过授权范围或擅自改长期决定 | 实施 PR 形成 → `DELIVERY_REVIEW`；用户暂停或范围变化待决 → `PAUSED` |
| `DELIVERY_REVIEW` 实施待审核 | 实施 agent + 用户 | 摆当次实施审核卡、处理发现、合并确认 | 沿用方案期审核档或自动合并 | 实施 PR 合并并回填 → `COMPLETED`；用户暂停 → `PAUSED` |
| `PAUSED` 已暂停 | 用户 + 当前 agent | 报告暂停事实、保留或按用户指令释放锁、记录恢复条件 | 未经用户恢复就继续实施、悄悄关单 | 用户恢复 → 回到暂停前的实施状态；用户取消 → `CANCELLED` |
| `CANCELLED` 已取消 | 用户 + 当前 agent | 记录取消原因、按既有规则释放 worktree 锁 | 继续实施或把取消伪装成完成 | 用户重新打开 → `SPEC_REVIEW` 或 `SPEC_READY` |
| `COMPLETED` 已完成 | 实施 agent | 回填验收、issue、ADR、状态并放锁 | 把未完成观察或已知阻断伪装成完成 | 当前交付收尾完成 |

状态名是流程协议的稳定语义；项目是否把它映射成标签、字段或正文小节，随项目体例，不由中央维护标签名单。`SPEC_READY` 与「交接态」同义，正文统一用 `SPEC_READY`。

「方案 agent 的本轮消息结束」不是状态转移，而是 `SPEC_READY` 下的责任终点；它不改变状态，也不解除用户后续委托的入口。

### 5.2 状态转移规则

```text
DESIGNING
  -> SPEC_REVIEW
SPEC_REVIEW
  -> SPEC_READY          [spec PR 合并]
  -> CANCELLED           [用户关闭]
  -> SPEC_REVIEW         [继续修订]
SPEC_READY
  -> IMPLEMENTATION_AUTHORIZED   [用户明确委托具体 issue]
  -> SPEC_REVIEW                 [用户要求返修 / 重审]
  -> CANCELLED                   [用户关闭执行 issue]
IMPLEMENTATION_AUTHORIZED
  -> IMPLEMENTING        [认领成功]
  -> SPEC_READY          [认领失败 / 用户撤销]
IMPLEMENTING
  -> DELIVERY_REVIEW     [实施 PR 形成]
  -> PAUSED              [用户暂停 / 范围变化待决]
DELIVERY_REVIEW
  -> COMPLETED           [实施 PR 合并并回填]
  -> PAUSED              [用户暂停]
PAUSED
  -> IMPLEMENTING / SPEC_READY   [用户恢复]
  -> CANCELLED                   [用户取消]
```

- `SPEC_READY` 是方案期的正常终点，不是“等待 agent 自己继续”的中间休息点。
- `SPEC_READY` 只对「结构已定、拆分卡已答」的执行 issue 自动创建交接载体；创建 issue 只是在持久化交接，不产生 `IMPLEMENTATION_AUTHORIZED`。创建失败时报告失败并停在 `SPEC_REVIEW`，不得在没有交接载体时自称 `SPEC_READY`。
- 没有用户委托时，`SPEC_READY` 不得跳到任何实施状态；方案 agent 应在交接报告后停止当前回合。
- 用户明确要求修改 spec、重新审核、调整拆分或关闭 issue 时，仍留在方案交接侧处理，不把这些话解释成实施授权。若 spec 已合并，先按「改旧 spec 卡」处理；旧的执行 issue 按用户指令关闭，返修合并后重新创建交接 issue。
- 用户说“继续”但未指明具体实施对象时，先确认对象和动作，不实施。
- “方案合并了”“改不改”“审核选轻审”“继续看看”“你没叫停”等话，不单独触发实施状态。

#### 5.2.1 既有 issue 入口

没有 `spec-flow 交接` 区的既有 issue 不因本协议失效：

- 用户明确说“做 #N”“开始实施 #N”等，即构成对该 issue 的实施委托；不要求它曾处于 `SPEC_READY`。
- 实施 agent 仍按 §8 读取项目规则、issue、获批 spec 和当前基线；若 issue 没有交接区，授权记录以 issue 评论形式追加（项目允许改正文时也可追加到正文），内容至少包含授权对象、用户原话、时间、范围。
- 既有 issue 若已有交接区且状态为 `SPEC_READY`，走 §8 的完整协议；若交接区存在但状态不是 `SPEC_READY`，先停下确认，不自行补齐。

#### 5.2.2 免方案期路径

用户说“直接干 / 别走流程”，或改动属于改一行、纯查事实时：

- 不产生 spec、执行 issue 或 `SPEC_READY` 交接物；用户的当场指令即实施授权，作用域是被点名的任务。
- 不需要 `#N`，也不需要交接区；若开 worktree，按 `references/worktree-lock.md` 的「没有 issue 号的活」执行，无锁可领。
- 实施成果交付前仍照摆闸卡，交付与回填规则不变。

#### 5.2.3 授权识别

- 实施授权的对象必须解析为 issue。PR 号（即使与 issue 共用编号）不触发实施状态；用户说“请做 #112”而 #112 是 PR 时，先确认是不是指某张 issue。
- 用户说“开始实施 #N”“按 #N 开工”“请做 #N”等明确绑定 issue 的话，可触发 `IMPLEMENTATION_AUTHORIZED`；语义等价表达必须同样带 issue 号。
- 未出现 issue 号的“继续”“就按这个做”“开始吧”，一律先确认对象，不自动进入实施。
- “只有候选唯一”不能替代 issue 号；候选唯一但用户没点名时，仍回问具体 `#N`。

#### 5.2.4 返修、撤销、接管与范围变化

- **返修 / 重审**：`SPEC_READY` 或实施前发现 spec 需要改，回到方案侧；已合并 spec 先走改旧 spec 卡，旧交接 issue 按用户指令关闭或标记失效，返修合并后重新交接。
- **撤销**：用户授权后反悔，进入 `PAUSED` 或按用户指令回到 `SPEC_READY`；已认领的 worktree 按 `references/worktree-lock.md` 放锁，issue 状态同步记录，不把撤销伪装成完成。
- **接管**：前一个 agent 已写授权记录但锁已失效（目录不在、分支可复用）时，新 agent 必须在用户明确授权后按 `references/worktree-lock.md` 的接手规则操作，并追加接管记录（新授权原话、时间、旧记录链接）；不得把旧授权直接当作新授权。
- **范围变化**：用户在授权时缩小范围（例如“只做 #N 的文档部分”），授权记录必须写明本次范围，交接区的「实施范围」仍是 spec 全量；两者不一致时以更窄的授权为准。范围扩大到 spec 之外，暂停受影响实施，按改旧 spec 卡 / 新 spec 处理。

### 5.3 方案期 PR 与审核顺序

方案期审核优先有一个可持久评论的 PR 作为落点，顺序固定为：

1. 方案 agent 完成 spec 草案并开 spec PR；此时 PR 可以是待审核状态，尚未合并。确实没有 PR 可走时，保留 `references/gate-details.md` 的对话兜底，不另造第三套落点。
2. 用户选择 spec 审核档位后：轻审 / 重审 / 重审 + 变异把审核结论原样贴到该 PR 的评论；「不审」档不产生审核结论，也不写免责声明。
3. 审核有发现时，摆修订卡；用户选择“改”后在同一 PR 修订 spec，并把处置记录写进 spec 末尾「审核修订记录」；选择“不改”或没答，不合并。
4. 方案 PR 合并后，才创建执行 issue 并写入 `SPEC_READY` 交接区。

“开 PR”是为了给审核建立持久落点，不代表 spec 已获批，也不代表实施已授权；“合并 spec PR”只结束方案期，不触发实施期。

## 6. 方案交接物

### 6.1 执行 issue 的固定交接区

方案 PR 合并后，对每张执行 issue 自动创建交接区。必填字段只有下面一张表；§12 的自定细节与本节冲突时，以本表为准：

| 字段 | 必填 | 谁写 / 更新 |
|---|---|---|
| 流程状态 | 是 | 方案 agent 写 `SPEC_READY`；实施 agent 认领前改为 `IMPLEMENTATION_AUTHORIZED` |
| 实施授权 | 是 | 方案 agent 写「待用户明确委托」；实施 agent 写授权对象 |
| Spec | 是 | 方案 agent 写合并后的永久链接 |
| 方案 PR | 是 | 方案 agent 写永久链接 |
| 上游 / ADR | 是 | 方案 agent 按项目规则写；默认见 spec 上游节，一跳可达，项目规定 issue 只链 spec 时不直链 |
| 实施范围 | 是 | 方案 agent 写做什么 / 不做什么 / 验收入口 / 已知限制 |
| 接手条件 | 是 | 方案 agent 写必读材料、开工命令、当前状态；实施 agent 更新当前状态 |
| 授权记录 | 认领前必填 | 实施 agent 追加；只追加，不改历史 |

模板：

```markdown
## spec-flow 交接

- 流程状态：`SPEC_READY`
- 实施授权：`待用户明确委托`
- Spec：<合并后的永久链接>
- 方案 PR：<永久链接>
- 上游 / ADR：<按项目规则；无则写“无”>

### 实施范围
- 做什么：<获批范围；建议用 spec 章节锚或逐字摘录，不写自由发挥的摘要>
- 不做什么：<明确排除项>
- 验收入口：<spec 验收节 / 证据要求>
- 已知限制：<未决、风险、未纳入项>

### 接手条件
- 实施前必读：项目 `AGENTS.md` / `CLAUDE.md`、获批 spec、现行 ADR（如项目已采用）、本 issue。
- 开工命令：用户必须明确绑定具体 issue，例如“开始实施 #N”；只有候选唯一也不能省略 issue 号。
- 当前状态：未创建实施 worktree，未修改实施代码。
- 授权记录：收到明确委托后，先把授权对象、用户原话、时间、范围写回本 issue，再认领 worktree；这一步是机械留痕，不再向用户追加确认。
```

- `SPEC_READY` 与“待用户明确委托”必须同时出现，避免只有一个标签或自然语言标题被误读。
- Issue 的 `open` / `closed`、项目标签（如采用 `issue-status` 的“未开始”）和 worktree 是否存在分别表达不同事实，不能互相替代。未采用 `issue-status` 的项目不假设存在“未开始”标签。
- 拆分组里每张执行 issue 各有自己的交接区；父 / 总览 issue 只跟踪，不进入状态机，不写实施交接区，也不被认领为执行任务。
- 既有 issue 没有交接区时，不要求补造 `SPEC_READY`；按 §5.2.1 用评论记录授权。

### 6.2 方案 agent 的最终交接报告

方案 agent 在 spec PR 合并、issue 创建和交接区写入完成后，只输出一次交接报告：

```text
方案阶段已完成，实施尚未授权。

Spec：<永久链接>
执行 issue：#N、#M（项目默认状态）
本次方案覆盖：<一行范围>
实施授权：待用户明确委托

下一步：如需实施，请明确说“开始实施 #N”。收到前我不会创建 worktree、修改代码或派实施 agent。
```

这条消息是方案 agent 的责任终点。报告之后不得继续调用工具做实施准备：不建 worktree、不写代码、不跑实施测试、不改 issue 为进行中、不派实施 agent。用户追问 spec 与现状的差异时，可以只读查看代码 / diff 并回答，但不得把只读检查扩展成实施准备。

## 7. 授权作用域

### 7.1 方案卡的权限表

| 用户动作 | 授权对象 | 明确不包含 |
|---|---|---|
| 需求 / 机制 / 拆分选择 | 当前方案如何定义 | 写代码或认领 issue |
| 审核档位选择 | 当前交付物的审核成本和路线 | 采纳审核发现、实施审核或代码修改 |
| 修订卡选择“改” | 把审核发现纳入当前 spec 修订 | 实施 spec 里的代码范围 |
| spec / 文档 PR 合并 | 该 PR 的合并；只含 spec / 文档的 PR 按豁免总表长期授权，用户当场点合并卡也只授权该 PR | 实施 issue 的认领与代码改动 |
| “自动开 issue”方案选择 | 创建交接用执行 issue | 开工、改 issue 为进行中、改代码 |
| “开始实施 #N” | 指定 issue 的实施阶段；随后授权记录写回该 issue | 超出 spec 或授权记录中更窄范围的部分、生产发布或其他 issue |

### 7.2 授权不向后传递

每个用户回答只解决它对应的那一个问题。agent 可以基于已授权动作继续完成该动作的必要机械步骤，但不能把一次授权扩张到下一阶段。尤其是：

- “改 spec”不等于“按 spec 改代码”；
- “合并 spec”不等于“合并实施 PR”；
- “轻审”不等于“实施也轻审”；
- “开 issue”不等于“认领 issue”；
- “用户没反对”不等于“用户已委托”。

## 8. 跨 agent 接手协议

实施 agent 收到明确委托后，按以下顺序进入实施期：

1. **解析对象**：用户指向的必须是 issue；PR 号不触发实施。交接 issue 必须处于 `SPEC_READY` 且 open；没有交接区的既有 issue 按 §5.2.1 处理。对象不存在、不唯一、不符合上述条件时，先停下确认，不猜。
2. **读项目规则**：读项目 `AGENTS.md` / `CLAUDE.md`，确认项目体例、已采用制度和工作区边界。
3. **读交接材料**：读 issue 的 `spec-flow 交接` 区（或既有 issue 的正文 / 评论）、获批 spec、相关 ADR 和当前项目事实；不能只读用户转述。合并后的 spec 是范围与验收的唯一权威。
4. **核事实**：核对 issue 仍 open、spec 链接仍指向合并版本、交接区的实施范围与 spec 一致（章节锚或逐字摘录对得上）。实际运行 `git worktree list`、`git branch --list 'issue-<N>'`、`git status`，把结果写进授权记录；不能只相信交接区里「未创建 worktree」这句自述。
5. **写授权记录**：交接 issue 在正文「授权记录」小节追加，并把流程状态改为 `IMPLEMENTATION_AUTHORIZED`；既有 issue 无交接区时，追加为 issue 评论（项目允许改正文时也可写正文）。记录至少包含：授权对象 `#N`、用户原话、授权时间、本次范围。只追加，不改历史；不扩写用户没有授权的范围。
6. **认领 worktree**：从远端基线获取并认领 `issue-<N>`；锁失败按 `references/worktree-lock.md` 停下，接手前必须有用户明确授权并追加接管记录。
7. **进入 `IMPLEMENTING`**：此后才允许写实施代码和测试。任何新长期决定、范围变化或 spec 事实错误，暂停受影响实施，按改旧 spec 卡 / 新 spec / ADR 规则处理，不自行吞掉。

授权记录的最小形态为：

```markdown
### 授权记录

- 流程状态：`IMPLEMENTATION_AUTHORIZED`
- 实施授权：用户明确委托实施 `#N`
- 授权原话：<用户原话>
- 授权时间：<记录时间>
- 本次范围：<spec 全量 / 用户明确缩小的范围>
- 基线核对：`git worktree list` / `git branch --list 'issue-N'` / `git status` 的结果摘要
```

**状态冲突判定**：交接区的 `流程状态` 是唯一权威；项目标签、issue 评论、旧摘要都只是辅助。若正文 `流程状态` 与项目标签或评论不一致，停下报告，不自行选一个继续。采用 `issue-status` 备忘录的项目按下表映射；未采用的项目只核正文状态，不假设标签存在：

| 流程状态 | 项目阶段标签（若采用） |
|---|---|
| `SPEC_READY` | 未开始 |
| `IMPLEMENTATION_AUTHORIZED` | 未开始（授权已记录、尚未认领） |
| `IMPLEMENTING` | 进行中 |
| `DELIVERY_REVIEW` | 待测试 / 待上线（按项目测试环境） |
| `COMPLETED` | 按备忘录的上线分拣与关单规则 |

如果交接区缺失、issue 已关闭、spec 尚未合并、用户委托没有绑定对象或状态与标签冲突，实施 agent 不能用“看起来应该可以”补齐授权；应报告缺口并停在交接态。
