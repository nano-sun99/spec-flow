## 1. 背景：spec 不是不够长，是长错了地方

现行段一是「需求 → spec → PR 过闸」。它假定 spec 一落笔就已经是对的形状，缺两个东西：

1. 没有「主流程先成形」这一步，规则和流程在 spec 正文里边写边发现；
2. 没有「设计稿 / 契约样例先当靶子」这一步，spec 里的界面、数据、状态没有可对照物。

#608 是反面样本：46 条评论、一份 spec 39 次提交、一次「合并 → revert → 重开」；主 spec 810 行，另有 551 行咨询 spec 和 476 行前端 spec、32 条 ADR；09-30 开单，10-29 才写第一行代码；四波实施 PR 的代码评审发现 30 / 33 / 23+ / 22 条；主 spec 110 个验收框仍是未勾。问题不是没写 spec，是 spec 成了「规则谈判记录」。

#159 是正面样本：设计样稿先有 146 项浏览器检查 / 0 fail，spec 308 行、38 条 `file:line` 证据、9 条非目标、13 条验收；spec 期 29 条发现（1 高 / 12 中 / 16 低）在写代码前改掉，实施期只剩 8 条（1 高 / 3 中 / 4 低）；spec 合并到发版 77 分钟。它赢在顺序：设计稿先当靶子，spec 再写成合同，代码最后。

结论：把 spec 当成一份会「长大」的文档，而不是一次写完的判决书。同一份 spec 走骨架 → 对照 → 实施版；有页面用设计稿对照，无页面用契约样例对照；只有实施版过闸。

## 2. 调研

| 说法 | 出处 | 对本 spec 的含义 |
|---|---|---|
| spec 是行为合同；spec → plan → tasks → implement；每一步验收后才走下一步 | [GitHub Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) | spec 先于代码，但不能一次写死；要有阶段验收 |
| design doc 写代码前写，讲目标 / 非目标 / 权衡，原型链接代替代码；大改不可能时才开工 | [Google design doc](https://www.industrialempathy.com/posts/design-docs-at-google/) | 设计稿是判断物，不是装饰；它先于实施版 spec |
| shaping 要「粗、已解、有边界」；太具体的线框限制创造力，太抽象的文字没有边界；固定胃口，明确不做什么 | [Shape Up](https://basecamp.com/shapeup/1.1-chapter-02) | 先出骨架，不先画高保真；非目标是一等公民 |
| 一条 ADR 一个决定；proposed → accepted → superseded；写 ADR 本身能逼出共识 | [Fowler ADR](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html) | 决策进 ADR，spec 正文只留当前真相 |

四者共同指向同一顺序：先定问题和边界 → 用粗样稿对齐 → 再写可执行合同 → 最后切片实施。没有一条支持「先写 810 行 spec，再等业务改口」。

## 3. 目标与非目标

### 目标

- **一份 spec，三个阶段**：骨架版 → 对照版 → 实施版；同一个文件、同一个 PR，不是三份文档。
- **先判页面**：有页面走「骨架 → Draft PR → 等设计稿 → 对照 → 实施版」；无页面走「技术骨架 → 3 个例子 / 1 张表 → 契约样例 → 实施版」。
- **对照先行**：四列对照（流程节点 ↔ 界面 / 样例 ↔ 数据 / 接口 ↔ 验收）没有空格，空格只能是「待拍板」或「本期不做」。
- **DoR 闸门**：实施版必须过 7 条完成定义，才能开正式 PR 过闸；骨架版 / 对照版不合并。
- **保持既有流程**：两段流程、卡片总表、审核档位、合并卡、worktree 锁、拆分规则不变；只是把段一的第 2–4 步写细。
- **简单改动豁免**：改一行、纯查事实、用户说「直接干」仍直接做。

### 非目标

- 不新增第三段流程，不改段二。
- 不要求每个需求都出设计稿；页面卡判「不出」时用样例。
- 不新增运行时拦截、CI、Hook、脚本或自动合并。
- 不把设计稿 / 样例做成独立文档；它们是同一份 spec 的输入或章节。
- 不新增步骤编号；保持 6 步，只重写第 2–4 步的含义。
- 不提高 `SKILL.md` 正文预算（4,700 字符）；新增内容靠压缩既有文字和参考文件承载。
- 不重写历史 spec、不批量改已合并文档。

## 4. 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **页面分叉**：先判动不动页面，判不了摆页面卡，默认不出设计稿 | 没有它：所有需求被同一套流程对待，页面需求缺设计，后端需求被硬塞设计 |

| 4 | **无页面契约样例**：脚本真实运行 / 后端时序 + 请求响应 + 薄切片 / 报表样例表 / 集成失败矩阵 | 没有它：无页面需求没有可判定的靶子，只能靠 prose 吵 |

## 5. 详细规则

### 5.1 先判页面

- agent 先判：看用户 / 操作者是否需要看见或点击界面，不看后端改动多少。
- 判不了才摆**页面卡**：`出设计稿` / `不出，用样例`；推荐项在前，默认按「不出」走。
- 页面卡只定「要不要出设计稿」；不代替机制卡、拆分卡、改旧 spec 卡。

### 5.2 骨架版

同一份 spec 的第一段，不是独立文档。

- **有页面**：主流程骨架——角色、状态、触发、主路径、异常路径、未定清单；一页。
- **无页面**：技术骨架——调用方、输入、输出、状态 / 数据对象、异常路径、未定清单；一页。
- 未定项列在文末，每项写「谁拍 / 截止 / 不决定的后果」；不散在聊天里。
- **有页面**：骨架确认后开 Draft PR，写设计需求（页面、状态、宽度、要回答的问题）；设计到位前不合并。
- **无页面**：不强制 Draft PR；复杂时可用同一 PR 保管骨架和样例。

### 5.3 对照版

#### 2A 有页面

设计稿到位后，在同一 Draft PR 里补：

- 设计稿链接与版本；
- 四列对照：流程节点 ↔ 界面 ↔ 数据 / 接口 ↔ 验收；
- 设计未覆盖的节点、流程未落地的界面、数据缺口；
- 待拍板项与「本期不做」。

对照不是设计评审会；是把空格变成决定或明确的非目标。

#### 2B 无页面

用最便宜的「能判对错」的样例代替设计稿：

| 类型 | 用什么当设计稿 | 必须回答 |
|---|---|---|
| 单出脚本 | 一次真实运行的命令 + stdout / 退出码 + 一次失败样例 | 输入输出、失败怎么办、重跑会怎样 |
| 后端架构 | 时序图 + 请求 / 响应样例 + 状态转移表 + 一条端到端薄切片 | 谁调用、数据从哪来到哪去、哪步会失败 |
| 数据 / 报表 | 一张带真实数字的样例表 + 边界口径 | 指标口径、边界值、异常数据 |
| 集成 | 请求 / 响应样例 + 失败矩阵 | 双方契约、重试 / 降级、版本兼容 |

- 一次性脚本可压缩成一段话 + 一次真实运行，不单独立文档。
- 同样补四列对照；样例回答不了上面三问，就不算合格。

### 5.4 实施版与 DoR

- 把对照结果写回正文，删掉所有「待定」。
- 补：规则、数据 / 接口、验收、迁移 / 回填 / 回滚、兼容、观测。
- 末尾「决策依据」链接 ADR；ADR 只记决定，不复制正文。
- 过 DoR 才开正式 PR 过闸；骨架版 / 对照版不过闸、不合并。

**DoR 七条：**

1. 承重规则只有一个结论，没有 TBD。
2. 每个流程节点有界面 / 样例，或明确「无界面」。
3. 每条写路径单一入口；每个状态有字段、有读侧。
4. 每条验收可执行（命令 / 截图 / 断言）。
5. 数据迁移、回填、回滚、兼容都写了。
6. 外部合同（报表 / 开放平台 / CH）影响与版本写了。
7. ADR 的 supersede 链清楚，spec 正文已同步。

### 5.5 Draft PR 与合并

- 有页面：骨架确认后开 Draft PR；设计到位前不合并。
- 无页面：不强制 Draft PR；复杂时可开，用于保管骨架和样例。
- 设计稿 / 样例到位后，在同一 PR 里补对照和实施版；不另开设计 PR、修订 PR。
- 只有实施版才摆闸卡；骨架版 / 对照版不过闸、不合并。
- 合并卡、审核档位、修订卡照旧；Draft PR 不是批准，设计稿不是验收。

### 5.6 与既有卡 / 拆分的关系

- 页面卡只定「要不要出设计稿」；机制卡、拆分卡、改旧 spec 卡照旧。
- 三个阶段是同一份 spec 的成熟度，不是三份 spec；不触发改旧 spec 卡。
- 拆分按 `references/split-large-spec.md`；每份子 spec 仍走自己的三阶段。
- 简单改动、纯查事实、用户说「直接干」按主文件豁免，不套。

## 8. 自定细节

- **页面卡**：选项「出设计稿」/「不出，用样例」；推荐「不出」；没答按「不出」走。
- **默认策略**：agent 先判页面；只有不确定或新页面 / 新交互、成本明显时才摆卡。
- **Draft PR**：有页面强制；无页面复杂时可选；同一 PR 走到实施版。
- **参考文件名**：`references/spec-maturity.md`。
- **DoR**：固定七条，不再增删；需要扩展时另开 spec。
- **步骤编号**：保持 6 步，不新增编号；第 2–4 步含义重写。
- **预算**：正文 4,700 不涨；新增内容进参考文件和 R34；压缩既有文字腾空间。
- **R34**：记录 #159 / #608 对照、来源日期、决定、代价、验证边界；不在主文件堆案例。
- **不拆**：1 份 spec + 1 张执行 issue；本 spec 自身不拆分。
