## 1. 背景：现在的流程哪里没闭环

PR #122 已把 `release` 备忘录合入，它已有单主线、合并闸、不可变 tag、hotfix 从 tag 切和回滚；但它只做到“发布选择”，没有把发布当成一个完整回路收口。缺的是发布记录账本、`待上线` 的证据门槛、依赖 / 非部署项过滤，以及发布后的验证 / 回填 / 失败回流；发布时逐项处置冲突、临时 release 分支挑 PR，这两处是补丁，不是常规路径。

现状的五个缺口：

1. **就绪没有证据**：`待上线` 只是标签，谁都能挂；没有测试结果或验收评论，标签就是自报。
2. **`待测试` 与 tag 的结构性错位**：按 `issue-status` 定义，`待测试` 已经合进主干；打 tag 必然带上它。发布时对齐只能兜底，根子在上游——要么测试前移，要么未完成功能默认关开关。
3. **依赖与非部署项没过滤**：`docs` / `chore` 不需要生产部署；被依赖的 issue 没就绪时，依赖它的 issue 也不该发。现在的流程都没有判据。
4. **发布后没有回路**：只把标签从 `待上线` 改成 `待验证`，没有验证结果、失败回滚后的 hotfix 回流固定落点。
5. **没有一张发布记录**：范围、证据、主干增量、冲突处置、tag、回滚目标、验证结果散在 issue 评论和发布台账里，无法一眼追溯“这一版到底发了什么、为什么发、出事回哪”。

结论：现在是“发布选择清单”，不是“发布管理闭环”。要补的不是更多分支或标签，而是一张贯穿始终的发布记录和发布后的回流。

## 3. 目标与非目标

### 目标

- 用**一张发布记录**串起范围、依赖、证据、主干增量、冲突处置、tag、回滚目标和发布后验证。
- 用**一个就绪门槛**把 `待上线` 从“标签”变成“有证据的标签”。
- 用**一次主干对齐**发现“搭车代码”；冲突默认是阻塞，只有等 / 关开关 / 回滚三选一。
- 用**一张发布卡**让用户确认发什么、不发什么、风险与回滚 tag，然后才打 tag。
- 用**一个发布后回路**收口：留下项转 `待验证`，无留下项才关单；失败回滚并开 bug / hotfix，回到同一张发布记录。
- 保持 `release` 的选修定位；不采用的项目零负担。

### 非目标

- 不新增 `release` / `release-*` 标签，不新增 issue 类型；发布记录用现有 `chore` 类型，没有 `issue-type` 时不挂类型。
- 不新增长期 `develop` / `uat` / `release` 分支；临时 release 分支只当紧急例外，且须用户同意。
- 不新增 CI、Hook、机器人、GitHub 保护规则或运行时拦截；本次只落 Markdown 规则与文档检查。
- 不改变两段流程、卡片总表、审核档位、合并卡和 worktree 锁。
- 不重写 `issue-status` 的标签定义；`release` 只引用其状态，不另造一套状态词。
- 不把发布时对齐做成逐项选择题；常规路径只有阻塞与三类处置。
- 不回溯历史发布、不批量改已有 issue 状态、不迁移旧发布记录。

## 4. 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **发布记录**：一张 `release: vYYYY.MM.DD` 跟踪 issue（有 `issue-type` 挂 `chore`，没有不挂类型），承载范围、依赖、证据、tag、回滚、hotfix 与验证结果 | 没有它：范围、决策、回滚目标散落，无法追溯“这一版发了什么” |
| 2 | **就绪证据门槛**：`待上线` 必须附通过的测试结果或用户验收评论；没有证据不算就绪 | 没有它：标签自报，发布卡无法判断真假 |
| 3 | **主干增量对齐**：`git log <最近一个生产 tag（含 hotfix tag）>..main` 的 PR 优先按 PR 正文关联 issue 归位，和发布记录比对 | 没有它：`待测试` / `进行中` 的代码会搭车上线 |
| 4 | **发布卡 + 不可变 tag**：用户确认纳入 / 排除 / 风险 / 回滚 tag 后，才打 tag 并从 tag 构建 | 没有它：agent 可能自作主张发布，或从 HEAD 构建出不可追溯产物 |
| 5 | **发布后回路**：验证 → 留下项转 `待验证`、无留下项才关单；失败回滚 → bug / hotfix → 回填同一张记录 | 没有它：发出去就断线，失败没有回流 |
| 6 | **标签与记录分工**：标签管单个 issue 的状态，发布记录管整版的范围和结果 | 没有它：要么用标签硬凑发布状态，要么为每次发布再造一套标签 |

## 5. 发布记录

### 5.1 形式

- 一张 GitHub issue，标题 `release: vYYYY.MM.DD`，类型 `chore`。
- 用 milestone 做分组可以，但 milestone 只是视图；**发布记录是唯一账本**，不维护第二份列表。
- 发布记录在发布前创建，开单挂 `进行中`（这是 `issue-status` §四「开单挂 `未开始`」的例外：发布准备已经动手）；发布后回填；归档 = 关单 + 写结论；验证失败时保持 open，直到回滚 / hotfix 收口。
- 发布成功后发生 hotfix 时，重开同一张记录并追加〈hotfix 记录〉，不新建第二张账本；发布卡选「先不发」时记录保持 open 并写结论，下一轮复用或按用户决定关单。

### 5.2 模板

```markdown
## 发布记录：v2026.11.03

- 目标 tag：v2026.11.03
- 基线 commit：
- 上一个生产 tag（含 hotfix tag）：v...（首次发布写「无 / 部署前快照」）
- 发布窗口 / 发布人：（不适用写「不适用」）

### 本期范围

- [ ] #N 标题（类型 / 状态 / 证据链接）
- [ ] #N 标题（类型 / 状态 / 证据链接）

### 依赖

- #N blocked by #M；#M 未就绪时，本项不发

### 非部署项

- #N docs；或明确不影响生产部署的 chore，合并即算上线，不占本期发布范围 / 不要求单独发布 / 不进发布卡纳入项

### 就绪证据

- #N：通过的测试结果 / 用户验收评论链接（失败记录不算）

### 主干增量核对

- 对齐起点：最近一个生产 tag（含 hotfix tag）：v...
- 生产 tag 到 main 的 PR：#...
- 已通过 hotfix 上线的 PR：#... → 排除，不按搭车阻塞
- 不在本期范围的主干 PR：#... → 处置：等 / 关开关 / 回滚
- 未就绪但已合主干的项：#... → 处置：等 / 关开关 / 回滚
- 非部署项 PR：#... → 列入〈非部署项〉，不按搭车阻塞

### 冲突处置

- #N 待测试 / 进行中 / 待拍板 / 受阻 / 待上线无证据 → 等 / 关开关 / 回滚该合并 / 紧急 release 分支（仅用户同意）
- #N 已通过 hotfix 上线 → 排除，不重发

### 发布结果

- 发布卡确认：确认人 / 时间 / 结论 / 评论链接（含排除项、未知 / 搭车项、已知风险与验证项）
- tag / commit：
- 产物 sha256：（不适用写「不适用」）
- 部署时间：
- 验证：健康检查 / 关键接口 / 错误日志 → 通过 / 失败
- 失败原因与回滚结果：（无失败写「无」）
- 回滚产物核对：可用 / 不可用
- 回滚演练：是 / 否 / 不适用
- 线上版本台账：已更新 / 不适用

### hotfix 记录

- hotfix tag / commit：
- 修复的 issue：
- 失败原因：
- 回滚结果：
- 是否已合回主线：

### 回填

- 按 `issue-status` §三〈上线时分拣〉：留下 → `待验证` + 下次看；转出 → 当场评论；有留下项 → 转 `待验证`，不关单；无留下项 → 评论后关单；全验完 → 关单
- 发布记录归档 = 关单 + 写结论
```

### 5.3 谁维护

- agent 在发布前准备发布记录、拉标签池与主干增量、填冲突项。
- 用户确认发布卡；agent 不打 tag、不部署，直到用户明确确认。
- 发布后 agent 回填结果；失败的记录不关，直到回滚 / hotfix 收口。

## 6. 状态与就绪门槛

| 状态 | 含义 | 发布动作 |
|---|---|---|
| `未开始` / `进行中` | 未进主干或还在改 | 不进本期；已合主干 = 未就绪，按阻塞处置（等 / 关开关 / 回滚） |
| `待测试` | 已合主干，等测试环境验收 | **不进本期**；已合主干 = 阻塞，等 / 关开关 / 回滚 |
| `待上线` | 测试环境验过，或本项目不需要测试环境；等发生产 | 候选；必须有通过的测试结果或用户验收评论，否则按未就绪阻塞 |
| `待验证` | 已上线，剩正式环境验证或批准的长尾项 | 已上线，不重发；不占本期池；其提交已包含在生产 tag（含 hotfix tag）里，对齐时排除 |
| `等拍板` / `受阻` | 等决定或被外部条件卡住 | 不进本期；依赖它的项也阻塞；已合主干 = 未就绪，按阻塞处置 |

规则：

- **证据门槛**：`待上线` 的证据 = issue 评论里**通过的**测试命令 / 结果链接，或用户验收评论；失败记录、只有命令没有结果不算。没有证据 → 未就绪；已合主干时按阻塞处置（等 / 关开关 / 回滚），不能只从发布卡里划掉。
- **阻塞原则**：单主线下，已合进主线的代码无法从 tag 里剔除。未就绪项和搭车项都默认阻塞，只有三类处置；`待测试` / `进行中` / `待拍板` / `受阻` 的已合代码同样适用。
- **非部署项**：`docs` 一律按非部署项；`chore` 只有在明确不影响生产部署时（纯文档 / 仓库杂务）才按非部署项，运行时、配置、依赖变更按部署项进本期。发布前对齐时发现即补进记录〈非部署项〉，不要求预先列全。
- **依赖**：发布记录〈依赖〉列出 blocked by / 父子单；被依赖项未就绪时，依赖项不能进入本期。GitHub 原生依赖可用就用，不可用就手写一行。
- **标签转换**：发布成功后按 `issue-status` §三〈上线时分拣〉执行——能验或方案期批准的长尾 → 留下，转 `待验证` + 「下次看」；不能验且未批准 → 转出，当场评论「以下不在本单跟踪：…」；**有留下项 → 转 `待验证`，不关单**；**无留下项 → 评论后关单**；全验完 → 关单。`待测试` 不动；`待验证` 不动。
- **采用依赖**：`release` 依赖 `issue-status` 提供状态标签；采用动作必须先核这些标签，缺了不写指针、不启用。`chore` 类型由 `issue-type` 提供；没有 `issue-type` 时发布记录标题写 `release:`，不挂类型。
- **回滚目标可用**：上一个生产 tag（含 hotfix tag）的产物可部署，或部署平台能回滚到该 tag；不可用 → 阻塞。首次发布写「无 / 部署前快照」。

## 7. 发布前对齐

### 7.1 顺序

1. **读发布记录**：本期范围、依赖、非部署项、就绪证据。
2. **拉主干增量**：`git log <最近一个生产 tag（含 hotfix tag）>..main`；首次发布以初始基线 commit（仓库第一个 commit）为起点，或使用发布前明确记录并写进发布记录的基线 commit，二选一，不能临时改。PR 归位优先用 PR 正文「关联 issue：#N」（`gh pr list --state merged` 取 body）；commit 标题里的 `#N` 只作线索；squash 合并时不能只看 `git log`；都拿不到 = 未知，不静默放行。已包含在任何生产 tag（含 hotfix tag）里的提交排除；hotfix 合回主线的提交标「已通过 hotfix 上线」，不按搭车阻塞。
3. **对齐四张表**：可发（`待上线` + 通过证据 + 在增量 + 依赖就绪）、未就绪（`待测试` / `进行中` / `等拍板` / `受阻` / `待上线` 无证据）、非部署项（`docs` 一律；`chore` 确认不影响生产部署）、搭车（在增量但不在本期范围、且非非部署项、且非已通过 hotfix 上线）。
4. **冲突处置**：未就绪项和搭车项默认阻塞，只有三类处置——等它验收、关开关、回滚该合并；临时 release 分支只当紧急例外，须用户同意。非部署项不适用这三类处置，直接列〈非部署项〉；已通过 hotfix 上线的项排除，不重发。
5. **发布卡**：列出发什么、不发什么、风险、回滚 tag；用户明确确认后才打 tag。

### 7.2 为什么不做逐项菜单

逐项菜单把“上游没挡住”的失败变成发布时的人工选择题，既慢又容易漏。常规路径只保留三类处置；如果同一版反复出现搭车项，说明合并闸或开关没守住，应回到上游修，而不是在发布时加更多选项。

### 7.3 发布卡

发布卡至少包含：

- 本期纳入的 issue（附证据）；
- 本期排除的 issue 与原因；
- 主干增量里的未知 / 搭车项与处置；
- 目标 tag、基线 commit、回滚 tag，以及回滚产物可用性（首次发布写「无 / 部署前快照」）；
- 已知风险与验证项。

未确认、被关闭、选“先不发”或用户暂停 → 停止，不打 tag、不部署。确认后把发布卡内容（含排除项、未知 / 搭车项、风险与验证项）贴成发布记录评论或写进〈发布结果〉，保持唯一账本完整。

## 8. 发布与 hotfix

- **tag 不可变**：常规发布在要发布的 commit 上打 tag，构建记录基线 commit，发布只从 tag 构建，不从 HEAD 构建。
- **hotfix**：从最近一个生产 tag（含 hotfix tag）切 `hotfix/<tag>-<slug>`；在 hotfix commit 上打临时 tag（如 `v2026.11.03-hotfix.1`），从该 tag 构建上线；修完合回主线，写回同一张发布记录（已归档则重开）。
- **hotfix 对齐**：hotfix 合回主线的提交在下一轮发布前对齐时标「已通过 hotfix 上线」，排除在增量之外，不按搭车阻塞；hotfix tag 列入发布记录的〈hotfix 记录〉。
- **worktree**：hotfix 的 worktree 基准是生产 tag，不是 `origin/main`（主流程工作区规则的例外）；有 issue 号按 `issue-<N>` 锁，无 issue 号按 `worktree-lock.md` 的“没有 issue 号的活”边界。
- **回滚**：重新部署上一个生产 tag（含 hotfix tag）；首次发布没有上一个 tag 时，用部署前快照 / 项目现有回滚方案。首次发布失败不适用 hotfix 路径，先恢复快照或重新发布修复后的新 tag。临时 hotfix tag 保留，不移动、不删除；回滚后开 bug / hotfix，回到发布记录（已归档则重开）。

## 9. 发布后回路

1. **验证**：按项目现有发布验证跑健康检查、关键接口、错误日志；至少覆盖发布记录〈发布结果〉里的验证项。
2. **成功**：按 `issue-status` §三〈上线时分拣〉处理——能验或批准的长尾 → 留下，转 `待验证` + 下次看；不能验且未批准 → 转出，当场评论；**有留下项 → 转 `待验证`，不关单**；**无留下项 → 评论后关单**；全验完 → 关单。发布记录归档 = 关单 + 写结论；更新线上版本台账。
3. **失败**：回滚到上一个生产 tag（含 hotfix tag）；首次发布用部署前快照 / 项目现有回滚方案，不从失败的目标 tag 切 hotfix；开 bug / hotfix；在发布记录写失败原因、回滚结果；下一轮按 hotfix 路径回到同一张记录（已归档则重开）。
4. **长尾**：`待验证` 的正式环境验证项按 `issue-status` 的“下次看”规则收口；不占下一期发布池。

## 12. 验收标准

### 12.1 场景

| # | 场景 | 期望 |
|---|---|---|
| V01 | 本期 `待上线` 都有证据，主干增量无搭车 | 发布卡确认 → 打 tag → 从 tag 构建 → 按上线时分拣回填 |
| V02 | `待测试` 代码已在主干，不在本期范围 | 阻塞；用户选等 / 关开关 / 回滚；未处置前不打 tag |
| V03 | `待上线` 但没有测试 / 验收证据 | 不算就绪；已合主干时按阻塞处置，不能只从发布卡划掉；未处置前不打 tag |
| V04 | `docs` 或明确不影响生产部署的 `chore` 已合并 | 列入非部署项；不占本期发布范围；不要求 tag；不进发布卡纳入项；运行时 / 配置 / 依赖类 `chore` 按部署项进本期 |
| V05 | #A blocked by #B，#B 未就绪 | #A 阻塞；发布记录写明依赖；不静默发 #A |
| V06 | 生产 bug 需要 hotfix | 从最近一个生产 tag（含 hotfix tag）切；打临时 hotfix tag；从 tag 构建；合回主线；写回发布记录；下一轮对齐标「已通过 hotfix 上线」 |
| V07 | 发布后验证失败，且上一个生产 tag 产物可用 | 回滚到上一个生产 tag；开 bug / hotfix；发布记录保持 open 直到收口 |
| V08 | 上一期 `待验证` 还有正式环境验证项 | 不占本期发布池；不阻塞本期；其在增量里的提交按已上线排除，不按搭车 |
| V09 | 主干有 PR 没关联 issue | 优先按 PR 正文「关联 issue：#N」归位；正文和 commit 都拿不到 = 列为“未知”，用户确认前不静默放行 |
| V10 | 用户在发布卡选“先不发” | 停止；不打 tag、不部署 |
| V11 | 首次发布，没有上一个生产 tag | 以初始基线 commit（仓库第一个 commit）或发布前明确记录的基线 commit 对齐；回滚写「无 / 部署前快照」；首次失败先恢复快照 / 重新发布，hotfix 首次不适用 |

## 13. 自定细节

- 发布记录类型用 `chore`，标题 `release: vYYYY.MM.DD`；没有 `issue-type` 时不挂类型。
- `release` 依赖 `issue-status`；采用动作先核 `进行中` / `待上线` / `待验证` 标签，缺了不启用。
- 首次发布以仓库第一个 commit 对齐，或使用发布前明确记录并写进发布记录的基线 commit；回滚写「无 / 部署前快照」；首次失败先恢复快照 / 重新发布。
- 发布记录挂 `进行中`（`issue-status` §四 的例外）；归档 = 关单 + 写结论；hotfix 重开同一张记录并追加〈hotfix 记录〉；选「先不发」保持 open 写结论。
- 模板只留在 `release-discipline.md`，不抄进 `apply`。
- milestone 可选；有 milestone 也不另维护列表。
- 证据放 issue 评论，必须是**通过的**测试结果或用户验收评论；失败记录不算。
- 常规发布 tag 用 `vYYYY.MM.DD`；hotfix 用 `vYYYY.MM.DD-hotfix.N`；生产 tag 含 hotfix tag。
- 发布卡未确认 / 选“先不发” → 停止，不打 tag、不部署。
- 未就绪项和搭车项默认阻塞；临时 release 分支只在用户明确同意时使用。
- `docs` 一律非部署；`chore` 仅在明确不影响生产部署时按非部署项。
- 发布记录验证失败时保持 open，直到回滚 / hotfix 收口。
