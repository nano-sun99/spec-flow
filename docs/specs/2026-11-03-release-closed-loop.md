## 1. 背景：现在的流程哪里没闭环

PR #122 已把 `release` 备忘录合入，但它只做到“发布选择”：用 `待上线` 标签圈候选、和主干增量对齐、用户确认后打 tag。它没有把发布当成一个完整回路收口，而且发布时逐项处置冲突、临时 release 分支挑 PR，这两处是补丁，不是常规路径。

现状的五个缺口：

1. **就绪没有证据**：`待上线` 只是标签，谁都能挂；没有测试结果或验收评论，标签就是自报。
2. **`待测试` 与 tag 的结构性错位**：按 `issue-status` 定义，`待测试` 已经合进主干；打 tag 必然带上它。发布时对齐只能兜底，根子在上游——要么测试前移，要么未完成功能默认关开关。
3. **依赖与非部署项没过滤**：`docs` / `chore` 不需要生产部署；被依赖的 issue 没就绪时，依赖它的 issue 也不该发。现在的流程都没有判据。
4. **发布后没有回路**：只把标签从 `待上线` 改成 `待验证`，没有验证结果、失败回滚、hotfix 回流。
5. **没有一张发布记录**：范围、证据、主干增量、冲突处置、tag、回滚目标、验证结果散在 issue 评论和发布台账里，无法一眼追溯“这一版到底发了什么、为什么发、出事回哪”。

结论：现在是“发布选择清单”，不是“发布管理闭环”。要补的不是更多分支或标签，而是一张贯穿始终的发布记录和发布后的回流。

## 3. 目标与非目标

### 目标

- 用**一张发布记录**串起范围、依赖、证据、主干增量、冲突处置、tag、回滚目标和发布后验证。
- 用**一个就绪门槛**把 `待上线` 从“标签”变成“有证据的标签”。
- 用**一次主干对齐**发现“搭车代码”；冲突默认是阻塞，只有等 / 关开关 / 回滚三选一。
- 用**一张发布卡**让用户确认发什么、不发什么、风险与回滚 tag，然后才打 tag。
- 用**一个发布后回路**收口：成功转 `待验证` / 关单；失败回滚并开 bug / hotfix，回到同一张发布记录。
- 保持 `release` 的选修定位；不采用的项目零负担。

### 非目标

- 不新增 `release` / `release-*` 标签，不新增 issue 类型；发布记录用现有 `chore` 类型。
- 不新增长期 `develop` / `uat` / `release` 分支；临时 release 分支只当紧急例外，且须用户同意。
- 不新增 CI、Hook、机器人、GitHub 保护规则或运行时拦截；本次只落 Markdown 规则与文档检查。
- 不改变两段流程、卡片总表、审核档位、合并卡和 worktree 锁。
- 不重写 `issue-status` 的标签定义；`release` 只引用其状态，不另造一套状态词。
- 不把发布时对齐做成逐项选择题；常规路径只有阻塞与三类处置。
- 不回溯历史发布、不批量改已有 issue 状态、不迁移旧发布记录。

## 4. 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **发布记录**：一张 `release: vYYYY.MM.DD` 跟踪 issue（type `chore`），承载范围、依赖、证据、tag、回滚与验证结果 | 没有它：范围、决策、回滚目标散落，无法追溯“这一版发了什么” |
| 2 | **就绪证据门槛**：`待上线` 必须附测试结果或验收评论；没有证据不算就绪 | 没有它：标签自报，发布卡无法判断真假 |
| 3 | **主干增量对齐**：`git log <上个生产 tag>..main` 的 PR 按关联 issue 归位，和发布记录比对 | 没有它：`待测试` / `进行中` 的代码会搭车上线 |
| 4 | **发布卡 + 不可变 tag**：用户确认纳入 / 排除 / 风险 / 回滚 tag 后，才打 tag 并从 tag 构建 | 没有它：agent 可能自作主张发布，或从 HEAD 构建出不可追溯产物 |
| 5 | **发布后回路**：验证 → 成功转 `待验证` / 关单；失败回滚 → bug / hotfix → 回填同一张记录 | 没有它：发出去就断线，失败没有回流 |
| 6 | **标签与记录分工**：标签管单个 issue 的状态，发布记录管整版的范围和结果 | 没有它：要么用标签硬凑发布状态，要么为每次发布再造一套标签 |

## 5. 发布记录

### 5.1 形式

- 一张 GitHub issue，标题 `release: vYYYY.MM.DD`，类型 `chore`。
- 用 milestone 做分组可以，但 milestone 只是视图；**发布记录是唯一账本**，不维护第二份列表。
- 发布记录在发布前创建，发布后回填；验证失败时保持 open，直到回滚 / hotfix 收口。

### 5.2 模板

```markdown
## 发布记录：v2026.11.03

- 目标 tag：v2026.11.03
- 基线 commit：
- 回滚 tag：上一个生产 tag
- 发布窗口：
- 发布人：

### 本期范围

- [ ] #N 标题（类型 / 状态 / 证据链接）
- [ ] #N 标题（类型 / 状态 / 证据链接）

### 依赖

- #N blocked by #M；#M 未就绪时，本项不发

### 非部署项

- #N docs / chore，合并即算上线，不进生产 tag

### 就绪证据

- #N：测试结果 / 验收评论链接

### 主干增量核对

- 上个生产 tag：v...
- 上个 tag 到 main 的 PR：#...
- 不在本期范围的主干 PR：#... → 处置：等 / 关开关 / 回滚

### 冲突处置

- #N 待测试 / 进行中 → 等 / 关开关 / 回滚该合并 / 紧急 release 分支（仅用户同意）

### 发布结果

- tag / commit：
- 产物 sha256：
- 部署时间：
- 验证：健康检查 / 关键接口 / 错误日志
- 回滚演练：是 / 否

### 回填

- 待上线 → 待验证 / 关单
- 发布记录归档
```

### 5.3 谁维护

- agent 在发布前准备发布记录、拉标签池与主干增量、填冲突项。
- 用户确认发布卡；agent 不打 tag、不部署，直到用户明确确认。
- 发布后 agent 回填结果；失败的记录不关，直到回滚 / hotfix 收口。

## 6. 状态与就绪门槛

| 状态 | 含义 | 发布动作 |
|---|---|---|
| `未开始` / `进行中` | 未进主干或还在改 | 不进本期；出现在主干增量里 = 异常，先查 |
| `待测试` | 已合主干，等测试环境验收 | **不进本期**；出现在主干增量里 = 阻塞，等 / 关开关 / 回滚 |
| `待上线` | 测试环境验过，或本项目不需要测试环境；等发生产 | 候选；必须有验收证据，否则不算就绪 |
| `待验证` | 已上线，剩正式环境验证或批准的长尾项 | 已上线，不重发；不占本期池 |
| `等拍板` / `受阻` | 等决定或被外部条件卡住 | 不进本期；依赖它的项也阻塞 |

规则：

- **证据门槛**：`待上线` 的证据 = issue 评论里的测试命令 / 结果链接，或用户验收评论；没有证据 → 不就绪，不进发布卡。
- **非部署项**：`docs` / `chore` 或明确不需要生产部署的项，在发布记录〈非部署项〉列出，合并即算上线，不要求 tag。
- **依赖**：发布记录〈依赖〉列出 blocked by / 父子单；被依赖项未就绪时，依赖项不能进入本期。GitHub 原生依赖可用就用，不可用就手写一行。
- **标签转换**：发布成功后，本期 `待上线` 转 `待验证`（有正式环境验证项）或关单；`待测试` 不动；`待验证` 不动。

## 7. 发布前对齐

### 7.1 顺序

1. **读发布记录**：本期范围、依赖、非部署项、就绪证据。
2. **拉主干增量**：`git log <上个生产 tag>..main`，把 PR 按“关联 issue：#N”归位；无关联的 PR 单独列为“未知”，不静默放行。
3. **对齐三张表**：可发（`待上线` + 证据 + 在增量）、未就绪（`待测试` / `进行中` / `等拍板` / `受阻`）、搭车（在增量但不在本期范围）。
4. **冲突处置**：搭车项默认阻塞，只有三类处置——等它验收、关开关、回滚该合并；临时 release 分支只当紧急例外，须用户同意。
5. **发布卡**：列出发什么、不发什么、风险、回滚 tag；用户明确确认后才打 tag。

### 7.2 为什么不做逐项菜单

逐项菜单把“上游没挡住”的失败变成发布时的人工选择题，既慢又容易漏。常规路径只保留三类处置；如果同一版反复出现搭车项，说明合并闸或开关没守住，应回到上游修，而不是在发布时加更多选项。

### 7.3 发布卡

发布卡至少包含：

- 本期纳入的 issue（附证据）；
- 本期排除的 issue 与原因；
- 主干增量里的未知 / 搭车项与处置；
- 目标 tag、基线 commit、回滚 tag；
- 已知风险与验证项。

未确认、被关闭、选“先不发”或用户暂停 → 停止，不打 tag、不部署。

## 8. 发布与 hotfix

- **tag 不可变**：常规发布在要发布的 commit 上打 tag，构建记录基线 commit，发布只从 tag 构建，不从 HEAD 构建。
- **hotfix**：从生产 tag 切 `hotfix/<tag>-<slug>`；在 hotfix commit 上打临时 tag（如 `v2026.11.03-hotfix.1`），从该 tag 构建上线；修完合回主线，写回同一张发布记录。
- **worktree**：hotfix 的 worktree 基准是生产 tag，不是 `origin/main`（主流程工作区规则的例外）；有 issue 号按 `issue-<N>` 锁，无 issue 号按 `worktree-lock.md` 的“没有 issue 号的活”边界。
- **回滚**：重新部署上一个生产 tag；临时 hotfix tag 保留，不移动、不删除；回滚后开 bug / hotfix，回到发布记录。

## 9. 发布后回路

1. **验证**：按项目现有发布验证跑健康检查、关键接口、错误日志；至少覆盖发布记录〈发布结果〉里的验证项。
2. **成功**：本期 `待上线` 转 `待验证` 或关单；发布记录归档；更新线上版本台账。
3. **失败**：回滚到上一个生产 tag；开 bug / hotfix；在发布记录写失败原因、回滚结果；下一轮按 hotfix 路径回到同一张记录。
4. **长尾**：`待验证` 的正式环境验证项按 `issue-status` 的“下次看”规则收口；不占下一期发布池。

## 12. 验收标准

### 12.1 场景

| # | 场景 | 期望 |
|---|---|---|
| V01 | 本期 `待上线` 都有证据，主干增量无搭车 | 发布卡确认 → 打 tag → 从 tag 构建 → 回填 `待验证` / 关单 |
| V02 | `待测试` 代码已在主干，不在本期范围 | 阻塞；用户选等 / 关开关 / 回滚；未处置前不打 tag |
| V03 | `待上线` 但没有测试 / 验收证据 | 不算就绪；不进发布卡 |
| V04 | `docs` / `chore` 已合并，不需要生产部署 | 列入非部署项；不要求 tag，不占发布池 |
| V05 | #A blocked by #B，#B 未就绪 | #A 阻塞；发布记录写明依赖；不静默发 #A |
| V06 | 生产 bug 需要 hotfix | 从生产 tag 切；打临时 hotfix tag；从 tag 构建；合回主线；写回发布记录 |
| V07 | 发布后验证失败 | 回滚到上一个生产 tag；开 bug / hotfix；发布记录保持 open 直到收口 |
| V08 | 上一期 `待验证` 还有正式环境验证项 | 不占本期发布池；不阻塞本期 |
| V09 | 主干有 PR 没关联 issue | 列为“未知”；用户确认前不静默放行 |
| V10 | 用户在发布卡选“先不发” | 停止；不打 tag、不部署 |

## 13. 自定细节

- 发布记录类型用 `chore`，标题 `release: vYYYY.MM.DD`。
- milestone 可选；有 milestone 也不另维护列表。
- 证据放 issue 评论，不新增字段。
- 常规发布 tag 用 `vYYYY.MM.DD`；hotfix 用 `vYYYY.MM.DD-hotfix.N`。
- 发布卡未确认 / 选“先不发” → 停止，不打 tag、不部署。
- 冲突默认阻塞；临时 release 分支只在用户明确同意时使用。
- 发布记录验证失败时保持 open，直到回滚 / hotfix 收口。
